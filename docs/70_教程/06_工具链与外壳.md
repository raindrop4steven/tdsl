## 1. 全景：编译器与它的使用者

```
                 ┌─────────── 编译主干（00-05 已讲）───────────┐
  todo.tdsl ──▶ parse ──▶ Typed AST ──▶ typecheck ──▶ codegen（java/react）
                 └──────────────────────────────────────────────┘
                        ▲              ▲              ▲              ▲
              cli（07） │    llm（08） │   server（09）│   eval（10） │
              人敲命令    LLM 拿 prompt   agent 沙箱调用    样卷跑批
```

四个使用者的共同形态：**拿着同一套管线 API 干不同的事**——
cli 给人用（命令行）、llm 给 LLM 备料（prompt）、server 给 agent 用（工具）、eval 给研究者用（指标）。

## 3. 三个贯穿外壳的设计决策

1. **逻辑层纯函数 + 薄封装**：cli 的 `run(argv)`、server 的 `compileSandbox`、llm 的 `composePrompt` 全是可测纯函数；打印/工具注册/API 路由只是薄壳。单测全走逻辑层。
2. **LLM 通道与编译器分离**：llm 包零 API 调用；server/eval 各自接 LLM（pi SDK / 直发 fetch），共享同一套 Prompt Pack 与裁判。
3. **反馈闭环分层**：编译诊断（确定）→ 运行日志（半确定）→ 用户实测（最终）——三层回流各有通道（feedback 文本 / logTail grep / client.log）。

## 4. playground —— 浏览器试验台（P2，体量小不独立成篇）

`pipeline.ts` 的 `compile` 纯函数：parse → typecheck → 双端 generate，与 slice 同路径。
Monaco **强制本地打包**（离线安全，与设计稿"必要时 CDN"相反——演示不能赌网络）+ 自写 monarch 高亮（不用 TS 语言服务——TDSL 不是 TS，红色波浪线是噪音）。四面板：诊断 / AST / Java / React，300ms 防抖。6 单测。

## 5. 本篇要记住的 3 件事

1. **外壳不造语义**：所有"懂 TDSL"的逻辑都在编译主干，外壳只做编排/备料/回流——修 bug 修一处全线受益。
2. **人工收窄是 FFI 的质量闸门**：bundle-jar 产物是"反射全量 → 精选"的收敛过程，机器扫全量、人定语义。
3. **验证链自动化**：单测锁示例 → check-spec 锁覆盖度 → eval 锁生成质量——三层都不靠人眼。

**动手练习**：依次跑 `npm run tdsl -- check examples/todo-multi/tdsl`、`npm run check-spec -w jxc`、`npm run playground`，感受同一个编译器的三种打开方式。
