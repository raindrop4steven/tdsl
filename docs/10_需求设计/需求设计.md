# 需求设计：自研低代码 DSL（TDSL）

> 前置阅读：`00_参考资料/NASL调研.md`
> 定位：回答"要做什么、为什么这样做"，输入产出需求、顶层目标与关键取舍。

---

## 1. 背景与目标

我们要做一个**用大模型生成低代码系统**的平台。核心思路参考网易 CodeWave 的 NASL，
但**摆脱其面向编辑器（前端视角）的 JSON AST**，从编译器/LLM 视角重新设计一套 DSL。

### 目标
- 用 TypeScript 定义一套自有 DSL。
- 让**大模型**来"写"这套 DSL（而不是手写业务代码）。
- 从 DSL 编译生成 **React 前端** 和 **Java(Spring) 后端** 代码。
- 语义内核干净、类型化、可分析、可检查（合格的中间表示）。

### 非目标（范围外，第一版不做）
- 不直接让 LLM 生成"手写 React/Java 业务代码"（那不是 DSL，失去语义控制力）。
- 不实现完整的在线可视化编辑器 UI（但预留编辑器元信息分层）。
- 不实现应用编排/发布流水线。

---

## 2. 核心路线（一句话）

> **让大模型用其近乎本能的 TypeScript 语法来"写" DSL（TS 书写投影 = 书写面），
> 我们把它解析成干净、类型化的语义 AST（语义核），再由 AST 编译生成 React + Java。**

即：**LLM 写 TS（书写面）→ 炼 Typed AST（语义核）→ 生成 React/Java（产物）**

三个消费端因此都顺：
1. **给 LLM 写** → TS 风格，训练语料多、近乎本能、少幻觉。
2. **给编译器炼** → 类型化 AST，才是合格的中间表示。
3. **给用户/产物** → AST 生成 React/Java。

---

## 3. 关键决策（取舍）与理由

### D1：事实来源用 Typed AST，而非 JSON AST
- NASL 把 JSON AST 当事实来源，为了编辑器渲染塞入 `concept`/`ruleMap`，前端视角、编译器业余。
- 我们：**类型化对象树作为唯一事实来源（SSoT）**；JSON 只是它的可序列化视图（存储/流通/LLM 中间产物）。

### D2：节点用强类型判别联合，而非运行时字符串 concept
- NASL 用字符串 `concept` + `switch`，无编译期检查、易拼错、重构不友好。
- 我们：判别联合的 `kind` 字面量即标签，`never` 收窄保证穷尽处理，新增节点未处理时编译报错。

### D3：跨节点引用用符号引用 + 编译期 resolve 绑定
- NASL 用 `typeNamespace`+`typeName` 字符串拼接，改名需全文改串。
- 我们：AST 中以 **nodePath 字符串** 保存引用（兼容 JSON/LLM/TS书写面），编译期 `resolve` 为真实对象并校验，
  悬空/改名引用被编译器捕获。

### D4：逻辑体 —— 书写层用 TS 语法子集（LLM 本能），AST/语义层是自研的
> 澄清一个重要问题："自研语言"会不会大模型不认识？
> 答：**不会，因为我们不自创语法。**"自研"只指 AST/语义（编译核心）是我们自己的；
> **书写层直接照 TS 语法子集**，这正是大模型训练语料里最庞大的、近乎本能的东西。

- NASL 逻辑体是拖拽型"场景脚本树"。
- 我们的方案分两层，兼顾"LLM 写得稳"和"语义可控/可编译/可检查"：
  - **书写/解析层（LLM 写的面）**：TS 语法**严格子集**（`if`/`for`/`return`/`new`/`a.b.c()`/字面量，`:=` 归一为赋值等）。
    大模型以其本能输出，`tsc` 可辅助校验语法。
  - **AST/语义层（编译核心）**：parser 把 TS 子集编译为**自研类型化节点树**，由自家生成器映射到 React/Java。
- 平台差异在生成器做翻译（`===`→`equals` 等），书写面恒定 TS 风格。

### D5：TS 书写投影是 LLM 主入口（借鉴 NASL 的 Natural TS，但转为主要输入面）
- NASL 的 Natural TS 只当展示投影。
- 我们：**TS 风格 DSL(TDSL) 作为 LLM 输出的主书写面**，`tsc` 可辅助校验语法，parser 编译为 AST。

### D6：编辑器 UI 元信息独立分层
- NASL 把布局/label 等混入 `ruleMap`/`annotations` 污染语义。
- 我们：语义核只放语义性注解；UI/布局元信息单独分层（第一版可延后）。

### D7：类型系统做到"较重：完整类型检查器"
- 定位：接近真实编译器的类型检查层。
- 范围：类型推导（局部推断）、子类型/赋值兼容、隐式转换（`Integer→Decimal`）、泛型实例化（`List<T>`）、
  统一（unification）用于泛型调用推断、可识别类型错误并给出诊断（带 nodePath/行列）。
- 这是编译期"语义可信"的保障，也是生成正确 React/Java 的重要前提。

- [ ] 一个端到端示例（Todo），能编译运行。

> 语义核（Typed AST）即事实来源。但保留扩展能力：未来若要接入编辑器/外部系统，可在 core 之上按需补序列化层，
> 不改变语义核本身。P1 聚焦"让语义可信"的类型系统。

- [x] nodePath 寻址与 `resolve`/`nodePathOf` 工具（P0 已实现）。

---

## 5. 验收标准（需求层面）
1. 一段自然语言需求 → 能端到端产出可编译的 React + Java 工程（P0 demo 范围内）。
2. 廉价、自动化：LLM 生成的 DSL 能被 parse + 校验 + 编译，语法错误可定位。
3. 语义可复用：同一份 Typed AST 可分别生成 React 与 Java，保持一致语义。
4. 可演进：新增节点类型时，编译器/生成器能强制要求处理（never 穷尽）。
