# 第 3 章 词法分析：从字符流到 Token 流

词法分析是编译器的第一道工序——它把一长串字符变成一组有意义的 Token，为后续的语法分析提供结构化的输入。

## 3.1 形式化基础：正则语言与有限自动机

词法分析处理的是**正则语言**——所有编程语言的词法规则都可以用正则表达式描述。

正则语言可以被有限自动机（Finite Automaton）识别。一个确定性有限自动机（DFA）由五元组定义：

```
DFA = (Q, Σ, δ, q₀, F)
```

其中 `Q` 是状态集合，`Σ` 是输入字母表，`δ` 是转移函数，`q₀` 是初始状态，`F` 是接受状态集合。

例如，TDSL 的标识符（identifier）可以用以下 DFA 描述：

```
状态：{start, in_ident, accept, reject}
字母表：{a-z, A-Z, 0-9, _, $}
转移：
  start --[a-zA-Z_$]--> in_ident
  in_ident --[a-zA-Z0-9_$]--> in_ident
  in_ident --[其他]--> accept
  start --[其他]--> reject
```

词法分析器本质上就是一个大 DFA——每个 Token 类型对应一组正则规则，lexer 逐字符消费输入，匹配最长前缀，产出 Token。

但实际实现中，手写 lexer 通常不用 DFA 而用**顺序尝试**：按优先级依次尝试每种 Token 的匹配规则，第一个成功的就是结果。TDSL 的 lexer 就是这种实现。

## 3.2 Token 的设计

TDSL 的 Token 类型一共只有五种（文件 `packages/parser/src/lexer.ts:1`）：

| Token 类型 | 描述 | 示例 |
|-----------|------|------|
| `ident` | 标识符（字母/下划线/`$` 开头） | `Order`, `createOrder`, `total`, `$route` |
| `number` | 数字字面量 | `0`, `3.14`, `100` |
| `string` | 字符串字面量（单引号或双引号） | `'hello'`, `'%'`, `"g:a:v"` |
| `punct` | 标点符号与运算符 | `{`, `(`, `===`, `<=`, `:=` |
| `eof` | 文件结束哨兵 | `<eof>` |

**为什么 Token 类型这么少？** 因为 TDSL 把"削减词汇表"做到了极致：**关键字不是独立类型**（`entity`、`page` 都是 `ident`，parser 看 `value` 判断）、**注解不是独立类型**（`@` 是一个单字符 `punct`，`@pk` 是 `@`、`pk` 两个 Token，parser 在声明处按需收集）、**括号/逗号/点都是上下文相关的 `punct`**（`<` 既可能是泛型尖括号也可能是小于号，由 parser 的上下文决定归属）。

把语义判断全部推迟到 parser，lexer 就退化成了一个完全无状态的字符扫描器——它的五条规则本质上对应正则语言 §3.1 里的五种模式（标识符 / 数字 / 字符串 / 空白与注释 / 标点）。tokens 少，parser 反而工作量变大了：它需要用"看后缀猜角色"的方式来分派（这正是第 4、5 章的核心）。

**为什么字符串同时支持单引号和双引号？** 引用原文 `lexer.ts:47`：`if (ch === "'" || ch === '"')`。两种引号都能开启字符串字面量。但**书写约定**上 TDSL 强制用单引号——数据源注解 `@datasource("erp")`、依赖坐标 `dependency java "g:a:v"` 这类"带引号的元数据"才用双引号。这种区分让 LLM 在生成时能凭引号种类判断"这是业务字符串还是元数据标识"。

## 3.3 行列信息追踪

每个 Token 都携带行列信息：

```ts
interface Token {
  type: TokenType;
  value: string;
  line: number;   // 行号（从 1 开始）
  col: number;    // 列号（从 1 开始）
}
```

行列信息是错误定位的基础。当 parser 遇到语法错误时，它可以报告"第 5 行第 12 列：预期 `}` 但得到 `)`"。当 typecheck 发现类型错误时，它可以报告"节点 `app.logics.createOrder` 第 3 行：参数类型不匹配"。

lexer 在处理换行符时递增行号、重置列号。这个看似简单的逻辑是错误消息质量的基础——没有准确的行列信息，用户（和 LLM）就无法定位错误。

## 3.4 手写 Lexer 的决策

TDSL 的 lexer 是手写的，没有使用 lex/flex 等生成工具。这个决策基于三个考量：

1. **控制力**：手写 lexer 可以精确定义错误消息的格式和内容。生成工具产生的 lexer 通常使用固定的错误模板，难以定制。

2. **零依赖**：TDSL 的编译器是 npm 包，目标是零运行时依赖。引入 lex/flex 意味着引入额外的构建工具链。

3. **教学透明**：手写 lexer 的每一行代码都可以被读者理解，没有生成代码的黑箱。

## 3.5 Lexer 实现精读

TDSL 的 `tokenize` 函数是一个 while 循环，每次迭代消费零到多个字符，产出一个 Token：

下面还原实际实现骨架（`lexer.ts:13`），注释省略了行列维护细节以便聚焦结构：

```ts
const PUNCT_SINGLE = '{}()[];,:.=<>!+-*/@';

export function tokenize(input: string): Token[] {
  const tokens: Token[] = [];
  let i = 0, line = 1, col = 1;
  while (i < input.length) {
    const ch = input[i];
    if (ch === '\n') { line++; col = 1; i++; continue; }      // 换行
    if (ch === ' ' || ch === '\t' || ch === '\r') { i++; col++; continue; }  // 空白
    if (ch === '/' && input[i + 1] === '/') {                 // // 单行注释
      while (i < input.length && input[i] !== '\n') i++;
      continue;
    }
    const startLine = line, startCol = col;
    if (ch === "'" || ch === '"') {                            // 字符串
      // 匹配到配对的引号，产出 string Token
    }
    if (/[0-9]/.test(ch)) {                                    // 数字
      // 匹配 [0-9.] 系列字符，产出 number Token
    }
    if (/[A-Za-z_$]/.test(ch)) {                               // 标识符（含 $ 前缀占位符）
      // 匹配 [A-Za-z0-9_$]，产出 ident Token
    }
    const three = input.slice(i, i + 3);                       // 三字符运算符
    if (three === '===' || three === '!==') { /* ... */ }
    const two = input.slice(i, i + 2);                         // 双字符运算符
    if (two === '&&' || two === '||' || two === '<=' || two === '>=' || two === ':=') { /* ... */ }
    if (PUNCT_SINGLE.includes(ch)) { /* 单字符标点 */ }
    throw new Error(`unexpected char '${ch}' at ${line}:${col}`);  // 非法字符
  }
  tokens.push({ type: 'eof', value: '<eof>', line, col });
  return tokens;
}
```

几个实现要点：

**标点匹配的优先级（最长匹配）。** 标点按**字符数降序**尝试：先 `===`/`!==`（三字符），再 `&&`/`||`/`<=`/`>=`/`:=`（双字符），最后单字符。否则 `>` 会被先匹配为单字符标点，导致 `>=` 被错误拆成两个 Token。注意列出的双字符集合里没有 `=`——因为 `=` 保留下来单独做赋值/键值分隔符，而比较相等用三字符的 `===`，与 JavaScript 一致。

**为什么还有 `:=`？** `:=` 是 P0 时代的赋值语法（受 NASL 影响），TS 化之后在语法层已删除（写成 `:=` 会报"已废弃"的专用错误）。token 保留下来，只是为了在报那条专用错误时词法能正常切分——如果我们删掉它，`a := 5` 会先撞一个难懂的 `unexpected char ':'`。

**注释的处理。** TDSL 只支持 `//` 单行注释。lexer 遇到 `//` 时跳到行尾——注释不是 Token，不会出现在 Token 流中。这与 C/Java/TypeScript 的行为一致，但避开了块注释的实现负担（`/* ... */` 需要状态机处理嵌套/跨行）。

**`$` 开头的标识符。** `[A-Za-z_$]` 允许 `$` 打头，用于 `$route`、`$data` 这类 codegen 注入的前端占位符值。这是词法迎合代码生成的一处细节——占位符以合法标识符形态出现，就不需要给 lexer 额外开一种 Token 类。

**行列信息的维护（重要）。** 每消费一个字符 `col++`；遇换行 `line++` 且 `col = 1`。关键是 Token 的行列在**匹配开始前**记录（`startLine = line, startCol = col`），而不是匹配结束时——这保证错误消息指向 Token 的起始位置，方便人眼定位。

**非法字符直接抛错。** `unexpected char` 是 lexer 层唯一的错误形态，用普通 `Error` 抛出（带行列）。语法层面的行号/列号/文件由第 4 章的 `TdslSyntaxError` 负责；词法层的失败被 `parseProject` 捕获后同样带上 `file` 字段重新抛出（`parser.ts:63-71`）。

## 3.6 词法歧义的消解

词法分析中的歧义是指**一个前缀可以被多种 Token 规则匹配**。TDSL 有几种典型的歧义：

### 标识符 vs 关键字

`entity` 既可以是一个标识符（用户定义的变量名），也可以是一个关键字（声明实体的保留字）。TDSL 的解决方案是：lexer 产出的 Token 类型统一是 `ident`，parser 在解析时检查 `value` 是否是保留字。

这种"lexer 不区分关键字和标识符"的策略简化了 lexer——lexer 只需要关心"这是不是一个合法的标识符"，不需要维护关键字表。代价是 parser 需要额外的保留字检查，但这个检查很廉价。

### 数字 vs 成员访问

`3.14` 是一个浮点数字面量，但 `order.total` 中的 `.` 是成员访问运算符。lexer 如何区分？

关键在于**上下文无关的最长匹配**：lexer 看到 `3.14` 时，从位置 0 开始匹配数字规则——`3` 匹配，`.` 匹配（数字的小数点），`14` 匹配。整个 `3.14` 被作为一个数字 Token 产出。

但 `order.total` 的情况不同：`order` 先被匹配为标识符，然后 `.` 被匹配为标点（成员访问），`total` 被匹配为另一个标识符。lexer 不会把 `order.total` 当作一个整体来匹配——因为标识符规则不包含 `.`。

这种歧义消解依赖于**规则的定义方式**：数字规则包含 `.`，标识符规则不包含 `.`。lexer 从当前位置开始，按优先级依次尝试每种规则，第一个成功的就是结果。

## 3.7 TdslSyntaxError 的生成

严格说，`TdslSyntaxError` 定义在 parser 层而非 lexer 层（`parser.ts:34-45`）：

```ts
export class TdslSyntaxError extends Error {
  constructor(
    message: string,
    public readonly line: number,
    public readonly col: number,
    public file?: string,       // 多文件场景由 parseProject 外层填充
  ) {
    super(`${message} (line ${line}, col ${col})`);
    this.name = 'TdslSyntaxError';
  }
}
```

分工是这样的：

- **lexer 遇到非法字符**直接抛普通 `Error`（`unexpected char ...`，不带类型标签）；
- **parser 遇到意外 Token / 语法不一致**抛 `TdslSyntaxError`（带 line/col）；
- **`parseProject` 捕获任何词法/语法错误**，如果 `file` 字段缺失就补上当前分片路径再向上抛（`parser.ts:63-71`）。

这样所有下游（CLI、Playground、LLM 诊断管线）拿到的错误对象都有一个统一的形态：`message + line + col + file`。类型检查阶段的 `Diagnostic` 与此同构但更结构化（路径 + 严重级别，见第 6 章）。

## 3.8 词法分析的地位

词法分析是编译器中最简单的阶段——TDSL 的 lexer 只有 125 行代码。但它的质量直接影响整个编译器的用户体验：没有准确的行列信息，后续所有阶段的错误消息都无法定位。

词法分析也是编译器中**与语言理论联系最紧密**的阶段——正则语言、有限自动机、最长匹配原则，这些概念直接映射到代码实现。后续的语法分析会进入上下文无关文法的领域，理论复杂度会上升一个层次。
