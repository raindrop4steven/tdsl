# 第 11 章 FFI 与外部能力：Java/npm 一等公民

> 这是 TDSL 区别于一般 DSL 编译器的核心设计。大多数教学 DSL 只教会你怎么写检索表达式，却回避了一个尖锐的工程问题：**一个真实的 DSL 不可能是一座孤岛**——它必须调用 Java 生态的库（FastJSON、Jackson），必须使用 npm 生态的组件（echarts、antd-charts）。本章展示 TDSL 如何把"调用外部世界的能力"做成与语言本身一样严谨的一等公民。

在大多数编译器教材中，"外部函数接口"（FFI, Foreign Function Interface）是一个边角话题——C 可以 `#include <stdio.h>`，Linux 可以用 `dlopen`。但对 DSL 来说，FFI 决定了它的**生态位**：没有成熟的 FFI，一个 DSL 只能被用于它内置的领域，无法借用现有生态的千万级轮子。

`#include <stdio.h>` 的语义是"这个头文件声明了 printf 的签名"——编译器依赖它做类型检查。TDSL 对第三方库的接入设计成同样的模式：**编译期目录 + 编译期成员解析**。区别在于目录不是手写的 `.h` 文件，而是从 jar/npm 自动扫描 + 人工收窄来的。

## 11.1 问题：DSL 如何调用第三方库

一个 DSL 需要调用第三方库时，有三种路线：

### 路线 A：硬编码 glue code

在内置方法列表里硬编码第三方库的常用方法：

```ts
const EXTRA_MEMBERS = [
  { name: 'toJSONString', params: ['Object'], ret: 'String' },  // FastJSON
  { name: 'parseArray', params: ['String'], ret: 'List' },
  // ... 每加一个库就要改一次编译器源码
];
```

**优点**：实现最简单。
**缺点**：不可扩展。每接入一个新库就要改编译器、发版、升级。库的方法很多时（FastJSON 有数百个成员），glue code 会失控。

### 路线 B：运行时反射

不把成员表放在编译期，而是在运行期通过反射（Java）或 `Object.prototype` 查找（JS）动态调用：

```ts
// 伪代码：运行期动态调用
return recv[methodName](...args);
```

**优点**：免维护成员表。
**缺点**：**不可检查**。编译器无法在编译期知道 `toJSONString` 是否存在、参数是否正确。错误延迟到运行时才暴露——恰好违背了 FFI 设计的初衷。

### 路线 C：编译期目录模型（TDSL 的选择）

把第三方库的能力扫描成**目录**（catalog），编译期装载目录并做成员解析——与 `#include <stdio.h>` 的原理同构，但目录会自动生成：

```
bundle-jar 已知的 javadoc/signature 反射
  → 产物 JSON（coordinate + classes + methods）
  → dsl bundle-jar 命令生成 libs/*.json
  → typecheck/codegen 通过 createCatalog 合并装载
  → 编译期成员解析（存在性检查）+ 双端代码生成
```

**优点**：类型安全（编译期检查）+ 可扩展（扫一个新 jar 就多一个目录）。
**缺点**：需要实现扫描器 + 目录合并逻辑——比前两条路线复杂得多。

TDSL 选路线 C。本章剩余部分详细展开它的设计。

## 11.2 FFI 内核五域：语言自有 vs 第三方的边界

FFI 的设计首先要回答一个问题：**哪些类型属于"语言自己"，哪些属于"第三方"？**

TDSL 的答案是一刀切：**五个域（String/Decimal/Date/DateTime/List）是语言自有的，进核心目录（`FFI_CORE`）；一切带 Maven/npm 坐标的类一律外置到 libs/**

```ts
export const FFI_CORE: FfiClass[] = [
  { class: 'java.lang.String', alias: 'String', frontend: true, members: STRING_MEMBERS },
  { class: 'java.math.BigDecimal', alias: 'Decimal', members: DECIMAL_MEMBERS },
  { class: 'java.time.LocalDate', alias: 'Date', members: DATE_MEMBERS },
  { class: 'java.time.LocalDateTime', alias: 'DateTime', members: DATETIME_MEMBERS },
  { class: 'java.util.List', alias: 'List', frontend: true, members: LIST_MEMBERS },
];
```

**为什么是这五个域？** 因为它们是 TDSL 的类型系统不可分割的一部分：

- `String` 是 TDSL 的 primitive 类型，它的方法（`trim`、`toUpperCase`）是语言表达式的一部分
- `Decimal` 对应 `java.math.BigDecimal`，它的精度语义（第 2 章的 `db` TypeRef）构成 TDSL 的数值模型
- `Date`/`DateTime` 对应 TDSL 的日期类型，为 `Date.now()`、`plusDays` 等语义提供实现
- `List` 对应 TDSL 的列表类型，`for-of` 的迭代语义 = `List` 的元素访问

**判别的标准是什么？** 一个类型是否进内核，标准是"DependencyNode 是否对应到一个 Maven/npm 坐标"。String/List 分布在 JVM/npm 的标准库中（没有单一坐标），Decimal/Date 在 JDK 中——它们不带有用户声明的坐标，所以是"语言自有"。而 FastJSON 的坐标是 `com.alibaba:fastjson2`，Jackson 是 `com.fasterxml:jackson`——它们是明确的第三方，必须外置。

**为什么第三方不进 core？** 实施边界：如果 core 直接引用 FastJSON，那么 core 就"认识" FastJSON 了。下一次接 Jackson 又要改 core。core 不认识任何一个第三方 jar，是**不变式**，它让 core 的 FFI 核心长期稳定。第三方能力通过 `LoadedCatalog`（扫出来的产物）+ `dependency` 声明（用户的意图）在编译期动态装入。

### FfiMethod 的双端模板机制

每个目录成员是一个 `FfiMethod`：

```ts
export interface FfiMethod {
  name: string;
  static?: boolean;
  params: FfiParamType[];
  ret: FfiParamType;
  /** java 模板：{recv} {0} {1} 占位；缺省 = {recv}.{name}({args}) 直发 */
  java?: string;    // 有 java 才能后端调
  /** js 模板；缺省 = 无 js 侧（backend-only） */
  js?: string;      // 有 js 才能前端调
}
```

**规则的灵魂是那一句注释：有 java 才能后端调、有 js 才能前端调。** 一个成员如果只有 `java` 模板，前端调用它在 typecheck 就会报错；如果同时有 `java` 和 `js` 模板，两端各按各自的模板翻译。

看两个具体例子。

**String.contains** 在两端的实现不同（Java 是 `contains`，JS 是 `includes`）：

```ts
{ name: 'contains', params: ['String'], ret: 'Boolean', js: '{recv}.includes({0})' }
```

- **java 侧**：缺省直发 → `'abc'.contains('b')` 生成 `"abc".contains("b")`
- **js 侧**：显式模板 → `'abc'.contains('b')` 生成 `"abc".includes("b")`

**String.isEmpty** 在 Java 是方法调用，在 JS 是属性比较：

```ts
{ name: 'isEmpty', params: [], ret: 'Boolean', js: '{recv}.length === 0' }
```

`x.isEmpty` 在 JS 生成 `x.length === 0`，在 Java 生成 `x.isEmpty()`。

**Decimal 域全无 `js` 模板**：

```ts
const DECIMAL_MEMBERS: FfiMethod[] = [
  { name: 'add', params: ['Decimal'], ret: 'Decimal' },
  { name: 'subtract', params: ['Decimal'], ret: 'Decimal' },
  // ...
];
```

因为前端没有 BigDecimal——JS 用的是原生 number，金额算术直接 `a + b`。TDSL 的 `Decimal` 算术在前端走普通运算符（`genBinary` 直接翻译），Decimal 的实例方法（`add`/`multiply`）是 backend-only，前端调用会被 typecheck 拦截。

模板占位符有三类：`{recv}`（接收者）、`{n}`（第 n 个参数）、`{args}`（参数列表）。缺省模板是 `{recv}.{name}({args})` 直发——绝大多数成员用缺省，显式模板只留给平台差异处。

### List 的语义糖：count 别名

```ts
{ name: 'size', params: [], ret: 'Integer', java: '{recv}.size()', js: '{recv}.length' },
{ name: 'count', params: [], ret: 'Integer', java: '{recv}.size()', js: '{recv}.length' },  // TDSL .count 语义糖别名
```

`List.count` 是 TDSL 的**语义糖别名**——它映射到 size（java 端）和 length（js 端）。为了让 `for (const it of input.items)` 之前写 `input.items.count === 0` 更自然，TDSL 提供了 `count` 别名。这是语言层面向业务语义的又一个微调——`count` 比 `size` 更贴合中文业务直觉（"列表有几条"）。

## 11.3 第三方的外置与装载

第三方能力不写死在 core，而是通过两个运行时数据流动：

### LoadedCatalog：工程侧的扫描产物

```ts
interface LoadedCatalog {
  file?: string;        // 来源文件（诊断定位用）
  eco: 'java' | 'npm';
  coordinate: string;   // Maven 坐标 g:a:v 或 npm 包名@版本
  classes: FfiClass[];
}
```

一个 `LoadedCatalog` 对应一个 jar（或一个 npm 包）的扫描结果。`coordinate` 是它的身份——`com.alibaba:fastjson2:2.0.58`。

`FfiClass` 是目录中的"类条目"：

```ts
interface FfiClass {
  class: string;        // 全限定名（codegen-java 用）
  maven?: string;       // Maven 坐标 g:a:v —— 目录驱动的 pom 依赖注入
  alias: string;        // TDSL 语义核别名（原始类型名或 List）
  frontend?: boolean;   // 该类是否默认前端可用
  members: FfiMethod[];
}
```

**`alias` 是 TDSL 世界里的"称呼"**。`JSONObject` 的 class 是 `com.alibaba.fastjson2.JSONObject`，alias 是 `JSONObject`——TDSL 源码里写 `JSONObject`，codegen 生成 `com.alibaba.fastjson2.JSONObject`。alias 就是 TDSL 与目标语言之间的名字翻译表的关键字段。

### bundle-jar：扫描器

`dsl bundle-jar <jar> -o <工程>/libs/x.json [--classes 简名]` 是一个 CLI 命令。它的工作：

1. 打开 jar，找到 `pom.properties`，读取 Maven 坐标（`coordinate` 字段的来源）
2. 反射扫描 jar 的全部类（方法签名、静态标记、返回类型）
3. 把反射结果序列化为产物 JSON（`classes` 数组）
4. **人工收窄**：开发者编辑产物 JSON，从"反射全量"收敛到"精选类 + 修 alias + 补模板"

**为什么需要人工收窄？** 机器能扫全量，但没有语义判断力：

- 一个 jar 有几百个类，大多数（工具类、内部类）业务用不到——收窄让 TDSL 的可调用面干净
- alias 可能撞车（两个 jar 都有 `JSON`）——人工决定谁是裸名、谁要 `as ns` 限定
- 双端模板需要人工补（机器不知道 `contains` 在 JS 里是 `includes`）

这就是"机器扫全量、人定语义"的质量闸门设计。

## 11.4 createCatalog：目录合并

现在两个输入都齐了：内核五域（代码内置）+ 若干 `LoadedCatalog`（libs/ 扫出来的）。`createCatalog` 把它们合并成**有效目录**：

```ts
function createCatalog(loaded: LoadedCatalog[], deps: DependencyNode[]): EffectiveCatalog {
  // 1. 建立 coordinate → ns 的映射（as <ns> 的依赖声明）
  const nsOf = new Map<string, string>();
  for (const d of deps) {
    if (!d.ns) continue;
    for (const lc of loaded) {
      if (lc.eco === d.eco && depMatches(d, lc.coordinate)) nsOf.set(lc.coordinate, d.ns);
    }
  }
  // 2. 先入内核五域
  const all: FfiClass[] = FFI_CORE.map((c) => ({ ...c }));
  // 3. 再入产物类
  for (const lc of loaded) {
    const ns = nsOf.get(lc.coordinate);
    for (const c of lc.classes) push(c, lc.eco === 'java' ? lc.coordinate : undefined, ns);
  }
  // 4. 计算 collisions
  // ...
}
```

合并的语义决策：

**`as <ns>` 的产物进 ns 限定索引，不占裸 alias。** 如果声明 `dependency java "com.alibaba:fastjson2:2.0.58" as fj`，FastJSON 的类进 `nsIndex.fj`，不出现在裸 alias 查询里——调用必须写 `fj.JSON`。这是别名冲突的消解通道（D-dep-4）。

**产物类补 maven 坐标。** java eco 的产物类自动带 `maven: coordinate`（来自产物头）。`maven` 字段是目录驱动 pom 注入的数据源。

**alias 冲突只记录不丢弃。** 合并时如果两个 jar 都有 `JSON`，两个都进 `hits['JSON']`，同时记入 `collisions`——**诊断权在 typecheck，不在目录合并**。目录合并保持"宽容"（记录所有命中），拦截由 typecheck 的 D-dep-4 裁决。

### EffectiveCatalog 的查询接口

```ts
interface EffectiveCatalog {
  byAlias(alias: string): FfiClass | undefined;                    // 裸名：唯一命中才返回
  byQualified(ns: string, alias: string): FfiClass | undefined;    // 限定名：ns.Alias
  hitsOf(alias: string): FfiClass[];                               // 全部命中（歧义诊断用）
  member(c: FfiClass, name: string): FfiMethod | undefined;        // 成员查找
  collisions: CatalogCollision[];                                  // 撞车记录
}
```

**`byAlias` 的"唯一命中才返回"是最微妙的设计。** 如果 `JSON` 只在 fastjson 里出现，`byAlias('JSON')` 返回它；如果 fastjson 和 jackson 都 import 了 `JSON`，`byAlias('JSON')` 返回 `undefined`——不是"随便挑一个"，而是"我不确定，请你用限定名"。这与 M1 命名空间的"歧义即报错"是同一个哲学。

## 11.5 依赖声明的 AST 表示

用户如何在 TDSL 中声明依赖？`dependency java/npm` 声明：

```
dependency java "com.alibaba:fastjson2:2.0.58";                            → 无 import（产物全量兼容）
dependency java "g:a" as jackson;                                           → ns='jackson'（版本缺省）
dependency java "g:a:v" import { JSON, JSONObject };                        → imports 列表（java 显式裸名）
dependency java "g:a:v" as fj import { JSON as JacksonJSON };               → 改名（产物类 alias 覆盖）
dependency npm "antd@^5.21.0";                                              → 纯依赖（只进 package.json）
dependency npm "echarts-for-react" import ECharts;                          → importDefault（默认导出组件）
dependency npm "@ant-design/charts" import { Pie, Bar };                    → 具名导出组件
```

AST 表示（第 2 章的 `DependencyNode`）：

```ts
interface DependencyNode {
  kind: 'Dependency';
  eco: 'java' | 'npm';
  name: string;                    // Maven 坐标 "g:a" 或 npm 包名
  version?: string;
  ns?: string;                     // as ns 命名空间
  imports?: Array<{ name: string; alias?: string }>;   // import 列表（A as B 改名）
  importDefault?: string;          // 默认导入（npm import X）
}
```

名词再梳理一遍——它们是 FFI 设计的三个层次：

| 概念 | 含义 | 谁产生 |
|------|------|--------|
| **声明**（dependency） | 用户意图：我想用这个库 | 人/LLM 写在 TDSL |
| **产物**（LoadedCatalog） | 库的能力清单：这个 jar 有哪些类/成员 | bundle-jar 扫描 + 人工收窄 |
| **目录**（EffectiveCatalog） | 可用的能力索引：声明 ∩ 产物 | createCatalog 合并 |

**一个关键不变式："声明才是意图，目录只是能力清单"。** 一个 jar 即使被扫描进 libs/，只要用户不写 `dependency java`，它就不进 pom、不进目录的调用面。反过来，写了声明但没有对应产物，会得到 D-dep-2 warning（提醒你去 bundle-jar）。声明与产物必须"对上"，缺一不可。

### import 段：java 与 npm 的统一形态（dev/34）

`import` 段自 dev/34 起统一为与 JS import 语义字面一致的形态：

- `import X`（单名）= 默认导入 → `import X from 'pkg'`
- `import { A, B as C }`（花括号）= 具名导入，`as` 改名 → `import { A, B as C } from 'pkg'`
- 无 import 的声明只进 package.json（npm）或全量兼容（java）

**java 端**：import 列表声明哪些产物类**以裸名可用**。两个 jar 都 import 了 `JSON` 才撞车（D-dep-4）；撞了就给其中一个加 `as ns`，调用写 `ns.JSON`。

**npm 端**：import 声明页面可用的组件名。`import ECharts` → 页面直接 `<ECharts />`，生成 `import ECharts from 'echarts-for-react'`。未显式 import 的声明只进 package.json。

## 11.6 dependency java 的 Java 端消费

### pom 注入：声明驱动

第 9 章的 `scaffoldFiles` 展示了 pom 生成：

```ts
const declaredDeps = app.dependencies
  .filter((d) => d.eco === 'java')
  .map((d) => {
    const version = d.version ?? libs.find((lc) => lc.eco === 'java' && depMatches(d, lc.coordinate))?.coordinate.split(':')[2];
    const [g, a] = d.name.split(':');
    return `<dependency>
  <groupId>${g}</groupId>
  <artifactId>${a}</artifactId>
  <version>${version}</version>
</dependency>`;
  });
```

**版本缺省时从产物坐标补**——`dependency java "g:a"`（无版本）时，codegen 在 libs 里找匹配 coordinate，取 `coordinate.split(':')[2]` 当版本。所以用户能写最简声明，版本由扫描产物决定。

### import 收集：从用到处反查

一个 Java 文件要 import 第三方类，codegen 需要知道**哪些 FFI 类被这个函数用到了**。这通过 `collectFfiExprsOfLogic` 扫描实现：遍历逻辑体的表达式树，找出所有 FFI 目录调用，收集它们对应的 class 全限定名，生成 import 语句。

```ts
// 逻辑体里出现 JSON.toJSONString(...)
// → collectFfiExprsOfLogic 找到 FFI 调用
// → 对应的 FfiClass.class = 'com.alibaba.fastjson2.JSON'
// → 生成 import com.alibaba.fastjson2.JSON;
```

这个"按用到处反查 import"与 `javaType` 的全限定名策略形成互补：**第三方类用 import（因为类名在源码中会重复出现，简名可读性重要），标准 Java 类型用全限定名（数量少，import 管理不值当）**。

### 成员翻译

成员调用 `JSON.toJSONString(o)` 在表达式翻译层：

1. `JSON` 是 Ident，通过 `cat.byAlias('JSON')` 找到 FfiClass
2. `toJSONString` 通过 `cat.member(cls, 'toJSONString')` 找到 FfiMethod
3. 用模板翻译：缺省 → `JSON.toJSONString(o)`；有自定义 → 按模板展开

typecheck 的角色是**前置拦截**：如果 `toJSONString` 不在 FastJSON 的目录成员里，report error（附补录口径 `dsl bundle-jar`）。这个"编译期成员解析"正是路线 C 相对路线 B 的胜负手。

## 11.7 dependency npm 的 React 端消费

React 端对 npm 依赖的消费分三处：

### package.json 合并

```json
{
  "dependencies": {
    "antd": "^5.21.0",           // 页面骨架默认项
    "dayjs": "^1.11.0",
    "react": "^18.2.0",
    "react-router-dom": "^6.22.0",
    "echarts-for-react": "^3.0.2"  // ← dependency npm 声明
  }
}
```

**`dependency npm` 是唯一的三方包名来源**——这是 dev/33 决策：删除了 `component` 注册层，npm 组件通过声明直用。

### import 语句生成

页面用到 `<ECharts />` 时，生成的文件顶部自动带 import：

- `dependency npm "echarts-for-react" import ECharts;` → `import ECharts from 'echarts-for-react'`
- `dependency npm "@ant-design/charts" import { Pie, Bar };` → `import { Pie, Bar } from '@ant-design/charts'`（同包聚合）
- `dependency npm "@scope/ui" import { A, B as C };` → `import { A, B as C } from '@scope/ui'`

### 组件发现与验证

`<Pie data={...} angleField="value" />` 是页面元素。typecheck 判断 `Pie` 是否可用的逻辑：**在 dependency npm 声明的 import 列表（含默认导出）里找**。找到了 → 合法；没找到 → 报错并提示补 `dependency npm`。

这打通了"页面 → 组件 → 包里哪个导出 → 工程 package.json"的完整链路——组件从声明中来，声明生成 import，import 对应包里真实存在的导出。三方组件在 TDSL 中与 `antd` 内置组件一样，是一等公民。

## 11.8 诊断闭环：四个 D-dep

依赖声明的质量由四个诊断兜底（第 6 章已列过，这里展开设计动机）：

| 诊断 | 级别 | 说明 |
|------|------|------|
| **D-dep-1 未声明依赖** | error | 用到带坐标的产物类，但坐标不在 `app.dependencies`——"用了但没声明" |
| **D-dep-2 声明无产物** | warning | 声明了但 libs/ 无匹配 coordinate——"想要但没扫出来" |
| **D-dep-3 版本漂移** | warning | 声明版本 ≠ 产物 coordinate 版本——"说好的版本和实际的版本不一致" |
| **D-dep-4 撞别名** | error | 同名类跨 jar / 与内核五域冲突——"两个 `JSON`，你指的是哪个" |

这四个诊断的设计共同指向一个理念：**声明与产物必须严格对上，含糊即报错**。

D-dep-1 的"用了"来自 FFI 检查过程中的 `usedCoords` 收集——typecheck 在解析每个 FFI 调用时记录用到的坐标，最后与声明比对。**用即追踪，声明与使用闭环**。

D-dep-4 是 `collisions` 触发的：`createCatalog` 发现的撞车（`hits[alias].length > 1`）被记录，typecheck 读取 `collisions` 生成诊断，附带两个 jar 的坐标和消解口径（加 `as ns` 或改产物 alias）。

## 11.9 设计权衡总结

把 Java/npm 做成一等公民，TDSL 付出了一些复杂度，换来了关键的工程收益。

### 换来的收益

1. **类型安全可移植**：第三方库的方法在编译期检查，错误不会留到运行期。这与手写 C 程序的 `man page` 教条（"先查签名再调用"）同源——只是自动化了。

2. **双端一致**：一个 DSL 同时生成 Java 和 React，第三方库两端各取所需——`contains` 在后端生成 `contains`，在前端生成 `includes`。如果没有目录机制，这种平台差异只能靠生成器硬编码，无法扩展。

3. **生态可生长**：接入一个新 jar 不需要改编译器。扫一下、收窄一下、声明一下就可用。目录模型把"语言"和"库"解耦——库的清单是数据，不是代码。

### 付出的代价

1. **双数据源同步**：声明（TDSL）+ 产物（libs/*.json）必须对上，否则 D-dep-2/D-dep-3 报警。这需要开发者遵守"扫了才声明、声明就有产物"的纪律。

2. **扫描器有天花板**：jar 反射扫描拿不到类型参数（泛型）。FastJSON 的 `parseArray(String, Type)` 这类泛型方法在产物里会退化为 `Object`。人工收窄环节负责部分补偿。

3. **别名撞车的治理成本**：D-dep-4 让用户在"加 `as ns`"和"改产物 alias"之间做选择。这是一个真实的成本，但它是**必要**的——含糊的引用必须在编译期暴露。

### 与 stdio.h 的理论对照

回到本章开头：`#include <stdio.h>` 给 C 编译器提供了 printf 的签名。TDSL 的 `dependency java "g:a:v" import { JSON }` 给 TDSL 编译器提供了 `JSON.toJSONString` 的签名。两者形态不同，但**编译期目录**的理论是一样的：

```
头文件 / 产物 JSON —— 声明外部世界的接口契约（签名）
include / dependency —— 把契约引入当前编译单元（意图）
链接器 / createCatalog —— 把引用解析到具体实现（绑定）
```

区别是：C 的头文件是人手写的、静态的；TDSL 的产物是扫描 + 收窄生成的、可增量扩展的。这正是一个"语言生态位"的体现——TDSL 作为低代码 DSL，它对外开放接口的方式必须足够"数据驱动"，否则第三方集成会拖垮整个语言的发展节奏。
