# 第 9 章 Java 代码生成：从 AST 到 Spring Boot

`generateJava(app, { libs })` 把一棵 TDSL 的 AppNode 翻译成一个完整的 Spring Boot 工程。这一章是"从理论到工程"最完整的一章——它展示了类型映射、语句翻译、查询编译、依赖注入如何在一个真实后端工程中协同工作。

## 9.1 生成物全景

一个 TDSL 应用（如 `examples/todo-app/todo.tdsl`）生成的后端工程文件清单：

| 生成物 | 来源 | 说明 |
|--------|------|------|
| `pom.xml` | 脚手架 + dependency 声明 | Maven 依赖（声明驱动） |
| `OrderApplication.java` / `application.yml` | 脚手架 | 启动类 + H2/JPA 配置 |
| `entity/Order.java` | Entity 节点 | JPA 实体 |
| `enums/OrderStatus.java` | Enum 节点 | Java 枚举（恒带 label 字段） |
| `repository/OrderRepository.java` | 查询形态 | JpaRepository + 派生存取方法 |
| `structure/OrderInput.java` | Structure 节点 | POJO + getter/setter |
| `service/OrderService.java` | Logic 节点 | 业务方法（@Transactional） |
| `controller/OrderApiController.java` | Interface 节点 | REST Controller |
| `service/api/UserService.java` | Service 节点 | dubbo 接口 / Feign 客户端 |
| `tdsl/TdslError.java` 等 | 脚手架 | 统一异常响应体 |

装配顺序（在 `generateJava` 函数内）：

```ts
function generateJava(app: AppNode, opts: GenerateJavaOptions = {}): GeneratedFile[] {
  const files: GeneratedFile[] = [];
  const pkg = pkgOf(app);                          // com.<appName>
  const cat = createCatalog(opts.libs ?? [], app.dependencies);
  const entities = app.datasources.flatMap((ds) => ds.entities);
  const querySpecs = collectQuerySpecs(app);       // ★ 查询编译（§9.4）

  files.push(...scaffoldFiles(app, opts.libs ?? []));
  for (const en of app.enums) files.push(enumFile(pkg, en));
  for (const ent of entities) {
    files.push(entityFile(pkg, ent, app.enums.length > 0));
    files.push(repositoryFile(pkg, ent, querySpecs.get(ent.name) ?? [], app.enums.length > 0));
  }
  for (const s of app.structures) files.push(structureFile(app, s));
  for (const svc of app.services) files.push(serviceApiFile(pkg, svc));
  for (const logic of app.logics) files.push(serviceFile(app, logic, cat));
  for (const itf of app.interfaces) files.push(controllerFile(app, itf));
  files.push(tdslErrorFile(pkg), tdslAdviceFile(pkg));
  return files;
}
```

## 9.2 类型映射：语义保持的基石

类型映射是每个生成阶段的公共基础。第 8 章的 `javaType(tr)` 函数定义了一个 TypeRef 到 Java 全限定名的映射。这个映射不是随意的——每个选择都有语义理由：

| TDSL | Java | 理由 |
|------|------|------|
| `Integer` | `Long` | 业务整数用 64 位避免溢出（Java `int` 是 32 位） |
| `Decimal` | `java.math.BigDecimal` | 精确十进制运算（金额不能有浮点误差） |
| `String` | `String` | 直接对应 |
| `Boolean` | `Boolean` | 直接对应 |
| `Date` | `java.time.LocalDate` | 仅日期，无时区 |
| `Time` | `java.time.LocalTime` | 仅时间，无时区 |
| `DateTime` | `java.time.ZonedDateTime` | 跨时区时刻（携带时区信息） |

一个值得注意的设计：**`javaType` 输出全限定名而非简名**。`BigDecimal` 生成 `java.math.BigDecimal`，`List` 生成 `java.util.List`。这省去了 import 管理——生成器不需要知道哪些类型被用到了、哪个没被用到。代价是生成代码的省略号（`java.util.List<Order>`）比简名长，但对生成代码完全无关紧要。

## 9.3 逐节点生成

### Entity → JPA 实体

```java
package com.todo.entity;

import javax.persistence.*;

@Entity
@Table(name = "order")
public class Order {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  private String customer;

  private java.math.BigDecimal total;

  public Order() {
  }

  public Long getId() { return id; }
  public void setId(Long id) { this.id = id; }
  // ... 其余 getter/setter
}
```

关键映射：

- `@pk` → `@Id` + `@GeneratedValue(strategy = GenerationType.IDENTITY)`（自增主键）
- `@nullable` → `@Column(nullable = true)`（可空列）
- 表名 → 实体名小写；**SQL 保留字处理**：如果实体名撞了 SQL 保留字（如 `order`、`group`、`user`），表名加双引号包裹：

```ts
function tableNameOf(ent: EntityNode): string {
  const base = ent.table ?? ent.name.toLowerCase();
  return SQL_RESERVED.has(base) ? `\\"${base}\\"` : base;   // quoted identifier
}
```

注意上面这段代码**是 codegen 的源码而非产物**：模板里的 `\\"` 在 TS 字符串求值后变成字符序列 `\"`，最终拼进 `@Table(name = "...")` 生成 `@Table(name = "\"order\"")`——这是合法的 Java 转义，运行时 H2 收到带引号标识符 `"order"`。如果你在别处读到类似的转义，迷失了层级，回到这个"源代码里看到的是字符串字面量，而不是生成后的目标代码"的原则来理清。

`order` 是 SQL 保留字，所以 `entity Order` 生成 `@Table(name = "\"order\"")`。这是真实工程踩坑的产物——不处理会直接 `mvn compile` 成功但运行时 Hibernate 报错。

### Enum → Java 枚举

```java
package com.todo.enums;

public enum OrderStatus {
  DRAFT("DRAFT"),
  SUBMITTED("SUBMITTED");

  private final String label;

  OrderStatus(String label) {
    this.label = label;
  }

  public String getLabel() {
    return label;
  }
}
```

**为什么枚举恒带 `label` 字段？** 因为 TDSL 的枚举用于前端显示——`DRAFT('暂存')` 中的中文标签需要保留到生成代码中。即使没有显式标签（`DRAFT`），也退化为枚举名，保证接口一致性（前端可以统一通过 `getLabel()` 取显示文本）。

### Structure → POJO

Structure 生成标准的 POJO：私有字段 + getter/setter + 空构造器。一个细节是 **import 自动收集**：

```ts
const referencesEntity = s.properties.some((p) => {
  const t = p.type;
  if (t.kind === 'reference') return entityNames.includes(t.path.split('.').pop() ?? '');
  if (t.kind === 'generic') {
    return t.args.some((a) => a.kind === 'reference' && entityNames.includes(a.path.split('.').pop() ?? ''));
  }
  return false;
});
```

如果 Structure 引用实体类型（`OrderDetail { order: Order; items: List<OrderItem> }`），生成 `import com.todo.entity.*;`。这个 import 不是 `javaType` 的全限定默认路径能解决的——`Order` 是项目内类，需要显式 import。

### Logic → Service：最复杂的生成

`serviceFile` 函数生成业务逻辑的 Service 类。它需要做几件事：

**依赖收集**。遍历逻辑体，收集需要的 Repository、外部 Service、以及被调用的其他 Logic：

```ts
const usedEntities = collectUsedEntities(app, logic);    // ForEach 容器 / X.get / entity.save / entity.delete
const usedServices = collectUsedServices(app, logic);    // userService.getUser(...)
const usedLogics = collectUsedLogics(app, logic);        // genContractNo() → genContractNoService
```

这些收集驱动**构造器注入**（Repository 用构造器注入，Service/Logic 用 @Autowired 字段注入）：

```java
@Service
public class CreateOrderService {
  private final OrderRepository orderRepository;
  private final OrderItemRepository orderItemRepository;

  @Autowired
  private UserService userService;

  public CreateOrderService(OrderRepository orderRepository, OrderItemRepository orderItemRepository) {
    this.orderRepository = orderRepository;
    this.orderItemRepository = orderItemRepository;
  }

  @Transactional
  public Order createOrder(OrderInput input) {
    // ... 翻译后的语句
  }
}
```

**@Transactional 自动推断**。通过 `hasWriteOps(logic)` 扫描逻辑体——只要包含 `.save()` 或 `.delete()` 调用，方法自动加 `@Transactional`：

```ts
function hasWriteOps(logic: LogicNode): boolean {
  // 递归扫描所有表达式中是否有 callee.prop === 'save' | 'delete'
}
```

这是"语义驱动代码生成"的典型例子——编译器帮你做决定，而不是要求用户显式标注。

**变量类型追踪**。`VarScope` 在整个语句翻译过程中维护变量 → Java 类型。参数最先登记，然后随着 `VarDecl` 语句逐个登记新变量。

## 9.4 QuerySpec 查询编译（核心机制）

这是 codegen-java 最精巧的部分。它的任务是：**把散布在函数体中的查询表达式（`Order.where(...)...`）转换为一组 Repository 方法**。

### 收集：collectQuerySpecs

```
扫描所有函数体的表达式
  → 识别查询链（Order.where(...).orderBy(...).page(...)）
  → 每个查询链 → 一个 QuerySpec 对象
  → 按实体归集
  → 去重（sameSpec 或方法名相撞）
```

一个 `QuerySpec` 描述了实体的一种查询形态：

```ts
interface QuerySpec {
  entity: string;                          // 目标实体
  conditions: Array<{                      // where 条件（展平为 AND/OR 序列）
    field: string;
    op: WhereOp;                            // '=' | '>=' | '<=' | '>' | '<' | 'like' | 'in'
    value: Expr;
    valueKind: 'param' | 'literal' | 'other';
    connector: 'and' | 'or';
  }>;
  orderBy: Array<{ field: string; dir: 'asc' | 'desc' }>;
  pageable: boolean;                        // 是否有 .page(...)
  limit?: number;                           // 是否有 .limit(n)
  aggregate?: { fn: 'sum'|'avg'|'max'|'min'|'count'; field?: string };
  groupBy?: string[];
}
```

### 去重机制

两个 QuerySpec 如果完全等价（sameSpec），只生成一个 Repository 方法。去重条件是逐字段比较：

```ts
function sameSpec(a: QuerySpec, b: QuerySpec): boolean {
  // 实体名、分页形态、limit、聚合函数/字段、groupBy、条件序列、排序序列
  // 全部一致 → true
}
```

但还有第二层去重：即使 `sameSpec` 不精确相等，如果派生方法名相同（比如两个条件集不同但生成的方法名撞了），Java 会报"重复方法"。codegen 的处理是检查派生方法名是否相撞，相撞则合并：

```ts
const collides = (s: QuerySpec) =>
  sameSpec(s, spec) ||
  (s.pageable === spec.pageable &&
    s.limit === spec.limit &&
    !s.aggregate && !spec.aggregate &&
    derivedMethodName(ent, s) === derivedMethodName(ent, spec));
```

这是真实工程踩坑的产物（jxc 对拍发现 javac 报重复定义）。

### 派生方法名生成

Spring Data JPA 的查询方法名是**派生方法**——方法名本身包含查询语义：

```ts
function derivedMethodName(ent: EntityNode, spec: QuerySpec): string {
  let name = spec.limit !== undefined ? `findTop${spec.limit}By` : 'findBy';
  spec.conditions.forEach((c, i) => {
    if (i > 0) name += c.connector === 'or' ? 'Or' : 'And';
    name += cap(c.field) + opSuffix(c.op);
  });
  for (const o of spec.orderBy) {
    name += `OrderBy${cap(o.field)}${o.dir === 'desc' ? 'Desc' : 'Asc'}`;
  }
  return name;
}
```

`opSuffix` 把条件运算符映射为方法名后缀：

```ts
function opSuffix(op: WhereOp): string {
  switch (op) {
    case '=': return '';
    case '>=': return 'GreaterThanEqual';
    case '<=': return 'LessThanEqual';
    case '>': return 'GreaterThan';
    case '<': return 'LessThan';
    case 'like': return 'Like';
    case 'in': return 'In';
  }
}
```

于是 `Order.where(customer like '%x%', total >= 100).orderBy(total desc)` 生成：

```java
List<Order> findByCustomerLikeAndTotalGreaterThanEqualOrderByTotalDesc(
  String customer, Long total);
```

### null 宽松查询：一种 JPQL 生成模式

普通派生方法（`findBy...`）有一个坑：如果查询条件参数是 null（比如前端没传 `customer`），Spring Data 默认会生成 `where customer = null`——永远为假，返回空集。这对列表页是灾难（用户没填筛选条件就看不到任何数据）。

TDSL 的解决是：**对无 in/or/limit 的 where 查询使用显式 JPQL，把条件包装成 `(?n IS NULL OR 谓词)`**：

```ts
const preds = spec.conditions
  .map((c, i) => {
    const col = `${alias}.${c.field}`;
    const inner =
      c.op === 'like'
        ? `${col} LIKE CONCAT('%', ?${i + 1}, '%')`
        : `${col} ${c.op} ?${i + 1}`;
    return `(?${i + 1} IS NULL OR ${inner})`;
  })
  .join(' AND ');
```

生成：

```java
@Query("SELECT o FROM Order o WHERE (?1 IS NULL OR o.customer LIKE CONCAT('%', ?1, '%')) AND (?2 IS NULL OR o.total >= ?2) ORDER BY o.total DESC")
List<Order> findByCustomerLikeAndTotalGreaterThanEqualOrderByTotalDesc(String customer, Long total);
```

参数为 null 时，`?n IS NULL` 为真，该条件不生效——实现了"可选筛选参数"的语义。

### limit / page / aggregate / groupBy

不同的查询形态生成不同的 Repository 方法：

- `.limit(n)` → `findTop{n}By...`（Spring Data 派生语法）
- `.page(n, size)` → 方法返回 `Page<Entity>`，尾部加 `Pageable pageable` 参数
- `.aggregate(sum(total))` → `@Query("SELECT SUM(o.total) FROM Order o")` + `BigDecimal sumTotal()`
- `.aggregate(sum(total)).groupBy(customer)` → `@Query("SELECT o.customer, SUM(o.total) FROM Order o GROUP BY o.customer")` + `List<Object[]> sumTotalByCustomer()`

## 9.5 语句翻译：genStatement / genExpr

函数体是**逐语句翻译**的，不是模板填充。`genStatement` 处理每种 Statement，`genExpr` 处理每种 Expr，两者通过参数共享 `VarScope` 和实体表。

### VarDecl（变量声明）

```ts
case 'VarDecl': {
  const initStr = st.init ? genExpr(app, st.init, entities, vars) : 'null';
  const existing = lookupVar(vars, st.name);
  if (existing) {
    return [`    ${st.name} = ${initStr};`];   // Java 复用语义：同名变量 → 赋值
  }
  // 推断类型
  const inferredType = inferVarDeclType(app, st, entities);
  ...
  vars.vars.set(st.name, typeStr);
  return [`    ${typeStr} ${st.name} = ${initStr};`];
}
```

类型推断的优先级：显式类型 > NewList 元素类型 > 推断（`X.get(...)` → 实体类型、查询链 → `List<Entity>`）> `var`（Java 10+ 局部变量推断兜底）。

一个细节：整数字面量累加器自动生成 `long`：

```ts
if (typeStr === 'var' && st.init?.kind === 'Numeric' && Number.isInteger(st.init.value)) {
  return [`    long ${st.name} = ${st.init.value}L;`];
}
```

因为实体 Integer 字段 getter 返回 `Long`，如果累加器是 `int`，`int + Long` 会精度损失报错。

### Assign（赋值）

```ts
case 'Assign': {
  const t = st.target;
  // target 是 实体/结构变量.prop → setter
  if (t.kind === 'Member' && t.obj.kind === 'Ident') {
    const varType = lookupVar(vars, t.obj.name)?.javaType;
    if (varType && !isValueType(varType)) {
      // Decimal 字段赋整数字面量 → BigDecimal.valueOf(...) 自动包装
      let v = value;
      const fieldType = memberFieldType(...);
      if (fieldType === 'java.math.BigDecimal' && exprJavaType(...) !== 'BigDecimal') {
        v = `java.math.BigDecimal.valueOf(${v})`;
      }
      return [`    ${t.obj.name}.set${cap(t.prop)}(${v});`];
    }
  }
  return [`    ${genExpr(app, st.target, entities, vars)} = ${value};`];
}
```

### 表达式的 FFI 翻译

第 11 章会详细展开 FFI。这里先给出概要：表达式中的 FFI 成员（`JSON.toJSONString(o)`、`xs.add(x)`）通过 FFI 目录查找对应的 `FfiMethod`，按模板翻译：

```ts
function genFfiCall(recv: string, method: FfiMethod, args: string[]): string {
  if (method.java) {
    return method.java(recv, args);   // 模板函数（缺省 {recv}.{name}({args})）
  }
  return `${recv}.${method.name}(${args.join(', ')})`;  // 直发
}
```

## 9.6 Interface → Controller

Controller 生成把 Interface 的每个 Endpoint 映射为一个 Spring MVC 方法：

```java
@RestController
@CrossOrigin(origins = "*")
public class OrderApiController {
  private final ListOrdersService listOrdersService;
  private final CreateOrderService createOrderService;
  // ...

  public OrderApiController(ListOrdersService listOrdersService, ...) { ... }

  @GetMapping("/api/orders")
  public java.util.List<Order> listOrders() {
    return listOrdersService.listOrders();
  }

  @PostMapping("/api/orders")
  public Order createOrder(@RequestBody OrderInput input) {
    return createOrderService.createOrder(input);
  }

  @GetMapping("/api/orders/{id}")
  public OrderDetail getOrderDetail(@PathVariable Long id) {
    return getOrderDetailService.getOrderDetail(id);
  }
}
```

参数映射的规则（`genEndpointMethod`）：

- **路径参数**：path 中的 `{id}` → `@PathVariable Long id`（先检查 `ep.path.includes('{id}')`）
- **GET 标量参数**：→ `@RequestParam(required=false, defaultValue=...)`（前端通常只传部分参数）
- **POST/PUT 结构参数**：→ `@RequestBody OrderInput input`

## 9.7 依赖驱动的 pom 注入

`dependency java` 声明直接驱动 pom 生成：

```ts
const declaredDeps = app.dependencies
  .filter((d) => d.eco === 'java')
  .map((d) => {
    const version = d.version ?? libs.find(...)?.coordinate.split(':')[2];
    const [g, a] = d.name.split(':');
    return `<dependency>
  <groupId>${g}</groupId>
  <artifactId>${a}</artifactId>
  <version>${version}</version>
</dependency>`;
  });
```

如果版本缺省，从 libs 扫描产物（`coordinate: 'g:a:v'`）中补齐——**声明是意图，目录是能力清单，版本从能力清单补**。

这个"声明驱动"理念贯穿整个 FFI 设计（第 11 章深入展开）。

## 9.8 小结：非模板生成的底气

codegen-java 的核心是**逐语句翻译**（`genStatement`/`genExpr`）而非固定模板。这意味着：只要 TDSL 能表达的逻辑，Java 就能生成——生成器只受 AST 类型的制约，不受预先列好的模板约束。

这个灵活性使 TDSL 不需要为每种业务形态定制模板。函数体的任意控制流（if/for/var/return）都能被翻译。查询语言则被 QuerySpec 机制"编译"成 Repository 方法——这是"什么时候用模板、什么时候逐句翻译"的分界：控制流逐句翻译，查询做归集编译。
