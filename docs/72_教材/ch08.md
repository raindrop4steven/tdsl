# 第 8 章 代码生成原理

代码生成是把语义树翻译成目标语言的过程。本章先讲通用原理，再讲 TDSL 的两个关键设计：纯函数生成器接口和穷尽 switch 的安全网。

## 8.1 代码生成的理论框架

传统编译器中，代码生成通常指从**中间表示（IR）**到**汇编代码**的翻译：寄存器分配、指令选择、指令调度。但 TDSL 的代码生成是**从 IR 到另一种高级语言**的高层翻译——更接近 transpiler（如 TypeScript→JavaScript）而非传统编译器。

这个区别的关键：TDSL 生成的 Java 和 React 不是"机器码"，而是**可读的、可直接编译的高层源码**。生成的目标码不需要优化——它只需要正确、语义忠实。

传统编译器的代码生成质量指标（指令数、寄存器压力、缓存友好性）不适用于 TDSL。TDSL 的指标是：

1. **可编译性**：生成的项目必须能通过 `mvn compile` 和 `vite build`（这是端到端测试的唯一硬性标准）
2. **语义正确性**：生成的代码必须与 TDSL 语义一致（通过演示应用的实际运行验证）
3. **可读性**：生成代码应该是人能读懂的高质量代码（便于排查）

## 8.2 TDSL 的"轻 IR"路线

传统编译器在源码中途引入一个**独立于源语言和目标语言**的中间表示：

```
源语言(source) → IR1 → IR2 → ... → 目标语言(target)
```

优化发生在 IR 层面——因为 IR 通常比源语言和目标语言都更简单、更抽象。

TDSL 的决策是**Typed AST 直接当 IR**。这意味着：

- 没有单独的 IR 层——AST 既是语义树，也是 codegen 的输入
- 没有优化阶段——目标代码直接从 AST 生成
- codegen 的输入和源语言直接对应——每个 TDSL 构造直接映射到目标语言构造

这个决策的合理性在于 TDSL 的目标：**不是生成高性能代码，而是生成语义正确的可运行代码**。TDSL 的查询语言（`where`/`orderBy`）是一种"有限形态"——它的语义完全由 AST 结构决定，不需要中间表示层面的推理。

代价是：codegen 必须处理两种目标语言的差异。`===` 在 Java 中要翻译成 `equals`，在 JS 中是 `===`。`Decimal` 在 Java 中是 `BigDecimal`，在 JS 中是原生 `number`。这些平台差异被封装在编译器的翻译层——这正是一本编译原理教材展示"语义保持翻译"的最佳案例。

## 8.3 纯函数生成器接口

TDSL 的 codegen 是纯函数：

```ts
interface GeneratedFile {
  path: string;      // 目标文件路径（相对工程根）
  content: string;   // 目标文件内容
}

function generateJava(app: AppNode, opts?: { libs?: LoadedCatalog[] }): GeneratedFile[]
function generateReact(app: AppNode): GeneratedFile[]
```

两个设计决策贯穿着这两个函数：

### 确定性

同一棵 AST，无论调用多少次，无论在哪台机器上，都产生**完全相同的输出**。这个保证来自纯函数约束——生成器不依赖任何外部状态（时间、随机数、文件系统、环境变量）。

确定性的实际价值：

1. **可快照测试**：单测可以把生成结果与预期字符串逐字比较。
2. **可 diff 回归**：多文件工程的 AST 合并结果可以与单文件对拍，AST 级一致才通过——如果没有确定性，对拍无法进行。
3. **可缓存**：`generateJava(app)` 的结果可以缓存，输入不变则输出不变。

### 不碰磁盘

codegen 返回 `GeneratedFile[]`，不直接写文件。写盘只发生在调用方（`scripts/slice.ts` 的脚本、CLI 的 IO 层）。

这个约束让 codegen 可以在任何环境运行（Node 脚本、浏览器 playground、测试环境），也让"预览生成结果"成为可能——把 `GeneratedFile[]` 展示给用户，用户确认后再写盘。

## 8.4 穷尽 switch + never 安全网

第 2 章介绍了 `never` 类型在 AST 设计中的作用。在 codegen 中，它是**强制完整性**的工具。

codegen-java 的某个生成函数：

```ts
function genExpr(app: AppNode, e: Expr, entities: Map<string, EntityNode>, vars: VarScope): string {
  switch (e.kind) {
    case 'Ident': return e.name;
    case 'Member': return genMember(app, e, entities, vars);
    case 'Index': return genIndex(e);
    case 'Call': return genCall(app, e, entities, vars);
    case 'New': return genNew(e);
    case 'NewList': return `List.of(${e.items.map(...).join(', ')})`;  // 或 new ArrayList
    case 'Literal': return genLiteral(e.literal);
    case 'Binary': return genBinary(app, e, entities, vars);
    case 'Group': return `(${genExpr(app, e.expr, entities, vars)})`;
  }
  const _never: never = e;  // TS 编译器强制穷尽
  throw new Error(`未处理的表达式类型: ${JSON.stringify(e)}`);
}
```

如果 `Expr` 联合类型新增了一种形态（比如 `Unary`），`genExpr` 的 `switch` 不会匹配到新形态——TypeScript 编译器会报错：`Type 'Unary' is not assignable to type 'never'`。这迫使开发者处理新形态，否则编译失败。

**这个模式的价值是"演进安全"**。TDSL 是一个活的语言，会不断新增语法。每一处 `switch` 都保证：新增语法后，所有消费端必须在编译期同步更新。如果有一处没更新，编译器会告诉你——而不是等到运行时产出错误代码。

## 8.5 表达式翻译的通用模式

表达式翻译的模式是"**结构递归 + 平台差异表**"：

```ts
function genBinary(app: AppNode, e: BinaryExpr, entities: Map<string, EntityNode>, vars: VarScope): string {
  const opMap: Record<string, string> = {
    '===': 'equals',      // Java 特化
    '!==': '!equals',
    '+': '+',
    '-': '-',
    '*': '*',
    '/': '/',
    '&&': '&&',
    '||': '||',
    // ...
  };

  if (e.operator === '===' || e.operator === '!==') {
    return `${genExpr(app, e.left, entities, vars)}.${opMap[e.operator]}(${genExpr(app, e.right, entities, vars)})`;
  }
  return `${genExpr(app, e.left, entities, vars)} ${opMap[e.operator]} ${genExpr(app, e.right, entities, vars)}`;
}
```

关键洞察：`===` 在 TDSL 语义中是"值相等"（不管引用相等），而在 Java 中对 String 和对象需要用 `equals`。所以 `===` 被翻译为 `a.equals(b)`，`!==` 被翻译为 `!a.equals(b)`。这是语义保持翻译的典型例子——源语言的"相等"概念和目标语言中被映射为不同的运算符。

翻译层的另一个职责是**类型触发的代码转换**。`order.total = 5`（Decimal 字段赋整数）在 Java 中需要 `order.setTotal(BigDecimal.valueOf(5))`。codegen 需要知道 `total` 是 Decimal 字段——这通过 `memberFieldType` 和 `exprJavaType` 两个辅助函数判断，然后自动包装：

```ts
// Assign 语句中，target 是实体/结构变量.prop，且 prop 是 Decimal 字段
if (fieldType === 'java.math.BigDecimal' && exprJavaType(...) !== 'java.math.BigDecimal') {
  value = `java.math.BigDecimal.valueOf(${value})`;
}
```

## 8.6 类型映射的通用模式

类型映射是 codegen 的"基石"——每个 TypeRef 必须映射为目标语言的一个类型。codegen-java 的 `type-map.ts` 定义了完整的映射：

```ts
export function javaType(tr: TypeRef): string {
  switch (tr.kind) {
    case 'primitive':
      switch (tr.builtin) {
        case 'Boolean': return 'Boolean';
        case 'Integer': return 'Long';
        case 'Decimal': return 'java.math.BigDecimal';
        case 'String': return 'String';
        case 'Date': return 'java.time.LocalDate';
        case 'Time': return 'java.time.LocalTime';
        case 'DateTime': return 'java.time.ZonedDateTime';
      }
      break;
    case 'reference':
      return typeNameFromPath(tr.path);   // 'Order' (实体类名)
    case 'generic':
      if (tr.name === 'List') return `java.util.List<${javaType(tr.args[0] ?? ...)}>`;
      if (tr.name === 'Map') return `java.util.Map<String, ${javaType(tr.args[0] ?? ...)}>`;
      if (tr.name === 'Page') return `org.springframework.data.domain.Page<${javaType(tr.args[0] ?? ...)}>`;
      return `java.util.List<${javaType(tr.args[0] ?? ...)}>`;
    case 'db':
      return 'java.math.BigDecimal';
  }
  const _never: never = tr;
  return _never;
}
```

注意几个映射决策：

- **全限定名 vs 简名**：Java 类型用全限定名（`java.math.BigDecimal`）而不是 `import + 简名`。这避免了 import 管理——生成器不需要追踪哪些类型需要 import。代价是生成代码略显冗长，但这不重要（生成代码不需要人手工维护）。

- **Integer → Long**：TDSL 的 `Integer` 映射到 Java 的 `Long`（64 位），因为 `Integer` 在 Java 中是 32 位（int），容易溢出。这是领域语义的体现——TDSL 的 `Integer` 是"业务整数"，用 `Long` 更安全。

- **DateTime → ZonedDateTime**：`ZonedDateTime` 携带时区信息，适合跨时区的业务时间。

## 8.7 代码生成的测试策略

codegen 的测试策略围绕确定性展开：

### 快照测试

单测直接断言生成结果：

```ts
it('genJava generates entity with @Id', () => {
  const files = generateJava(parseApp(node));
  const entity = files.find((f) => f.path === '.../entity/Order.java');
  expect(entity?.content).toContain('@Id');
  expect(entity?.content).toContain('@GeneratedValue(strategy = GenerationType.IDENTITY)');
});
```

### 对拍测试

M7 多文件工程的 `parseProject` 将多个分片合并为一个 App。对拍机制把合并结果与手工写就的等价单文件比较——AST 级一致才通过：

```
待比较的合并结果                单文件 AST（标准答案）
     │                                │
     └──────── AST 级 diff ────────────┘
```

### 端到端构建

最硬的测试是 `npm run slice`：从 `todo.tdsl` 开始，经过完整流水线，生成 Spring Boot 工程并运行 `mvn compile`，生成 React 工程并运行 `vite build`。如果生成的代码有语法错误，构建会失败——这个测试保证了"不止语义正确，还要合法可编译"。
