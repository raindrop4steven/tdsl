# 第 6 章 类型检查：语义正确性的守护

parser 保证语法正确，typecheck 保证语义正确。本章讨论 TDSL 类型检查器的设计——它检查什么、为什么检查、以及最重要的，为什么有些东西**故意不检查**。

## 6.1 类型检查在编译器中的位置

传统编译器的语义分析包括两大块：

1. **类型检查**（type checking）：验证表达式的类型是否匹配上下文的要求——`if` 的条件必须是布尔，`+` 的两个操作数必须是数值，赋值的目标类型必须兼容值的类型。
2. **静态语义检查**（static semantic checking）：验证类型以外的语义约束——变量在使用前已声明、函数调用有正确数量的参数、没有重复定义。

TDSL 把两者统一在 `check(app, { libs })` 这一个函数中，返回 `{ ok, diagnostics }`。`ok` 是一个布尔值（所有诊断都是 error 级别的结果为 false），`diagnostics` 是一个诊断数组。

```ts
interface CheckResult {
  ok: boolean;
  diagnostics: Diagnostic[];
}

interface Diagnostic {
  path: string;             // 出错节点 nodePath（可编程寻址）
  line?: number;            // 错误所在行（可选）
  col?: number;             // 错误所在列（可选）
  file?: string;            // M7 多文件工程：错误所在分片（可选）
  message: string;          // 人话错误消息
  severity: 'error' | 'warning';
}
```

## 6.2 TDSL 类型系统的理论基础

### 类型等价：结构等价 vs 名义等价

两种类型系统定义"两个类型相同"的方式不同：

- **名义等价**（Nominal Equivalence）：类型是否相同取决于类型的**名字**。Java 中的 `class A` 和 `class B`，即使字段完全一样，也是两个不同的类型。`A` 类型的值不能赋给 `B` 类型的变量。

- **结构等价**（Structural Equivalence）：类型是否相同取决于类型的**结构**。两个都包含 `{ name: string; age: Integer }` 的类型被视为相同，无论它们的名字是什么。

TDSL 选择**名义等价**为主：实体的类型就是它的名字。`Order` 类型和 `OrderInput` 类型是不同——即使字段相似。这是合理的，因为实体是持久化模型，`Order` 和 `OrderInput` 有不同的运行时角色。

但 TDSL 也引入了结构等价的味道——赋值的兼容性检查是**基于字段**的（TypeRef 的引用解析）而非基于内存布局的。不过这主要影响 codegen（生成 getter/setter），不影响类型系统的核心。

### 类型层级：顶层与底层

TDSL 的类型系统有一个简单的层级：

```
        Any（顶层类型，所有类型的超类型）
         │
   ┌─────┼─────┬──────┬─────┐
  String Integer Decimal Boolean Date DateTime
         │
        Null（底层类型，所有类型的子类型）
```

- `Any` 是所有类型的超类型：任何值都可以赋给 `Any` 类型的变量。
- `Null` 是所有类型的子类型：`null` 可以赋给任何类型的变量（在 TDSL 中，`null` 是一个字面量，可以出现在任何位置）。

还有一个单向的**隐式转换**（implicit conversion）：

```
Integer → Decimal
```

`Integer` 可以隐式转换为 `Decimal`（因为每个整数都可以精确表示为 Decimal），但 `Decimal` 不能隐式转换为 `Integer`（可能丢失小数部分）。这个转换规则在 codegen-java 中体现为：给 Decimal 字段赋整数时会自动 `BigDecimal.valueOf(...)` 包装。

### 泛型实例化

```
List<T>  → 元素类型是 T 的列表
Map<K,V> → 键类型是 K、值类型是 V 的映射
Page<T>  → 分页结果，内容是 T
```

TDSL 的泛型只支持在 `TypeRef` 层面（类型声明），不支持泛型方法。`List<Order>` 表示一个元素类型为 `Order` 的列表。

泛型的类型参数在 typecheck 中用于：

1. **ForEach 容器检查**：`for (const x of xs)` 中的 `xs` 必须是一个 `List<T>` 类型的表达式——元素类型 `T` 就是循环变量 `x` 的类型。
2. **Page 的分页语义**：`Page<T>` 只能由 `.page(n, size)` 查询链产生，codegen-java 据此生成 `Page<T>` 返回类型的 Repository 方法。

## 6.3 typecheck 的签名与入口

代码里的真实签名是 `opts: CheckOptions = {}`（具名类型 + 默认参数）而非书中常见的 `opts?: {...}`——两种写法等价：

```ts
export interface CheckOptions {
  /** 工程侧 FFI 扫描产物（libs/*.json，dev/32）：与 dependency 声明坐标匹配合并进有效目录 */
  libs?: LoadedCatalog[];
}

export function check(app: AppNode, opts: CheckOptions = {}): CheckResult {
  // ...
}
```

`libs` 是工程侧的 FFI 扫描产物（用 `dsl bundle-jar` 生成的 `libs/*.json`）。如果调用方不传 `libs`，typecheck 只使用内核五域（见第 11 章）。

`check` 的入口流程（所有步骤**内联**在同一个函数里，按注释编号展开）：

```ts
export function check(app: AppNode, opts: CheckOptions = {}): CheckResult {
  const diagnostics: Diagnostic[] = [];
  const ownerPath = (owner: BaseNode): string => nodePathOf(app, owner) ?? 'app';
  const cat = createCatalog(opts.libs ?? [], app.dependencies);
  const usedCoords = new Set<string>();

  // 1. 悬空引用：遍历所有 TypeRef，reference 必须能 resolve（Object 内建放行）
  forEachTypeRef(app, (tr, owner) => {
    if (tr.kind === 'reference' && tr.path !== 'Object' && !resolve(app, tr.path)) { ... }
  });

  // 2. ForEach 容器：必须是 List（实体查询 X.all/X.where / 已知变量 / 成员）
  for (const l of app.logics) { forEachStatement(l.body, (st) => { ... }); }

  // 3. Interface：每个 Endpoint 的 logicRef 必须可 resolve
  for (const itf of app.interfaces) { itf.endpoints.forEach((ep) => { ... }); }

  // 4. 实体方法：Todo.get / entity.save / entity.delete 的接收者类型检查
  for (const l of app.logics) {
    forEachStatement(l.body, (st) => checkEntityCalls(app, st, l, diagnostics, ownerPath));
  }

  // 4.6 FFI 目录（dev/27）：receiver 类型已知的成员调用查目录；未知类型放行
  for (const l of app.logics) { checkFfi(cat, app, l, diagnostics, ownerPath, usedCoords); }

  // 4.7 依赖声明与目录一致性（dev/32）：D-dep-1/2/3/4
  checkDependencies(app, cat, opts.libs ?? [], usedCoords, diagnostics, ownerPath);

  // 4.5 外部服务：kind 合法；http 操作必须带 METHOD 'path'
  for (const s of app.services) { ... }

  // 5. View：组件类型已知 + useQuery/useMutation 逻辑存在 + navigate 页面存在
  const exposedLogics = new Set(app.interfaces.flatMap((i) => i.endpoints.map((ep) => ep.logicRef?.split('.').pop() ?? '')));
  for (const v of app.views) { checkView(app, v.elements, diagnostics, ownerPath, exposedLogics); }

  // 6. 文件定位（M7）：按诊断 path 反查所属顶层声明节点的来源文件
  for (const d of diagnostics) { const f = fileOfPath(fileMapOf(app), d.path); if (f) d.file = f; }

  return { ok: diagnostics.length === 0, diagnostics };
}
```

值得一提的实现取舍：真实代码**没有**把每个步骤包装成 `checkDanglingRefs`/`checkForEachContainers`/`attachFile` 这样的独立辅助函数——除实体方法/FFI/依赖/View 抽成了具名的 `checkEntityCalls`/`checkFfi`/`checkDependencies`/`checkView`（且都在本文件内），其余步骤是遍历 app 的**内联循环**，文件定位用 `fileMapOf` + `fileOfPath` 两个纯函数反查。这是"入口函数即流程清单"的写法——6 个 pass 与 6.4 的六类诊断一一对应；真实执行顺序是 `1→2→3→4→4.6→4.7→4.5→5→6`，注释里保留着 4.5/4.6/4.7 这类"历史层积"的编号痕迹。

**读者提示**：上面这段流程是**教学化的编排**。真实实现（`typecheck/src/index.ts:131-245`）的步骤更多且顺序是"历史层积"的——实体方法/FFI/外部服务/依赖声明是先后叠加的独立 pass（注释编号甚至保留着 4.5/4.6/4.7 的历史痕迹），View pass 里还多了"绑定逻辑必须被 interface 端点暴露"这一道（dev/18 的反馈闭环补丁）。但六类核心职责与这里描述的一致：悬空引用、ForEach 容器、Interface 绑定、实体方法与查询链、View 绑定、依赖/外部能力。理解职责划分比记住 pass 编号重要。

`ok` 的判定值得注意：**只要存在任一 error（无论有没有 warning）就判失败**。warning 级别的诊断（如 D-dep-2 依赖未声明 imports）不会阻断 codegen——它们只是提醒，不导致构建失败。

每个 `check*` 函数遍历 AST 的某个部分，发现问题时往 `diagnostics` 数组中推入 `Diagnostic`。

## 6.4 六类诊断详解

### 第一类：悬空引用（Dangling References）

遍历 AST 中所有的 `TypeRef`，检查每个 `reference` 类型的 `path` 能否通过 `resolve(app, path)` 成功解析：

```ts
function checkDanglingRefs(app: AppNode, diagnostics: Diagnostic[]): void {
  for (const ds of app.datasources) {
    for (const ent of ds.entities) {
      for (const prop of ent.properties) {
        checkTypeRef(prop.type, diagnostics);
      }
    }
  }
  for (const s of app.structures) {
    for (const prop of s.properties) {
      checkTypeRef(prop.type, diagnostics);
    }
  }
  // ... Function params / returns / enum 等
}
```

`checkTypeRef` 递归检查 `TypeRef`，包括泛型参数（`List<Order>` 中的 `Order`）：

```ts
function checkTypeRef(tr: TypeRef, diagnostics: Diagnostic[]): void {
  if (tr.kind === 'reference') {
    if (tr.path !== 'Object' && resolve(app, tr.path) == null) {
      diagnostics.push({
        path: nodePathOf(tr),
        message: `悬空引用：无法解析类型 '${tr.path}'`,
        severity: 'error',
      });
    }
  } else if (tr.kind === 'generic') {
    tr.args.forEach((a) => checkTypeRef(a, diagnostics));
  }
}
```

**为什么字符串字面量 `'Object'` 例外？** 因为 TDSL 允许 `Object` 作为"任意类型"的通配符——它对应 Java 的 `Object`。`Object` 不是 TDSL AST 中定义的节点，所以在符号表里找不到，`resolve` 必然返回 null。typecheck 用一句话里最平凡的方式放行这种特殊情况：在判断条件里字面比较 `tr.path !== 'Object'`。（真实实现的诊断消息是精简的 `悬空引用: ${tr.path}` 半句风格，这里为教学展开了完整句子——第 5 章讲过，**错误消息也是文档**，TDSL 正逐步把消息写得项目向 LLM 的"人话"。）

### 第二类：ForEach 容器

`for (const x of xs)` 中的 `xs` 必须是一个可迭代的 List。否则循环无法展开：

```ts
function checkForEachContainers(app: AppNode, diagnostics: Diagnostic[]): void {
  for (const logic of app.logics) {
    forEachStmt(logic.body, (st) => {
      if (st.kind === 'ForEach') {
        const container = st.container;
        if (!isIterableExpr(app, container)) {
          diagnostics.push({
            path: nodePathOf(st),
            message: `ForEach 容器 '${exprToString(container)}' 不是可迭代类型`,
            severity: 'error',
          });
        }
      }
    });
  }
}
```

`isIterableExpr` 的判定逻辑体现了 typecheck 的"宽松放行"策略：

```ts
function isIterableExpr(app: AppNode, e: Expr): boolean {
  // 实体查询 → List<Entity>，可迭代
  if (isEntityQuery(e)) return true;
  // 已知变量 → 查变量表（var 未知类型时放行）
  if (e.kind === 'Ident') {
    const t = lookupVarType(app, e.name);
    return t == null || t.startsWith('List') || t.startsWith('java.util.List');
  }
  // 成员访问 → 结构字段的 List 类型
  if (e.kind === 'Member') { /* 类似上面的判断 */ }
  // 函数调用 → 返回类型是 List 或未知（放行）
  if (e.kind === 'Call') return true;  // 宽松：能调出 List 的才能知道
  return false;
}
```

**为什么函数调用无条件放行？** 因为 TDSL 的函数返回类型是静态声明的——但 typecheck 在简单实现中不追踪每个函数的返回类型（这意味着需要完整的类型推导）。它选择放行函数调用表达式——如果运行时发现不是列表，那是逻辑错误而非类型错误。

### 第三类：Interface 绑定

每个 Endpoint 的 `logicRef` 必须指向存在的 Logic：

```ts
function checkInterfaces(app: AppNode, diagnostics: Diagnostic[]): void {
  for (const itf of app.interfaces) {
    for (const ep of itf.endpoints) {
      const logicName = ep.logicRef?.split('.').pop();
      const logic = app.logics.find((l) => l.name === logicName);
      if (!logic) {
        diagnostics.push({
          path: nodePathOf(ep),
          message: `接口端点 '${ep.name}' 绑定的逻辑 '${logicName}' 不存在`,
          severity: 'error',
        });
      }
    }
  }
}
```

### 第四类：实体方法与查询链

这是最大、最复杂的检查块。它验证：

**静态实体方法**：
- `Order.get(id)`：必须恰好 1 个参数
- `Order.where(...)`：条件字段必须存在于实体、运算符必须在白名单内
- `Order.aggregate(sum(f))`：聚合函数必须在白名单内

**链式方法**：
- `.orderBy/.page/.limit/.groupBy`：参数与字段校验，沿链递归找到起点实体

**实例方法**：
- `.save()/.delete()`：无参数
- `list.add(x)` / `list.count`：接收者必须是 List

**外部服务调用**：
- `userService.getUser(id)`：接收者小驼峰命名匹配 service 短名，核对方法与参数个数

**FFI 成员解析**：
- receiver 类型已知（变量表 / 目录别名静态调用 / 链上 ret 传播 / `ns.Alias` 限定）才查目录
- 未知类型放行；目录外成员报 error 并附"补录口径"

### 第五类：View 组件与绑定

**组件类型发现**：`ViewElementNode.type` 必须属于内置组件集合（table/column/button/form/input/repeat/text/detail/...）或匹配的 dependency npm 三方组件。

**Binding 完整性**：`useQuery('listOrders')` 中的 `listOrders` 必须是一个被 interface 端点暴露的 Logic——否则前端会白屏（这是实战踩坑回流的规则）。

**端点暴露要求**：页面 binding 引用的逻辑必须被 interface 暴露。前端通过 HTTP 调用逻辑，如果逻辑只存在于后端但没暴露为端点，前端无法访问。

### 第六类：依赖声明

D-dep 系列诊断：

| 诊断 | 级别 | 条件 |
|------|------|------|
| D-dep-1 未声明依赖 | error | 用到有效目录中带坐标的产物类，但坐标未出现在 `app.dependencies` |
| D-dep-2 声明无产物 | warning | 声明了依赖但 libs/ 无匹配 coordinate 产物 |
| D-dep-3 版本漂移 | warning | 声明版本 ≠ 产物 coordinate 版本 |
| D-dep-4 撞别名 | error | 同名类跨 jar / 与内核五域冲突 |

## 6.5 FFI 成员解析算法

FFI 成员解析是 typecheck 中最精巧的部分之一。它回答的问题是：`JSON.toJSONString(o)` 中的 `toJSONString` 是否存在？

解析算法：

```ts
function resolveFfiMember(app: AppNode, cat: EffectiveCatalog, expr: Expr): FfiMethod | null {
  if (expr.kind !== 'Member') return null;
  const obj = expr.obj;

  // 情形 1：接收者是目录别名（JSON.toJSONString）——裸名命中
  if (obj.kind === 'Ident') {
    return cat.byAlias(obj.name);
  }

  // 情形 2：接收者是 ns.Alias（fj.JSON）——限定名
  if (obj.kind === 'Member' && obj.obj.kind === 'Ident') {
    const ns = obj.obj.name;
    const alias = obj.prop;
    return cat.byQualified(ns, alias);
  }

  // 情形 3：接收者是变量（x.contains(y)）——查变量类型
  if (obj.kind === 'Ident') {
    const varType = lookupVarType(app, obj.name);
    if (varType?.startsWith('String')) return FFI_STRING_MEMBERS;
    if (varType?.startsWith('List')) return FFI_LIST_MEMBERS;
  }

  return null;
}
```

关键决策是**未知类型放行**：

```ts
// 接收者的类型无法静态确定 → 返回 null，调用方视为"放行"（不报错）
```

为什么放行未知类型？因为 TDSL 的类型推导还不完整（M3 切面尚未实现），如果对未知类型报错，会产生大量误报。误报会污染 LLM 修复闭环——LLM 会对不存在的错误做无意义修改。

## 6.6 宽松放行的设计哲学

TDSL 的类型检查策略可以概括为三个字：**不误报**。

在信息论视角下，这是决策论中的**不对称损失**问题：

- **误报（False Positive）**：报了一个不存在的错误。后果：用户（尤其是 LLM）做无意义的修改，浪费一轮修复循环。
- **漏报（False Negative）**：放过了一个真实的错误。后果：错误到达 codegen，可能生成无法编译的代码。

TDSL 的策略是"能确定才报，不确定就放行"。这源于它的核心用户群体——LLM。LLM 的修复循环是：诊断 → 修改 → 再编译 → 诊断。每一次误报都消耗一整轮循环的算力和时间。相比之下，漏报的后果（无法编译的产物）更容易被下游的"编译失败"信号捕获。

这个策略的具体体现：

- 函数调用表达式的 ForEach 容器：放行
- 未知类型变量的成员方法解析：放行
- 查询链的字段名：检查（如果字段明确是实体属性）
- 条件字段的运算符：检查（固定白名单）

实现中，"宽松放行"不是随意的——每条已实现的诊断都对应一个真实的踩坑记录：

- **端点暴露拦截**：页面 binding 引用了未暴露的逻辑 → 前端白屏（真实事故）
- **D-dep-1 未声明依赖**：用到了 fastjson 但没声明 → 产物编译失败（真实事故）
- **ForEach 容器检查**：遍历了非 List 变量 → 运行时异常（真实事故）

## 6.7 诊断的三要素设计

一个高质量的诊断必须让接收者（人或 LLM）能**立刻知道发生了什么、该怎么办**：

```ts
{
  path: 'app.logics.createOrder.body[0]',   // 可寻址：定位到具体节点
  message: '借款金额不能小于 0',              // 人话：语义明确
  severity: 'error',                         // 级别：决定 ok=false
}
```

三点设计考量：

1. **`path` 是可编程寻址的**。不是文本匹配、不是行号匹配——是一个可以从 `resolve(app, path)` 直接解析出节点的路径。编辑器可以用它高亮节点，LLM 可以用它定位修改点。

2. **`message` 是人话**。错误消息不是"Type mismatch at Expr#3"，而是"条件字段 'status' 不是实体 'Order' 的属性"。这降低了 LLM 理解错误语义的成本。

3. **`file` 支持多文件定位**。M7 之后，诊断可以追到具体分片文件。`attachFile` 函数通过 nodePath 反查顶层声明节点的 `file` 标记。
