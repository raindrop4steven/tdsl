# 第 1 章 导论：为什么需要一个编译器

## 1.1 专用语言的本质

编程语言的设计是一场关于**表达力**与**简洁性**的永恒权衡。

通用编程语言（GPL）如 TypeScript、Java、Python 追求的是表达力——它们要能描述任意算法、任意数据结构、任意并发模型。代价是语法庞大、学习曲线陡峭，对于特定领域的问题，程序员不得不编写大量"脚手架代码"来表达本质上很简单的业务概念。

领域专用语言（DSL）走了相反的路：它只描述一个特定领域的问题，因此可以用极少的语法表达极高的语义密度。SQL 描述数据查询，HTML 描述文档结构，正则表达式描述字符串模式——它们都是 DSL，都比对应的通用语言方案简洁一到两个数量级。

一个典型的低代码场景可以说明这种差异。假设我们要描述"订单"这个业务实体：

**用 Java（GPL）**：需要定义 JPA 实体类、Repository 接口、Service 类、Controller 类——四个文件、约 100 行代码，其中只有属性定义是业务信息，其余全是框架脚手架。

**用 TDSL（DSL）**：同样的语义被压缩到 15 行：

```
entity Order {
  id: Integer @pk;
  customer: String;
  total: Decimal;
  status: String;
}
```

但 DSL 的简洁性不是凭空而来的。那 100 行 Java 代码里的脚手架不会消失——它们被**编译器**自动产生了。DSL 的本质是：把重复性的、可机械推导的代码交给编译器，让人类（或 LLM）只书写不可压缩的业务语义。

这就是为什么 DSL 需要一个编译器。

## 1.2 低代码系统的两条路线

"低代码"这个概念下隐藏着两种截然不同的技术路线，它们对"中间表示"的选择决定了整个系统的上限。

### 路线 A：JSON AST（编辑器驱动）

网易 CodeWave 的 NASL（Natural Application Specification Language）选择了这条路。用户在可视化编辑器中拖拽组件，编辑器产生一棵 JSON 树作为抽象语法树（AST）。这棵 JSON 树是系统的**唯一事实来源**（Single Source of Truth, SSoT）——前端渲染依赖它，后端代码生成依赖它，序列化/反序列化依赖它。

这条路线的优势在于编辑器集成：JSON 天然可序列化、可 diff、可传输。但它的根本缺陷在于**语义贫瘠**——JSON 只有 `string/number/boolean/null/array/object` 六种类型，无法自然表达类型信息、作用域、引用关系。为了弥补这个缺陷，系统不得不在 JSON 之上叠加大量约定和元信息，最终导致 AST 膨胀、校验复杂、错误消息模糊。

### 路线 B：Typed AST（编译器驱动）

TDSL 选择了另一条路：用**类型化的对象树**作为 SSoT，JSON 只是它的派生视图。

一棵 Typed AST 中的每个节点都有明确的 TypeScript 类型——`EntityNode`、`LogicNode`、`Expr`——编译器可以在编译期检查这棵树的结构完整性。如果有人试图在 `EntityNode` 下挂一个不存在的字段，TypeScript 编译器会在编译期就报错，而不是等到运行时才发现。

这条路的代价是更高的实现复杂度——你需要自己写 lexer、parser、类型检查器。但收益是根本性的：**AST 的正确性由类型系统保证，而不是由运行时断言保证**。

### 为什么选路线 B

核心原因是 TDSL 的三个消费端：

1. **给 LLM 写**：TDSL 的书写面是 TypeScript 风格的文本（`function`、`const`、`for-of`）。大语言模型对 TypeScript 有海量训练数据，写 TDSL 近乎本能，极少产生语法幻觉。

2. **给编译器炼**：parser 把文本炼成 Typed AST，typecheck 校验语义正确性，codegen 从 AST 翻译成目标代码。每个阶段都在 AST 上工作。

3. **给用户/产物**：同一棵 AST 分别生成 React 前端和 Java 后端。因为它们来自同一棵树，语义天然一致——不存在"前端展示的订单字段和后端接口返回的不一样"这类问题。

这三个消费端形成了一个闭环：LLM 生成 TDSL 文本 → 编译器验证并翻译 → 产物可运行。如果中间表示是 JSON，LLM 就必须学会输出符合 schema 的 JSON——这比学会写 TS 风格的文本难得多。

## 1.3 编译器作为"语义忠实的翻译器"

传统的编译器教材会花大量篇幅讨论"优化"——常量折叠、死代码消除、内联展开。TDSL 的编译器**不做优化**。它的职责是纯粹的翻译：把一种语言（TDSL）忠实地翻译成另一种语言（Java / React），保证语义不变。

这个"语义不变"是整个系统最核心的不变式。我们用一个形式化的方式来表述它：

> 设 `⟦·⟧_TDSL` 是 TDSL 语义，`⟦·⟧_Java` 是 Java 语义，`⟦·⟧_React` 是 React 语义。编译器的正确性保证是：
> 对任意通过 typecheck 的 TDSL 程序 P，
> `⟦codegen_java(P)⟧_Java ≈ ⟦P⟧_TDSL` 且 `⟦codegen_react(P)⟧_React ≈ ⟦P⟧_TDSL`

其中 `≈` 表示"在业务语义上等价"（不是形式等价，因为两个平台的运行时模型不同）。

这个不变式在实践中的含义是：如果 TDSL 中写了 `Order.where(total > 0)`，Java 端的 Repository 会生成一个查询方法，React 端的 hooks 会调用这个方法——两端看到的"总金额大于 0 的订单"是同一批数据。

## 1.4 流水线全貌

一个 TDSL 源文件从文本到可运行产物，经历以下阶段：

```
source code (text)
      │
      ▼
  ┌─────────┐
  │  Lexer   │  字符流 → Token 流（带行列信息）
  └────┬────┘
       │
       ▼
  ┌─────────┐
  │  Parser  │  Token 流 → 裸 AST（短名未绑定）
  └────┬────┘
       │
       ▼
  ┌─────────┐
  │ linkApp  │  短名 → nodePath 绑定（悬空引用报错）
  └────┬────┘
       │
       ▼
  ┌──────────┐
  │ Typecheck │  六类诊断（悬空引用/类型/绑定/依赖...）
  └────┬─────┘
       │ ok
       ▼
  ┌──────────┐    ┌──────────────┐
  │codegen-java│   │codegen-react │
  └─────┬────┘    └──────┬───────┘
        │                │
        ▼                ▼
  Spring Boot        Vite+React
   工程 (.java)       工程 (.tsx)
```

注意三个关键设计决策：

**1. linkApp 是 parser 的一部分，不是独立阶段。** parser 在产出 AST 之后立即执行链接，把所有短名（如 `Order`、`createOrder`）替换为完整的 nodePath（如 `app.datasources.defaultDS.entities.Order`）。下游拿到的 AST 中，所有引用都已经是可直接 `resolve()` 的路径字符串。这保证了 AST 的自包含性——一棵 AST 可以脱离原始文本被独立分析。

**2. typecheck 是唯一的"安全网"。** 不论 AST 来自 parser（正常路径）、多文件合并（`parseProject`）、还是未来可能的 JSON 直出，都必须经过 `check()` 函数。typecheck 不关心 AST 是怎么产生的，它只关心这棵树是否合法。

**3. codegen 是纯函数。** `generateJava(app)` 和 `generateReact(app)` 接收一棵 AST，返回 `GeneratedFile[]`（文件路径 + 内容的数组）。它们不读磁盘、不写磁盘、不产生副作用。同一棵 AST 必然产生相同的输出——这使得快照测试和对拍成为可能。

## 1.5 为什么用 TypeScript 实现

TDSL 的编译器本身是用 TypeScript 编写的。这不是一个随意的选择，而是基于三个工程考量。

### 判别联合：代数数据类型的 TS 表达

TDSL 的 AST 节点用 TypeScript 的**判别联合**（Discriminated Union）定义。每个节点有一个 `kind` 字段作为类型标签：

```ts
type Expr =
  | { kind: 'Ident'; name: string }
  | { kind: 'Member'; obj: Expr; prop: string }
  | { kind: 'Call'; callee: Expr; args: Expr[] }
  | { kind: 'Binary'; operator: string; left: Expr; right: Expr }
  | ... // 更多变体
```

TypeScript 的类型收窄（narrowing）机制使得 `switch (e.kind)` 之后，编译器自动知道 `e` 是哪个变体。这等价于 ML/Haskell 的代数数据类型（ADT）和模式匹配，但不需要引入额外的语言或编译器。

### `never` 类型：编译期穷尽性检查

当一个 `switch` 处理了所有 `kind` 变体后，变量的类型会收窄为 `never`——一个不可能存在的类型。如果有人新增了一个 `kind` 变体但忘了在某个 `switch` 中处理它，TypeScript 编译器会在编译期报错：

```ts
const result = genExpr(expr);
switch (expr.kind) {
  case 'Ident': return expr.name;
  case 'Member': return genMember(expr);
  case 'Call': return genCall(expr);
  // 如果 Expr 新增了 'New' 变体但这里没处理，
  // TS 编译器会报错：Type 'New' is not assignable to type 'never'
}
```

这意味着：**新增 AST 节点类型时，编译器会强制你补齐所有消费端的处理逻辑**。这不是负担，而是设计——它把"忘记处理新情况"这类 bug 从运行时错误前移到编译期错误。

### npm 生态

TDSL 的目标产物是 React + Java。这两个生态的工具链（Vite、Maven）都通过 npm 分发。用 TypeScript 实现编译器意味着所有工具链可以用同一个包管理器统一管理，开发者不需要学习额外的构建工具。

## 1.6 代码规模与复杂度

TDSL 的编译器不是学术项目——它是一个有 272 个单测、能端到端生成可编译工程的真实系统。但它的代码量控制在了一个适合教学的规模：

| 包 | 职责 | 核心代码量 |
|---|------|-----------|
| `core` | AST 类型定义、符号表、FFI 目录 | ~650 行 |
| `parser` | 词法分析 + 递归下降 + 链接 | ~1350 行 |
| `typecheck` | 六类诊断 | ~1250 行 |
| `codegen-java` | AST → Spring Boot | ~1900 行 |
| `codegen-react` | AST → React | ~2100 行 |

总计约 7250 行 TypeScript（不含单测）。这个规模大约是一本 300 页教材中一个完整案例的典型大小——足够复杂以展示真实的设计决策，又足够小以在一周内通读全部源码。

## 1.7 本书的结构

本书按编译器的经典阶段组织，但每一章都围绕 TDSL 的**具体设计决策**展开，而不是泛泛地介绍理论。

第一部分（第 2 章）直接切入 AST 设计——因为 AST 是编译器所有阶段共享的"合约"，先理解 AST 的设计才能理解后续每个阶段为什么这样做。

第二部分（第 3-5 章）覆盖前端：词法分析、语法分析、引用绑定。这是传统编译器教材花最多篇幅的部分，我们也不例外——但重点放在 TDSL 的特殊挑战上（查询语言的形态分派、JSX 子集解析）。

第三部分（第 6-7 章）是语义分析：类型检查和符号表。这里的理论密度最高——类型等价、子类型、作用域嵌套——但每个理论概念都直接映射到 TDSL 的具体实现。

第四部分（第 8-10 章）是代码生成：从 AST 到 Java 和 React。这是 TDSL 最独特的部分——同一个 AST 如何产生两种截然不同的目标语言。

第五部分（第 11 章）是 FFI 与外部能力：Java/npm 如何作为一等公民接入 DSL。这是 TDSL 区别于一般 DSL 编译器的核心设计。

每一章的结构是：先讲原理，再讲 TDSL 的设计决策，最后展示关键实现片段。我们不追求逐行解释代码——那是源码注释的工作——而是追求解释**为什么代码长这样**。
