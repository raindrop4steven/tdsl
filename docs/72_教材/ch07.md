# 第 7 章 符号表与作用域分析

符号表是编译器连接"名字"与"定义"的结构。名字解析的准确性直接决定了 typecheck 的准确性和 codegen 的确定性。

## 7.1 名字解析的理论

编译器需要一个机制来回答一个问题：源码中的名字 `X` 指的是哪个定义？

这个问题的理论基础是**作用域**（scope）——名字的可见范围。经典的作用域规则：

1. **词法作用域**（Lexical Scoping）：名字的绑定由代码的**文本结构**决定，不是由运行时调用栈决定。JS/Java/C 都是词法作用域。

2. **嵌套作用域**（Nested Scopes）：内层作用域可以访问外层作用域的绑定，但外层不能访问内层。

3. **遮蔽**（Shadowing）：内层作用域可以声明与外层同名的绑定，此时内层的名字遮蔽外层——内层的引用解析到内层绑定。

4. **绑定时间**（Binding Time）：名字什么时候被解析到定义？编译期（静态绑定）或运行期（动态绑定）。编译器在链接阶段做静态绑定。

TDSL 的符号表遵循词法作用域原则，但有几个领域特化的设计。

## 7.2 符号表的数据结构选择

符号表有几种实现选择：

| 数据结构 | 插入 | 查找 | 缺点 |
|---------|------|------|------|
| 线性列表 | O(1) | O(n) | 规模大时慢 |
| 哈希表 | O(1) | O(1) | 不支持作用域层次 |
| 分层结构（作用域栈） | O(1) | O(depth) | 需要显式管理作用域 |

TDSL 的数据规模很小（一个应用的实体/结构/逻辑通常不超过几十个），线性查找完全够用。但它选择了**分层结构**，不是因为它快，而是因为它的语义与语言的作用域规则精确对应。

## 7.3 TDSL 的分层符号表

TDSL 的符号表定义在 `packages/core/src/symbols.ts`：

```ts
interface TypeSymbolTable {
  global: Map<string, string>;                       // 全局概念 → nodePath
  dataSources: Map<string, Map<string, string>>;     // 数据源名 → (实体短名 → nodePath)
}
```

### global 层

`global` 映射存储不归属任何数据源的全局概念：结构、枚举、逻辑、接口、以及**全局唯一的实体短名**。

为什么实体短名也出现在 global？因为 M1（命名空间里程碑）之前的 TDSL 没有数据源概念——所有实体归入一个隐式全局命名空间。为了兼容，单数据源应用中的实体短名是全局唯一的，多数据源应用中的实体短名归入各自的 `dataSources` 映射。

### dataSources 层

`dataSources` 映射存储数据源内部的实体：

```
dataSources = {
  'erp':  { 'Order': 'app.datasources.erp.entities.Order', 'Product': '...' },
  'crm':  { 'Customer': 'app.datasources.crm.entities.Customer' }
}
```

**为什么实体短名归数据源而不是归全局？** 因为不同数据源可能有同名实体（`erp.Order` 和 `crm.Order`）。这是真实业务场景——ERP 系统和 CRM 系统都可能有"订单"概念，但它们是不同的实体。M1 命名空间让它们共存。

### VarScope：函数内变量

```ts
interface VarScope {
  vars: Map<string, { javaType: string }>;
}
```

`VarScope` 是 function 内变量的符号表。它不同于全局符号表——它记录变量名 → Java 类型（在 codegen 时使用）。每个 function 的 codegen 开始时会创建一个新的 `VarScope`，把参数登记进去，然后逐语句翻译，把新变量登记进去。

**为什么 VarScope 记录 Java 类型而非 TDSL 类型？** 因为 codegen 需要知道变量的 Java 类型来决定生成什么代码。例如，`order.total` 的赋值需要判断目标字段类型是否为 `BigDecimal`——如果是，整数赋值需要自动包装。

## 7.4 resolveShort：短名解析

`resolveShort` 回答"`Order` 这个名字指向什么"。它的算法分三步：

```ts
function resolveShort(table: TypeSymbolTable, name: string, ctxDs?: string): string | null {
  // 1. 当前数据源优先
  if (ctxDs) {
    const ds = table.dataSources.get(ctxDs);
    const hit = ds?.get(name);
    if (hit) return hit;
  }
  // 2. 回退全局
  if (table.global.has(name)) return table.global.get(name)!;
  // 3. 未找到
  return null;
}
```

**先查当前数据源，再回退全局**。这个顺序很重要：

1. 如果 `Order` 在 `erp` 数据源有定义，在 `erp` 作用域中引用 `Order` 时解析到 `erp.Order`。
2. 如果 `Order` 只存在于 global（单数据源应用），`resolveShort` 也能命中。
3. 如果 `Order` 在多个数据源都有定义，`resolveShort` 可能产生歧义——这时调用方需要使用 `isAmbiguousEntity` 检测。

### 歧义检测

TDSL 对歧义的处理是**宁可报错也不猜测**：

```ts
function isAmbiguousEntity(table: TypeSymbolTable, name: string, ctxDs?: string): boolean {
  if (ctxDs && table.dataSources.get(ctxDs)?.has(name)) return false;  // 当前数据源命中 → 无歧义
  // 统计所有数据源中有多少个同名实体
  let dsCount = 0;
  for (const [, map] of table.dataSources) {
    if (map.has(name)) dsCount++;
  }
  return dsCount > 1;  // >1 → 歧义
}
```

这个决策的工程理由：**歧义时猜测必然导致错误**。如果编译器在 `erp.Order` / `crm.Order` 中"猜测"了最近的或第一个，用户（或 LLM）会不知不觉地把错误的实体引入代码。D-dep-4（撞别名）也是同样的哲学——含糊即报错，让用户显式消解。

## 7.5 resolveQualified：限定名解析

`resolveQualified` 解析 `erp.Order` 这种带数据源前缀的限定名：

```ts
function resolveQualified(table: TypeSymbolTable, dsName: string, entName: string): string | null {
  const ds = table.dataSources.get(dsName);
  return ds?.get(entName) ?? null;
}
```

限定名是唯一没有任何歧义的引用形式——数据源名和实体名都是显式的。typecheck 和 codegen 遇到 `erp.Order` 时，优先尝试限定名解析，失败后再回退短名解析。

### 在 linkApp 中的应用

linkApp 用这两个函数解析 TypeRef 引用。策略是：

```ts
function linkTypeRefName(app: AppNode, name: string, ctxDs?: string): void {
  // 先判断是否是限定名
  if (name.includes('.')) {
    const [ds, ent] = name.split('.');
    const path = resolveQualified(table, ds, ent);
    if (!path) throw new TdslSyntaxError(`未知限定名 '${name}'`);
    return path;
  }
  // 短名
  if (isAmbiguousEntity(table, name, ctxDs)) {
    throw new TdslSyntaxError(`'${name}' 在多个数据源中存在歧义，请使用限定名 dsName.Entity`);
  }
  const path = resolveShort(table, name, ctxDs);
  if (!path) throw new TdslSyntaxError(`未知类型 '${name}'`);
  return path;
}
```

## 7.6 linkApp 的完整绑定流程

linkApp 是 parser 的最后一环。它的输入是裸 AST，输出是绑定后的 AST。流程：

```
buildTypeSymbolTable(app)     // 1. 遍历 AST 构建符号表（收集所有顶层声明）
  → 检测重名                     // 2. 数据源内实体重名、全局概念重名 → 报错
  → 绑定 TypeRef               // 3. 遍历所有类型的引用 → 换成 nodePath
  → 绑定 Endpoint.logicRef     // 4. 接口端点 → 绑定函数 nodePath
  → 绑定 View Binding.target   // 5. 页面绑定 → 绑定函数/页面 nodePath
```

### 重名检测

linkApp 在构建符号表时检测重名。两个层级的重名规则不同：

- 数据源内实体重名 → `duplicate entity 'Order'`（同源冲突）
- 全局概念重名 → `duplicate type name 'OrderInput'`（跨源冲突）

**为什么全局概念（struct/enum/function/interface）不能跨数据源重名？** 因为它们是跨数据源共享的——DTO、枚举、业务逻辑不属于任何一个数据源。如果两个数据源都声明了 `OrderInput`，引用 `OrderInput` 时编译器无法确定用哪个。

### 绑定 TypeRef

遍历所有 `TypeRef`，把 `reference` 节点的 `{ name: 'Order' }` 替换为 `{ path: 'app.datasources.defaultDS.entities.Order' }`。这个替换发生在 AST 内部，下游（typecheck/codegen）拿到的 AST 中所有引用都已经是完整路径。

### 绑定 Endpoint.logicRef

每个 Endpoint 的 `logicRef` 字段（如 `'getOrder'`）被替换为完整的 `'app.logics.getOrder'`：

```ts
function linkEndpoints(app: AppNode): void {
  for (const itf of app.interfaces) {
    for (const ep of itf.endpoints) {
      const logic = app.logics.find((l) => l.name === ep.logicRef);
      if (!logic) {
        throw new TdslSyntaxError(`接口端点 '${ep.name}' 引用了不存在的函数 '${ep.logicRef}'`);
      }
      ep.logicRef = nodePathOf(logic);
    }
  }
}
```

### 绑定 View Binding.target

类似的逻辑处理 View 中的 Binding。`useQuery('listOrders')` 的 Binding target 被替换为 `listOrders` 函数对应的 nodePath；`navigate('OrderDetail')` 的 target 被替换为 `OrderDetail` 页面的 nodePath。

## 7.7 寻址的双向函数

符号表的最终输出是 nodePath 字符串，而 nodePath 的反向解析需要 `resolve` 和 `nodePathOf`。

### resolve：从路径到节点

```ts
function resolve(app: AppNode, path: string): AnyNode | null {
  // 沿路径逐段下降
  const segs = path.split('.');
  let current: AnyNode = app;
  for (const seg of segs) {
    if (seg === 'app') continue;
    const next = descend(current, seg);
    if (!next) return null;
    current = next;
  }
  return current;
}
```

`descend` 根据当前节点的类型决定如何进入子节点：

- `App` 节点：查数组字段（`datasources`、`structures`、`enums`、`logics`、...）
- `DataSource` 节点：查 `name` 匹配，然后进入 `entities`
- `Entity` 节点：查 `name` 匹配
- 数组索引：`endpoints[0]` 支持下标访问

### nodePathOf：从节点到路径

```ts
function nodePathOf(node: AnyNode): string {
  // 每个节点在 AST 构建时被分配一个唯一的 id，其中编码了路径
  return node.id;  // 简化示意
}
```

实际实现中，TDSL 的每个节点都有一个 `id` 字段，parser 在构建节点时同时分配 `id`（编码了路径信息）和它在数组中的位置。`nodePathOf` 直接返回这个 `id`——不需要重新遍历 AST 寻找路径。

## 7.8 变量作用域与 Java 语义对齐

`VarScope` 的设计有一个微妙但重要的决策：**与 Java 语义对齐**。

Java 中局部变量的作用域规则是"块作用域"——同一个块中不能重复声明同名变量，但不同块可以。TDSL 的处理是：

```ts
function lookupVar(scope: VarScope, name: string): VarEntry | null {
  // 简化：查当前块，找不到沿外层块向上
  let current: VarScope | undefined = scope;
  while (current) {
    const hit = current.vars.get(name);
    if (hit) return hit;
    current = current.parent;
  }
  return null;
}
```

**为什么不用 JavaScript 的规则（可以遮蔽）而用 Java 的规则（同一块内不能重复声明）？** 因为 TDSL 编译的目标是 Java——如果 TDSL 允许同块遮蔽，codegen 会遇到"生成两个同名局部变量"的冲突。与目标语言语义对齐，让编译器的翻译更简单、更可预测。

这个决策在 codegen 中的体现：`VarDecl` 语句生成时先查 `lookupVar`——如果找到同名变量，生成"赋值"而非"声明新变量"，沿用外层的类型。这模拟了 Java 的变量复用语义。
