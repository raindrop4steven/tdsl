# 第 4 章 语法分析（上）：文法、递归下降与表达式解析

语法分析是编译器中理论密度最高的阶段之一。它把 Token 流变成 AST，过程中需要处理优先级、结合性、左递归、错误恢复等一系列问题。

## 4.1 形式化基础：上下文无关文法

词法分析处理正则语言，语法分析处理**上下文无关语言**（Context-Free Language, CFL）。上下文无关语言由上下文无关文法（Context-Free Grammar, CFG）定义。

一个 CFG 是四元组 `G = (V, Σ, P, S)`：

- `V`：非终结符集合（`S`, `Expr`, `Stmt`, ...）
- `Σ`：终结符集合（Token 类型）
- `P`：产生式集合（`S → Expr ; S`）
- `S`：起始符号

例如，一个极简的表达式文法：

```
Expr → Expr '+' Expr
     | Expr '*' Expr
     | '(' Expr ')'
     | number
```

这个文法描述了"由 `+`、`*`、括号和数字组成的算术表达式"。从起始符号 `Expr` 开始，反复应用产生式，可以推导出任何合法的表达式。

### BNF 与 EBNF 表示法

产生式通常用 BNF（Backus-Naur Form）或其扩展 EBNF 表示：

```
// BNF
<expr> ::= <expr> '+' <expr>
         | <expr> '*' <expr>
         | '(' <expr> ')'
         | <number>

// EBNF（加入重复和可选）
expr = expr ('+' | '*') expr
     | '(' expr ')'
     | number ;
```

EBNF 的 `{ ... }` 表示零次或多次重复，`[ ... ]` 表示可选。TDSL 的文法用 EBNF 描述。

## 4.2 TDSL 文法的设计过程

TDSL 的文法不是从某个理论模型推导出来的——它从**需求**反推。设计过程大致是：

1. **列出所有顶层声明**：entity、struct、enum、function、interface、page、dialog、service、dependency
2. **为每种声明设计语法**：entity 有 name + properties，function 有 name + params + body
3. **设计表达式语言**：字面量、二元运算、函数调用、成员访问
4. **设计语句语言**：变量声明、赋值、条件、循环、返回
5. **处理歧义**：查询语言、JSX 子集

最终的文法大致如下（简化版）：

```
App       = { TopDecl } EOF ;
TopDecl   = Annotation* EntityDecl
          | Annotation* FuncDecl
          | Annotation* InterfaceDecl
          | Annotation* ViewDecl
          | DependencyDecl
          | Annotation* ServiceDecl ;

EntityDecl = 'entity' IDENT '{' { EntityProp } '}' ;
EntityProp = IDENT ':' TypeRef [ AnnotationList ] ';' ;

FuncDecl  = 'function' IDENT '(' Params ')' [ ':' TypeRef ] Block ;
Block     = '{' { Stmt } '}' ;
Stmt      = 'const' IDENT [ ':' TypeRef ] '=' Expr ';'
          | Expr '=' Expr ';'
          | 'if' '(' Expr ')' Block [ 'else' Block ]
          | 'for' '(' 'const' IDENT 'of' Expr ')' Block
          | 'return' [ Expr ] ';'
          | Expr ';' ;

Expr      = Expr '.' IDENT
          | Expr '(' Args ')'
          | Expr BinOp Expr
          | '(' Expr ')'
          | 'new' TypeRef '(' Args ')'
          | 'new' '[' Args ']'
          | IDENT | NUMBER | STRING | 'null' | 'true' | 'false' ;
```

注意：这不是 TDSL 的完整文法——完整的 EBNF 在附录 A 中。但这个简化版已经展示了几个关键设计。

## 4.3 递归下降原理

**递归下降**（Recursive Descent）是最直观的语法分析方法：文法中的每个非终结符对应一个函数，函数体就是产生式的翻译。

例如，`Block = '{' { Stmt } '}'` 对应：

```ts
function parseBlock(): Statement[] {
  expect('{');
  const stmts: Statement[] = [];
  while (!check('}')) {
    stmts.push(parseStatement());
  }
  expect('}');
  return stmts;
}
```

递归下降的优势：

1. **直观**：文法 → 代码的映射几乎是机械的
2. **易于调试**：每个函数对应一个语法结构，栈回溯可以精确定位解析失败的位置
3. **易于错误恢复**：每个函数可以在失败时产生精确的错误消息

### LL(1) 的限制

纯递归下降要求文法是 LL(1) 的——在每个非终结符的产生式中，各个选择的 FIRST 集合不能相交。如果相交，解析器在看到一个 Token 时无法确定该走哪个分支。

例如，如果文法有：

```
Stmt → Expr ';'
     | IDENT '=' Expr ';'
```

当看到 `IDENT` 时，解析器无法确定这是 `Expr`（变量赋值的左值）还是 `IDENT '=' Expr`（赋值语句的左部）。两个选择的 FIRST 集合都包含 `IDENT`。

TDSL 的解决方案是：**不在 parser 层面区分赋值和表达式调用**——先解析成表达式，然后在语义分析阶段检查赋值的合法性。这避免了 LL(1) 的限制，但把部分检查推迟到了 typecheck。

## 4.4 消除左递归

文法中的左递归是递归下降的天敌。考虑表达式文法：

```
Expr → Expr '+' Expr
     | '(' Expr ')'
     | number
```

如果直接翻译成递归下降：

```ts
function parseExpr(): Expr {
  const left = parseExpr();  // 无限递归！
  expect('+');
  const right = parseExpr();
  return { kind: 'Binary', operator: '+', left, right };
}
```

`parseExpr` 的第一行就调用自身——无限递归。

### 优先级爬升（Precedence Climbing）

解决左递归的标准方法是把**优先级**编码到**递归层次**中：

```
Expr      → Or ;
Or        → And ( '||' And )* ;
And       → Equality ( '&&' Equality )* ;
Equality  → Relational ( ( '===' | '!==' ) Relational )* ;
Relational→ Additive ( ( '<' | '<=' | '>' | '>=' ) Additive )* ;
Additive  → Multiply ( ( '+' | '-' ) Multiply )* ;
Multiply  → Postfix ( ( '*' | '/' ) Postfix )* ;
Postfix   → Primary ( '.' IDENT | '(' Args ')' )* ;
Primary   → '(' Expr ')' | 'new' TypeRef '(' ... ')' | IDENT | NUMBER | STRING | ... ;
```

每层对应一个优先级。低优先级运算符在高层（外层递归），高优先级在低层（内层递归）。**这里有个重要区分：`=`、`like`、`in` 不属于通用表达式优先级链**——它们只在 `parseWhereArgs()` 里通过专用函数 `parseWhereCond()` 解析（第 5 章详述）。这是因为 `=` 在通用表达式里没有意义（赋值是语句，见第 2 章），只有在 `where(...)` 查询条件下才有"相等比较"的语义。同理 `like`（模糊匹配）和 `in`（集合成员）只在 where 里合法——把它们留在通用表达式里会意外让 `x = 5` 作为表达式合法，破坏了"赋值是语句"的不变式。

在实现中，`Additive` 的解析循环是：

```ts
function parseAdditive(): Expr {
  let left = this.parseMultiplicative();
  while (this.peek().value === '+' || this.peek().value === '-') {
    const op = this.next().value as '+' | '-';
    left = { kind: 'Binary', operator: op, left, right: this.parseMultiplicative() };
  }
  return left;
}
```

`while` 循环处理同优先级的左结合：`1 + 2 + 3` 被解析为 `(1 + 2) + 3`。

### Pratt Parsing

另一种处理表达式优先级的方法是 **Pratt Parsing**（也叫 Top-Down Operator Precedence）。它为每个运算符维护两个优先级：**左绑定力**（left binding power）和**右绑定力**（right binding power）。

Pratt Parsing 的核心是：

```ts
function parseExpr(minBp: number): Expr {
  let left = parsePrimary();
  while (precedence(peek()) > minBp) {
    const op = advance();
    const right = parseExpr(rightBindingPower(op));
    left = { kind: 'Binary', operator: op, left, right };
  }
  return left;
}
```

TDSL 的 parser 使用的是**优先级爬升**（分层递归下降）而非 Pratt Parsing——前者更直观，与文法的对应关系更清晰。

## 4.5 TDSL 的完整优先级表

对照 §4.4 的分层文法，从低到高（数字越小优先级越低）：

| 优先级 | 层级函数 | 运算符 | 结合性 |
|--------|---------|--------|--------|
| 1 | `parseOr` | `\|\|` | 左 |
| 2 | `parseAnd` | `&&` | 左 |
| 3 | `parseEquality` | `===`, `!==` | 左 |
| 4 | `parseRelational` | `<`, `<=`, `>`, `>=` | 左 |
| 5 | `parseAdditive` | `+`, `-` | 左 |
| 6 | `parseMultiplicative` | `*`, `/` | 左 |
| 7 | `parsePostfix` | `.`, `(...)` 成员访问与调用 | 左 |

这个优先级表不是拍脑袋定的——它遵循了数学和编程语言的惯例：

- **乘法优先于加法**（数学惯例）：`2 * 3 + 1` 是 `6 + 1`。
- **关系运算优先于逻辑运算**：`total > 0 && status = 'paid'` 不需要写 `(total > 0) && ...`。这里两次比较里，一个是 `<`（关系层）一个是 `=`（只存在 where 层，见后），所以 `where(...)` 里的条件天然比 `&&` 先求值。
- **三等号与关系运算分两层是 JavaScript 惯例**：`a === b < c` 这样的链式比较在 JS 里是 `a === (b < c)`——TDSL 保留了这一分级。
- **成员访问和函数调用是后缀的、优先级最高**：`order.save()` 先绑定 `save` 再绑定 `()`。

和 C/Java 的优先级表相比，TDSL 的表**刻意缺了两类运算符**：没有一元 `!`（逻辑非），也没有位运算符（`&`、`|`、`<<`）。逻辑非缺失是因为布尔取反在 TDSL 里直接写成 `=== false`（`!paid` → `paid === false`），语义一样且少一层优先级问题；位运算被认为不是业务 DSL 需要的能力（写的人基本是业务分析师而非底层程序员）。**删运算符永远比加运算符省事**——每个运算符都意味着 typecheck 要检查类型、codegen 要生成代码、LLM 要学习语义。这正是"小语言"（little language）哲学：只留业务必需的最小运算符集。

## 4.6 顶层分派

TDSL 的 parser 入口 `parseAppInto`（`parser.ts:159`）是一个 while 循环，按"注解优先、再接关键字"两步分派：

```ts
parseAppInto(file: string): AppNode {
  const app = { ...createNode('App'), name: 'todo', datasources: [], structures: [], ... };
  let currentDs: DataSourceNode | null = null;      // 当前数据源（@datasource 切换）

  while (this.peek().type !== 'eof') {
    // 第一步：顶层注解
    if (this.peek().value === '@') {
      this.next();
      const ann = this.expectIdent();
      if (ann === 'datasource') {      // @datasource('erp')：声明/切换当前数据源
        ... currentDs = 同名数据源或新建 ...
      } else if (ann === 'service') {  // @service(...)：暂存配置，等下一个 service 声明消费
        ...
      } else if (ann === 'title' || ann === 'menu') {  // 视图中文名/菜单分组
        ...
      }
      continue;
    }

    // 第二步：结构关键字
    const kw = this.peek().value;
    if (kw === 'entity') { /* 若无当前数据源则隐式建 defaultDS，加入 currentDs.entities */ }
    else if (kw === 'struct') app.structures.push(this.parseStructure());
    else if (kw === 'enum') app.enums.push(this.parseEnum());
    else if (kw === 'function') app.logics.push(this.parseLogic());
    else if (kw === 'interface') app.interfaces.push(this.parseInterface());
    else if (kw === 'page' || kw === 'dialog') { /* parseView；挂上暂存的 @title/@menu 注解 */ }
    else if (kw === 'service') app.services.push(this.parseService(pendingServiceConfig));
    else if (kw === 'dependency') app.dependencies.push(this.parseDependency());
    else if (kw === 'component')
      this.fail("'component' 注册层已删除（dev/33）：npm 一等公民——页面直接写三方组件标签");
    else this.fail(`unexpected '${kw}' at top level`);
  }
  stampFile(app, file);
  return app;
}
```

几个值得注意的设计：

**注解优先两遍式。** 注解（`@` 开头）先被整体消费并作用于"下一个声明"，然后才看关键字节。`@datasource('erp')` 不能独立成声明——它只是为后续 entity 设置数据源归属的标志。TDSL 的顶层注解用竖线 `@` 而不是 `keyword` 的方式，让"声明修饰"和"声明本身"在语法上泾渭分明。

**`@datasource('erp')` 是隐式的、可累加的。** 没有显式的"数据源结束"标记——数据源从 `@datasource('x')` 开始，一直持续到下一个 `@datasource(...)`。同一名字复用已有数据源，entity 追加进去。完全没有注解时，第一个 entity 触发隐式 `defaultDS`。

**为什么用 while 循环而非递归？** 因为顶层声明是平级的（不是嵌套的），用循环更自然。每个 `parse*` 函数消耗一种声明，把结果推入 `app` 的对应数组。

**专用错误消息是"文档"。** `component` 分支展示了 TDSL 的一个习惯：**被删除的语法不是默默报 unexpected，而是报出一条带路径的错误，解释它变成了什么**。对 LLM 而言，这条错误消息就是一次免费的文档注入——模型读到"已删除（dev/33）：npm 一等公民——页面直接写三方组件标签"就直接学会新写法了。这是错误诊断"人话化"设计的一个缩影（第 6 章会看到 Diagnostic.message 也有同样的风格追求）。

## 4.7 错误策略：失败即止

TDSL 的 parser 对语法错误的策略是**失败即止**（fail-fast），不是教科书式的错误恢复。看 `fail` 的完整实现：

```ts
private fail(msg: string): never {
  const t = this.peek();
  throw new TdslSyntaxError(msg, t.line, t.col);
}
```

它在**第一个错误**就抛出 `TdslSyntaxError`，整个 `parseAppInto` 中止。**没有同步 token 集、没有跳过 Token 继续解析、没有尝试报告多个错误的机制**。这与学术界推荐的做法相反——经典编译器（如 GCC、Clang）会做错误恢复，一次编译抓出尽量多的错误。

**为什么故意失败即止？** TDSL 的消费场景不是"人类把整个文件写完再全量报错"，而是 **LLM 在环内修复**：模型生成 → 编译 → 得到第一条带行列的错误 → 修改 → 重新编译。在这种循环里：

1. **串联错误（cascading errors）是噪音**。恢复解析往往在真正错误的位置报出一连串连锁错误，其中大多是假的。LLM（和人类一样）会被第一个真实的错误消息喂饱——多报只会稀释注意力。
2. **终止符即重启点**。模型下一次生成是基于"上一条错误消息"做定点修改的，失败即止保证了"上一条错误"语义上最接近首错位置。
3. **parser 更简单**。没有恢复逻辑，`fail` 只有一个职责：抛错。错误恢复的正确性维护是个无底洞（"这个位置该跳过谁？"），省下来等于省整片复杂度。

代价也真实存在：一次编译只能修一个语法错误，语法错误的修复需要多轮。但 TDSL 里语法错误率低（示例矩阵单测锁定可编译性、LLM few-shot 稳定），一轮 3-5 秒的编译足够抵消。**这是"编译器正确性服务于下游自动化"而非"服务于人类阅读"的一次权衡**——同样的哲学在第 6 章"宽松放行"、第 11 章诊断闭环中反复出现。
