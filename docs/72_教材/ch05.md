# 第 5 章 语法分析（下）：查询语言、JSX 与链接

上一章讲解了递归下降和表达式解析的一般原理。本章聚焦 TDSL 特有且更具挑战的部分：查询语言如何在普通函数调用语法中"生长"出来、JSX 子集如何解析、以及 linkApp 如何把短名绑定到 nodePath。

## 5.1 问题：`Order.where(total > 0)` 为什么特殊

考虑这个表达式：

```
Order.where(total > 0)
```

从语法角度，它看起来就是一次普通的方法调用——`where` 是方法名，`total > 0` 是实参。如果按普通函数调用的规则解析实参，`total > 0` 会被解析为 `Binary`（比较表达式）——这没问题，因为 `Binary` 是合法的表达式。

问题出在**语义**上。普通方法调用的实参是"运行时求值的表达式"，而 `where` 的实参是**编译期求值的查询条件**：

- `total > 0` 中的 `total` 不是运行时变量，而是**实体字段**（编译期类型引用）
- `where(...)` 的语义是"过滤"，不是"调用一个函数"
- 查询条件（`field op value`）的语序和组成规则不同于普通表达式

如果 parser 用普通函数调用的规则解析 `where` 的实参，它无法捕获 `field op value` 这种三元结构（字段、运算符、值）——因为这本质上不是一个二元的表达式。

## 5.2 形态分派：按调用点选择解析策略

TDSL 的解决方案是**形态分派**（morphological dispatch）：parser 在解析函数调用时，根据"接收者是否是实体 + 方法名"来决定实参的解析方式。

核心逻辑在 `parseCallArgs` 中：

```ts
function parseCallArgs(callee: Expr): Expr[] {
  expect('(');
  const args: Expr[] = [];

  if (callee.kind === 'Member') {
    const isEntityCall = isEntityType(callee);
    const methodName = callee.prop;

    if (isEntityCall && methodName === 'where') {
      return parseWhereArgs();      // 查询条件语法
    }
    if (isQueryChain(callee)) {
      return parseChainMethodArgs(); // 链式方法语法
    }
  }

  // 普通调用
  while (!check(')')) {
    args.push(parseAdditive());
    if (check(',')) advance();
  }
  expect(')');
  return args;
}
```

三种形态：

| 形态 | 触发条件 | 实参解析策略 |
|------|---------|-------------|
| 普通调用 | 其他 | `parseAdditive`（标准表达式，不含比较/逻辑层） |
| where | 接收者是实体 + 方法名 `where` | `parseWhereArgs`（`field op value` 三元结构） |
| 链式 | 接收者是查询链 | `parseChainMethodArgs`（orderBy 方向、page/limit 参数） |

### where 条件解析

```ts
function parseWhereArgs(): Expr[] {
  const conds: Expr[] = [];
  while (!check(')')) {
    // 用 parseAdditive 而非 parseExpr 解析条件——
    // 防止 parseExpr 把 && 或 ) 吞进值的表达式里
    conds.push(parseWhereCondition());
    if (check(',')) advance();
  }
  expect(')');
  return conds;
}
```

`parseWhereCondition` 的关键决策是**使用 `parseAdditive` 而非完整的 `parseExpr`**。为什么？

因为条件的右值可能包含比较运算符（`total >= 0`），如果用 `parseExpr`（完整优先级层），`parseExpr` 会尝试把 `&&`、`||` 等逻辑运算符也解析进右值。但 `where(total > 0, status = 'A')` 中的逗号是**条件的分隔符**——右值的解析必须停在逗号或右括号处。

`parseAdditive` 只解析加减乘除层（不含比较和逻辑），右值的终止条件刚好能停在逗号/右括号处。这是"用语法层级的自然边界替代显式终止条件"的经典技巧。

条件内的 `&&`/`||` 组合通过递归处理：

```ts
function parseWhereCondition(): Expr {
  let left = parseWhereAtom();   // field op value
  while (check('&&') || check('||')) {
    const op = advance().value;
    const right = parseWhereAtom();
    left = { kind: 'Binary', operator: op, left, right };
  }
  return left;
}
```

### 链式方法解析

`Order.where(...).orderBy(...)` 这类链式调用是另一个特殊形态。`orderBy` 的参数是 `field asc|desc`——其中 `asc`/`desc` 是方向**关键字**，不是普通标识符。

```ts
function parseChainMethodArgs(): Expr[] {
  const args: Expr[] = [];
  while (!check(')')) {
    const arg = parseIdent();   // 字段名
    args.push(arg);
    // 方向参数 desc/asc
    if (check('desc') || check('asc')) {
      args.push(parseIdent());  // 解析为 Ident 节点
    }
    if (check(',')) advance();
  }
  expect(')');
  return args;
}
```

有趣的是，`desc`/`asc` 在 AST 中被存储为 `Ident` 节点而非字符串字面量。codegen-java 的 `extractOrderBy` 函数会检查参数的类型——如果参数是 `Ident` 且值等于 `desc`/`asc`，就识别为方向。

## 5.3 查询链的递归判定：isQueryChain

parser 如何判断一个调用"C 是链式方法调用"？答案是递归地检查 C 的接收者是否是查询链的组成部分：

```ts
function isQueryChain(expr: Expr): boolean {
  if (expr.kind !== 'Call') return false;
  if (expr.callee.kind !== 'Member') return false;
  const method = expr.callee.prop;
  return (
    method === 'where' || method === 'orderBy' || method === 'page' ||
    method === 'limit' || method === 'groupBy' || method === 'aggregate'
  ) && (isQueryChain(expr.callee.obj) || isEntity(expr.callee.obj));
}
```

这个判定是**递归**的：`Order.where(...).orderBy(...).page(...)` 的最外层调用是 `page`，`page` 的接收者是 `Order.where(...).orderBy(...)`，而后者本身是一个调用（`orderBy`），`orderBy` 的接收者是 `Order.where(...)`，`where` 的接收者是 `Order`——最终回到实体。任何一个环节的判断失败都会让整个链式判定失败。

这个递归判定之所以重要，是因为它让 parser 在**不知道实体类型**的情况下就能识别查询链——parser 不需要符号表（那是 linkApp 阶段的事），只需要语法层面的递归检查。

## 5.4 JSX 子集解析

TDSL 的 `page` 声明使用 JSX 子集语法：

```
page OrderList {
  <table dataSource={useQuery('listOrders')}>
    <column field="id" />
    <column field="customer" />
    <button text="详情" action={navigate('OrderDetail', row.id)} />
  </table>
}
```

parser 对 JSX 子集的处理是"**结构化的标签解析**"——每个 `<tag attrs>children</tag>` 或 `<tag attrs />` 被解析为一个 `ViewElementNode`。实现（`parseViewElement`）：

```ts
private parseViewElement(): ViewElementNode {
  this.expect('<');
  const type = this.expectIdent();
  const props: Record<string, Expr | string> = {};
  const bindings: BindingNode[] = [];

  // 属性：attr="str" | attr={expr}
  while (this.peek().value !== '>' && this.peek().value !== '/') {
    const attrName = this.expectIdent();
    this.expect('=');
    if (this.peek().value === '{') {
      this.next();
      const e = this.parseExpr();       // 花括号里是表达式
      this.expect('}');
      props[attrName] = e;
      const binding = extractBinding(e); // 提取 useQuery/useMutation/... 绑定
      if (binding) bindings.push(binding);
    } else {
      props[attrName] = this.expectString();  // 普通字符串属性
    }
  }

  const children: ViewElementNode[] = [];
  if (this.peek().value === '/') {
    this.next(); this.expect('>');       // 自闭合标签 <tag ... />
  } else {
    this.expect('>');
    // 跳过文本节点（如按钮文字），直到子元素
    while (this.peek().value !== '<' && this.peek().value !== '<eof>') this.next();
    while (this.peek().value === '<' && this.peekAfter().value !== '/') {
      children.push(this.parseViewElement());
    }
    // 闭合标签 </tag> —— 校验标签名匹配
    this.expect('<'); this.expect('/');
    const closeTag = this.expectIdent();
    if (closeTag !== type) this.fail(`mismatched closing tag '${closeTag}', expected '${type}'`);
    this.expect('>');
  }
  return { ...createNode('ViewElement'), type, props, bindings, children };
}
```

关键设计决策：

1. **属性值是表达式 AST 而非字符串**。`dataSource={useQuery('listOrders')}` 中的 `useQuery('listOrders')` 被解析为一棵 `Call` 表达式树。这使 codegen-react 能够分析绑定语义。注意属性有两种形态——`{expr}` 和 `"str"`（`props` 的记录类型是 `Expr | string`）。

2. **Binding 是属性表达式的"投影"**。`extractBinding` 检查属性值表达式是不是 `useQuery(...)` / `useMutation(...)` / `navigate(...)` / `openDialog(...)` 调用。如果是，就提取出一个 `BindingNode`。这样 `props` 充当"原始语法"，`bindings` 数组充当"语义索引"——codegen 可以直接遍历 `bindings` 而不用重新分析属性表达式。

3. **文本节点被跳过**。`<button text="详情">` 的 `text` 是属性，不是子文本节点。子元素之间的空白/文本被 `while` 循环跳过，直到遇到 `<`。这让 `<table>` 里夹着的换行缩进不会干扰子元素的解析。

4. **闭合标签名与开始标签名校验**。`parseViewElement` 在 `</tag>` 处校验 `closeTag === type`，不匹配直接报 `mismatched closing tag`——这避免了未闭合/错配标签在生成 React 时产生难以定位的 DOM 错误。

## 5.5 dependency 声明的复杂语法

```
dependency java "com.alibaba:fastjson2:2.0.58" import { JSON, JSONObject };
dependency java "g:a" as jackson;
dependency npm "antd@^5.21.0";
dependency npm "echarts-for-react" import ECharts;
dependency npm "@ant-design/charts" import { Pie, Bar };
```

这个语法比 TDSL 其他声明复杂得多——它有生态类型（java/npm）、坐标（Maven 坐标或 npm 包名）、命名空间（as）、import 列表（含默认导入和具名导入）四种可选成分。

parser 的处理是一个"可选后缀链"：

```ts
function parseDependency(): DependencyNode {
  const kind = parseIdent();  // 'java' | 'npm'
  const coord = parseString();
  const { name, version } = splitCoordinate(kind, coord);

  let ns: string | undefined;
  let imports: { name: string; alias?: string }[] | undefined;
  let importDefault: string | undefined;

  // 可选后缀：as ns
  if (match('as')) ns = parseIdent();

  // 可选后缀：import X | import { A, B as C }
  if (match('import')) {
    if (check('{')) {
      imports = parseNamedImports();  // { A, B as C }
    } else {
      importDefault = parseIdent();   // import X
    }
  }
  expect(';');

  return { kind: 'Dependency', eco: kind, name, version, ns, imports, importDefault };
}
```

**坐标切分**：`splitCoordinate` 根据生态类型做不同的切分：

```ts
function splitCoordinate(eco: string, coord: string) {
  if (eco === 'java') {
    // "g:a:v" 三段，或 "g:a" 两段（版本缺省）
    const parts = coord.split(':');
    const [g, a] = parts;
    const version = parts.length >= 3 ? parts[2] : undefined;
    return { name: `${g}:${a}`, version };
  }
  // npm：按最后一个 @ 切 name/version，scoped 包名 @scope/ui 不受影响
  const at = coord.lastIndexOf('@');
  if (at > 0) {
    return { name: coord.slice(0, at), version: coord.slice(at + 1) };
  }
  return { name: coord, version: undefined };
}
```

npm 坐标切分有个陷阱：`@scope/ui@^1.0.0` 是合法的 scoped 包名带版本，其中 `@` 出现在中间。`lastIndexOf('@')` 保证不会误切 scoped 包名——切分发生在最后一个 `@`，而 scoped 包的 `@` 在开头。

## 5.6 @annotation 解析

`@pk`、`@export`、`@datasource('erp')` 这些注解需要一个通用的解析机制：

```ts
function parseAnnotations(): Annotation[] {
  const anns: Annotation[] = [];
  while (check('@')) {
    advance();
    const name = parseIdent();
    const args: Record<string, Expr> = {};
    expect('(');
    while (!check(')')) {
      const key = parseIdent();
      expect('=');
      const value = parseExpr();
      args[key] = value;
      if (check(',')) advance();
    }
    expect(')');
    anns.push({ name, args });
  }
  return anns;
}
```

`@datasource('erp')` 被解析为 `{ name: 'datasource', args: {} }`——等等，`@datasource('erp')` 中的 `'erp'` 是定位参数（positional），不是命名参数（named）。

TDSL 的注解解析实际上优雅地处理了这两种形态：`@service(kind='dubbo', group='user-center')` 使用命名参数，`@datasource('erp')` 使用定位参数。parser 在遇到 `ident` 后面跟着 `=` 时解析为命名参数，否则解析为定位参数。

## 5.7 linkApp：引用绑定

parser 做完语法分析后，得到的是一棵**裸 AST**——所有跨节点引用还是短名（`Order`、`createOrder`）。linkApp 阶段把这些短名换算成完整的 nodePath 字符串。

### 为什么需要 linkApp

裸 AST 中的引用是源码文本的直接映射：

```
entity Order { ... }
struct OrderInput { ... }
function createOrder(input: OrderInput): Order { ... }
```

在 `createOrder` 的 AST 中，`OrderInput` 和 `Order` 的类型引用路径是 `OrderInput`、`Order`——它们指向什么？哪个数据源？哪个文件？linkApp 的工作就是回答这些问题。

### linkApp 的策略

linkApp 接收裸 AST，返回绑定后的 AST（通常是原地修改，或者返回新对象）。它执行三类工作：

**1. 重名检测。** 同数据源内实体重名、全局概念（struct/enum/function/interface）重名，都会报错。这保证了 AST 中每个符号都有一个唯一的解析目标。

**2. 类型引用绑定（TypeRef）。** 每个 `TypeRef` 中的 `reference` 节点（如 `Order`、`OrderInput`）被替换为完整的 nodePath（如 `app.datasources.defaultDS.entities.Order`）。这里使用 `resolveShort`（短名解析）和 `resolveQualified`（限定名解析）两个函数——详见第 7 章。

**3. 行为引用绑定。** Endpoint 的 `logicRef`（REST 路径绑定的函数名）、Binding 的 `target`（页面绑定的函数/页面名）被替换为对应的 nodePath。如果引用指向不存在的目标，linkApp 报错。

### 一个具体的绑定流程

以下面的 TDSL 为例：

```
entity Order { id: Integer @pk; total: Decimal }

function getOrder(id: Integer): Order {
  return Order.get(id);
}

interface OrderApi {
  GET '/api/orders/{id}' -> getOrder
}
```

linkApp 的执行流程：

1. 遍历 `Order` 实体属性，`Integer`/`Decimal` 不绑定（primitive 类型直接可用）。
2. `getOrder` 的返回类型 `Order` 被绑定为 `app.datasources.defaultDS.entities.Order`。
3. `return Order.get(id);` 中的 `Order` 是个 `Call` 的接收者——`Order` 被识别为实体引用，但 `Order.get(...)` 本身是一个表达式，其"绑定"在 codegen 层完成（codegen-java 通过 `entityNameOfReceiver` 分析实体方法调用）。
4. `OrderApi` 的 `getOrder` 端点引用 `getOrder` 函数——`logicRef` 被绑定为 `app.logics.getOrder`。

### 悬空引用的处理

linkApp 在解析短名时，如果找不到目标（比如 `getOrder` 函数不存在），会抛出 `TdslSyntaxError` 或记录诊断。对于 TypeRef 引用，悬空会导致 typecheck 的"悬空引用"诊断；对于 Endpoint 引用，悬空会导致"绑定函数不存在"的语法错误。

**为什么一部分错误在 linkApp 就报，另一部分留给 typecheck？** 因为两类错误的"静态可判定性"不同：TypeRef 的悬空引用涉及全局命名空间（需要符号表，这是 typecheck 的领域）；而 Endpoint 的 `logicRef` 只涉及当前 app 的函数名（linkApp 完全掌握这个信息）。linkApp 能确定的错误就尽早报，可以减省 typecheck 的负担。
