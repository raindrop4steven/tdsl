# 第 2 章 语义核：Typed AST 的设计

> "一旦你选定了中间表示，编译器能做什么就已经被决定了大半。"

本章讨论 TDSL 编译器中最核心的设计决策：抽象语法树（AST）的类型系统。AST 不是 parser 的副产品——它是编译器所有阶段共享的合约。parser 产出它，typecheck 验证它，codegen 消费它。AST 的设计直接决定了语言的表达能力、校验的精确度、生成的灵活性。

## 2.1 AST 不是 Parse Tree

初学者常混淆抽象语法树（AST）和具体语法树（Parse Tree / Concrete Syntax Tree）。区别在于**保留了多少语法细节**。

一棵 Parse Tree 会保留源码中的所有语法结构。例如 `const x = 1 + 2;` 的 Parse Tree 大致是：

```
        Declaration
       /     |      \
  'const'   Name   Initializer
              |        |
             'x'    Expression
                   /    |     \
              Expr  '+'  Expr
               |         |
              1         2
```

括号、分号、关键字这些**语法噪音**全部保留。但编译器后续阶段不需要知道"1 + 2 是否用了括号"——它只需要知道"这是一个加法表达式，左操作数是 1，右操作数是 2"。

AST 砍掉了语法噪音，只保留语义骨架。`1 + 2` 在 AST 中表示为：

```
{ kind: 'Binary', operator: '+', left: { kind: 'Numeric', value: 1 }, right: { kind: 'Numeric', value: 2 } }
```

这个区别不仅仅是压缩——AST 承载的是**语义信息**而非语法信息。parser 的工作就是从 Parse Tree（或等价的 Token 流分析）中提取语义，产出 AST。

## 2.2 三种中间表示的比较

编译器设计中，中间表示（IR）的选择是最关键的架构决策。TDSL 考虑了三种方案：

### Untyped AST

最简单的 AST：节点没有类型信息，字段值是 `any` 或 `unknown`。JSON 天然适合表示这种 AST：

```json
{
  "kind": "Entity",
  "name": "Order",
  "properties": [
    { "kind": "Property", "name": "id", "type": "Integer" }
  ]
}
```

Untyped AST 的优点是灵活——任何工具都能用 JSON 操作它。缺点是**所有下游都必须防御性地校验结构**。codegen 读到一个 `EntityNode` 时，不知道它是否有 `properties` 字段、每个 property 是否有 `type`——它必须先做运行时断言。当 AST 结构有 19 种节点类型、每种 5-10 个字段时，这种防御性代码会膨胀到不可维护。

### JSON Schema 校验

在 Untyped AST 上叠加 JSON Schema 可以解决结构校验问题。但 JSON Schema 无法表达**跨字段约束**（如"entity 的 primary key 必须存在"）和**语义约束**（如"引用的类型必须已定义"）。这些约束需要在 typecheck 阶段用代码表达——而 JSON Schema 无法参与 TypeScript 的类型系统。

### Typed AST（TDSL 的选择）

每个节点有精确的 TypeScript 类型，字段类型在编译期确定：

```ts
interface EntityNode {
  kind: 'Entity';
  name: string;
  properties: EntityPropertyNode[];
}
```

Typed AST 的优势在于**类型系统驱动开发**。当 `types.ts` 中的类型定义改变时，TypeScript 编译器会强制所有消费端（parser、typecheck、codegen-java、codegen-react）同步更新。如果 codegen 的某个 `switch` 分支没有处理新的节点类型，编译直接报错——不需要运行测试，不需要人工 review。

这个优势的代价是：`types.ts` 成了整个系统的 SSoT。任何对 AST 结构的修改都从这里开始，波及所有下游。但这个"波及"被编译器自动化了——你只需要跟着 TypeScript 的错误提示一路改完，就能确保所有阶段的同步。

## 2.3 节点的统一基座

所有 TDSL AST 节点共享一个基座接口：

```ts
interface BaseNode {
  kind: string;     // 类型标签，用于判别联合的收窄
  id: string;       // 全局唯一 ID（用于生成器追踪）
  annotations?: Annotation[];  // 语义注解（@pk, @nullable, @export 等）
  file?: string;    // M7 多文件工程：该节点来自哪个分片
}
```

三个字段各有深意。

**`kind` 是类型标签而非运行时字符串。** 在 `switch (node.kind)` 之后，TypeScript 可以将 `node` 的类型收窄为对应的接口。这不是字符串比较——它是 TypeScript 编译器的类型推导机制。`kind` 的值是字面量类型（如 `'Entity'`、`'Logic'`），不是 `string`。这保证了 switch 的每个分支中，编译器都知道 `node` 的精确类型。

**`id` 用于生成器追踪。** codegen 在生成代码时需要追踪"这个 AST 节点对应生成文件的哪个位置"。`id` 是一个全局唯一的字符串（由 parser 在构建 AST 时分配），它使得生成器可以在不依赖对象引用的情况下标识节点。

**`annotations` 是语义注解的扩展点。** `@pk`（主键）、`@nullable`（可空）、`@export`（导出）这些信息不改变节点的结构类型，但影响 codegen 的行为。它们被挂在 `annotations` 数组上，而不是作为节点的独立字段——这样新增注解不需要修改节点的接口定义。

**`file` 是多文件工程的溯源标记。** 当 `parseProject` 合并多个分片时，每个顶层声明节点会被打上来源文件的标记。typecheck 在报诊断时可以反查这个标记，把错误定位到具体的分片文件。

## 2.4 判别联合与 `never` 穷尽

TDSL 的 AST 用 TypeScript 的**判别联合**（Discriminated Union）定义。这是整本书最重要的语言特性——理解它就理解了 TDSL 编译器为什么能在编译期保证正确性。

### 什么是判别联合

判别联合是一组共享同一个字段（判别字段）的接口的联合类型。每个接口的判别字段是不同的字面量类型：

```ts
type Shape =
  | { kind: 'circle'; radius: number }
  | { kind: 'rectangle'; width: number; height: number }
  | { kind: 'triangle'; base: number; height: number }
```

`Shape` 类型的变量在 `switch (s.kind)` 之后，TypeScript 会自动收窄：

```ts
function area(s: Shape): number {
  switch (s.kind) {
    case 'circle':
      return Math.PI * s.radius * s.radius;  // s.radius 已知存在
    case 'rectangle':
      return s.width * s.height;              // s.width, s.height 已知存在
    case 'triangle':
      return 0.5 * s.base * s.height;         // s.base, s.height 已知存在
  }
}
```

在每个 `case` 分支中，`s` 的类型自动收窄为对应的接口——访问 `s.radius` 不需要类型断言，编译器知道它存在。

### `never` 类型与穷尽性检查

`never` 是 TypeScript 中"不可能存在的值"的类型。当一个变量的所有可能类型都已被 `switch` 分支处理后，它的类型收窄为 `never`：

```ts
function area(s: Shape): number {
  switch (s.kind) {
    case 'circle':
      return Math.PI * s.radius * s.radius;
    case 'rectangle':
      return s.width * s.height;
    // 假设忘了处理 'triangle'
  }
  // s 的类型是 never，不是 Shape
}
```

利用这个特性，可以在 switch 之后放一个赋值来触发编译期检查：

```ts
function area(s: Shape): number {
  switch (s.kind) {
    case 'circle':
      return Math.PI * s.radius * s.radius;
    case 'rectangle':
      return s.width * s.height;
    case 'triangle':
      return 0.5 * s.base * s.height;
  }
  // 如果所有 case 已处理，s 到这里是 never
  // 如果漏了某个 case，s 到这里是 Shape（不是 never），赋值给 never 会报错
  const _exhaustive: never = s;
  return _exhaustive;
}
```

这就是 TDSL 编译器中无处不在的 `const _exhaustive: never = x` 模式。它的含义是：**如果我新增了一个 AST 节点类型但忘了在这里处理它，TypeScript 编译器会在编译期告诉我**。

### 在 codegen 中的应用

codegen-java 和 codegen-react 的核心是一系列 `switch` 语句，每个都以 `const _never: never = x` 结尾。例如在 `type-map.ts`（类型映射）中：

```ts
export function javaType(tr: TypeRef): string {
  switch (tr.kind) {
    case 'primitive':
      switch (tr.builtin) {
        case 'Boolean': return 'Boolean';
        case 'Integer': return 'Long';
        case 'Decimal': return 'java.math.BigDecimal';
        // ...
      }
      break;
    case 'reference':
      return typeNameFromPath(tr.path);
    case 'generic':
      // ...
      break;
    case 'db':
      return 'java.math.BigDecimal';
  }
  const _never: never = tr;
  return _never;
}
```

这段代码保证了：如果 `TypeRef` 新增了一种形态（比如未来加 `Union` 类型），`javaType` 函数会在编译期报错，而不是在运行时返回 `undefined`。

## 2.5 节点全家福

TDSL 的 AST 以 `AppNode` 为根，按领域聚合成八类子节点。我们按层次展开。

### 聚合根：AppNode

```ts
interface AppNode {
  kind: 'App';
  name: string;
  datasources: DataSourceNode[];    // 数据源（M1 命名空间的载体）
  structures: StructureNode[];      // DTO / 嵌套结构
  enums: EnumNode[];                // 枚举
  logics: LogicNode[];              // 业务逻辑
  interfaces: InterfaceNode[];      // REST 契约
  views: ViewNode[];                // 页面声明
  services: ServiceNode[];          // 外部服务（dubbo/http）
  dependencies: DependencyNode[];   // 依赖声明（java/npm）
}
```

`AppNode` 是整棵 AST 的根节点。所有 codegen 都从这个根开始遍历。它的八个数组字段对应 TDSL 的八种顶层声明（数据源/结构/枚举/逻辑/接口/视图/服务/依赖）。

**为什么用数组而不是映射？** 因为 AST 需要保持声明顺序——TDSL 中 entity 的声明顺序会影响后续代码的可读性（虽然不影响语义）。数组天然保序，映射不保序。

**为什么 `name` 是字符串而不是标识符节点？** 因为 app 名称只在 codegen 时用于生成包名（`com.<name>`），不需要在 AST 层面做语义分析。过度建模（over-engineering）是 AST 设计中常见的陷阱——不是所有源码结构都需要精确的 AST 表示。

### 持久化模型：Entity

```ts
interface EntityNode {
  kind: 'Entity';
  name: string;
  table?: string;                    // 自定义表名（默认 lowercase 实体名）
  properties: EntityPropertyNode[];
}

interface EntityPropertyNode {
  kind: 'EntityProperty';
  name: string;
  label?: string;                    // 显示标签（中文名）
  type: TypeRef;                     // 类型引用（见 §2.6）
  primary?: boolean;                 // @pk 主键
  nullable?: boolean;                // @nullable 可空
  unique?: boolean;                  // @unique 唯一约束
}
```

Entity 是 TDSL 中最重要的领域概念——它直接映射到 JPA 实体和数据库表。`primary`、`nullable`、`unique` 三个布尔标记是数据完整性的 AST 表示——它们在 codegen 中分别生成 `@Id`、`@Column(nullable=true)`、`@Column(unique=true)`。

**为什么标记是可选的布尔而非必填？** 因为"没有标记"有默认语义：非 primary、非 nullable、非 unique 是绝大多数字段的常态。如果要求每个字段都显式标注 `primary=false`，源码会变得冗长。可选字段配合 `?? false` 的默认值处理，在保持语义清晰的同时减少了书写负担。

### 业务逻辑：Logic

```ts
interface LogicNode {
  kind: 'Logic';
  name: string;
  params: ParamNode[];
  returns: ReturnNode[];
  body: Statement[];
}

interface ParamNode {
  kind: 'Param';
  name: string;
  type: TypeRef;
}

interface ReturnNode {
  kind: 'Return';
  name?: string;
  type: TypeRef;
}
```

Logic 是 TDSL 中"会做事"的部分——它对应 Java 的 Service 方法和 TDSL 源码中的 `function`。`body` 是语句数组（`Statement[]`），每个语句是一个控制流结构（`VarDecl`、`If`、`ForEach`、`Return` 等）。

**为什么返回值用 `ReturnNode[]` 而不是单个 `TypeRef`？** 因为 TDSL 允许多返回值的扩展（虽然当前只用一个）。更重要的是，`ReturnNode` 是一个节点而非裸类型——它需要 `id`（继承自 BaseNode）以便 codegen 追踪。

### REST 契约：Interface

```ts
interface InterfaceNode {
  kind: 'Interface';
  name: string;
  endpoints: EndpointNode[];
}

interface EndpointNode {
  kind: 'Endpoint';
  method: 'GET' | 'POST' | 'PUT' | 'DELETE';
  path: string;
  name: string;
  logicRef?: string;    // nodePath 到 LogicNode（由 linkApp 绑定）
}
```

Interface 将 Logic 暴露为 HTTP 端点。`logicRef` 存储的是 nodePath 字符串（如 `app.logics.createOrder`），由 parser 的 linkApp 阶段绑定。如果 `logicRef` 指向的 Logic 不存在，linkApp 会报错。

**为什么 `logicRef` 是字符串而非对象引用？** 因为 AST 需要可序列化。字符串引用使得 AST 可以被 JSON 序列化/反序列化，可以被 diff 工具比较，可以被 LLM 按路径定点修改。对象引用会破坏这些能力。

### 页面声明：View

```ts
interface ViewNode {
  kind: 'View';
  name: string;
  viewKind: 'page' | 'dialog' | 'block';
  elements: ViewElementNode[];
}

interface ViewElementNode {
  kind: 'ViewElement';
  type: string;                    // 组件类型：'table' | 'column' | 'button' | 'form' | ...
  props: Record<string, Expr | string>;  // 属性：{expr} 是表达式，"" 是字符串
  bindings: BindingNode[];         // 数据绑定
  children: ViewElementNode[];     // 子元素
}

interface BindingNode {
  kind: 'Binding';
  name: string;      // 'useQuery' | 'useMutation' | 'navigate' | 'openDialog'
  target: string;    // nodePath 到 Logic 或 View（由 linkApp 绑定为完整路径）
  args: Expr[];
}
```

View 是 TDSL 区别于传统 DSL 的独特设计——它用 JSX 风格的语法声明前端页面，然后由 codegen-react 翻译成 React 组件。

`ViewElementNode` 的 `props` 值有两种形态：`attr={expr}`（表达式 AST）和 `attr="str"`（字符串）。`dataSource={useQuery('listOrders')}` 中的 `useQuery('listOrders')` 是一棵子 AST 而非字符串——codegen 可以分析这棵子 AST 来生成 hooks 代码。

`BindingNode` 的 `target` 是 nodePath 字符串（指向 Logic 或 View），由 linkApp 绑定为完整路径。这保证了页面绑定的可检查性——typecheck 可以验证 `useQuery('createOrder')` 指向的 Logic 确实存在。

### 外部服务：Service

```ts
interface ServiceNode {
  kind: 'Service';
  name: string;
  kind_: 'dubbo' | 'http';
  config: Record<string, string>;   // group, version, baseUrl 等
  operations: ServiceOperationNode[];
}
```

`kind_` 字段（注意下划线）与节点的 `kind` 判别字段做了区分——`kind_` 是服务的子类型，不是 AST 节点的类型标签。这种命名约定在 TDSL 中用于区分"节点判别"和"节点内分类"。

### 依赖声明：Dependency

```ts
interface DependencyNode {
  kind: 'Dependency';
  eco: 'java' | 'npm';
  name: string;           // Maven 坐标 "g:a" 或 npm 包名
  version?: string;       // 版本号（可选，npm 带版本范围）
  ns?: string;            // 命名空间别名（as ns）
  imports?: Array<{ name: string; alias?: string }>;  // import 列表
  importDefault?: string; // 默认导出（npm）
}
```

Dependency 是 TDSL 与外部生态的桥梁。`eco` 区分 Java（进 pom.xml）和 npm（进 package.json）。`imports` 字段记录显式导入的类/组件——如果未声明 imports，则产物全量兼容（D-dep-2 warning）。

这个设计体现了"声明驱动"的理念：编译器不猜测你想用什么库，你必须显式声明依赖和导入。typecheck 会在使用了未声明的库时报 D-dep-1 error。

## 2.6 TypeRef：类型的四种形态

类型引用（TypeRef）是 TDSL 类型系统的核心。它有四种形态：

```ts
type TypeRef =
  | { kind: 'primitive'; builtin: BuiltinType }
  | { kind: 'reference'; path: string }
  | { kind: 'generic'; name: 'List' | 'Map' | 'Page'; args: TypeRef[] }
  | { kind: 'db'; builtin: string; args?: Record<string, unknown> };
```

### Primitive：语言内建类型

```ts
type BuiltinType = 'String' | 'Integer' | 'Decimal' | 'Boolean' | 'Date' | 'DateTime' | 'Time';
```

这七个类型是 TDSL 的**领域类型**，不是 JavaScript 的类型。`Integer` 不是 `number`（JS 的 number 是浮点数），`String` 不是 `string`（JS 的 string 没有 `trim` 方法的编译期检查）。每个 primitive 在 FFI 目录中映射到对应的 Java 类型（`Integer → Long`、`Decimal → BigDecimal`）。

**为什么不直接用 JavaScript 的类型名？** 因为 TDSL 需要与 Java 对齐。`Integer` 映射到 `Long`（Java 的 64 位整数），而 `number` 在 JS 中是双精度浮点——两者语义不同。使用领域类型名避免了语义混淆。

### Reference：跨节点引用

```ts
{ kind: 'reference'; path: string }
```

`path` 是 nodePath 字符串，如 `app.datasources.defaultDS.entities.Order`。它指向 AST 中的另一个节点（Entity、Structure、Enum 等）。

reference 是 TDSL 处理跨节点引用的核心机制。源码中的 `Order` 类型在 linkApp 阶段被绑定为完整的 nodePath。后续的 typecheck 和 codegen 都通过 `resolve(app, path)` 函数查找被引用的节点。

### Generic：参数化类型

```ts
{ kind: 'generic'; name: string; args: TypeRef[] }
```

TDSL 支持三种泛型：`List<T>`（列表）、`Map<K,V>`（映射）、`Page<T>`（分页）。`name` 是泛型名称，`args` 是类型参数。

`List` 是最常用的泛型——实体查询的结果类型就是 `List<Entity>`。`Page` 是 Spring Data 的分页结果，只在 codegen-java 中使用（React 端用普通数组处理分页数据）。

### Decimal(p,s)：带精度的数值

```ts
{ kind: 'db'; builtin: 'decimal'; args: { precision: number; scale: number } }
```

`Decimal(10,2)` 被 parser 解析为 `{ kind: 'db', builtin: 'decimal', args: { precision: 10, scale: 2 } }`——它携带精度信息，映射到 Java 的 `BigDecimal` 和数据库的 `DECIMAL(10,2)`。`precision` 是总位数，`scale` 是小数位数。注意裸写的 `Decimal`（不带括号）是 `primitive` 形态，只有带精度参数才是 `db` 形态。

`db` 这个 kind 名称来源于"database type"——这种类型最终映射到数据库列定义，不只是 Java 类型。类型系统因此跨越了三个层面（DSL → Java → SQL），类型引用需要携带足够的信息以支持所有层面的代码生成。`args` 是一张通用记录表，未来新增 `VARCHAR(n)` 这类带参数的库类型时，不需要改动 `TypeRef` 的联合定义。

## 2.7 表达式与语句的边界

TDSL 将"能产生值"的结构和"能产生副作用"的结构严格分离：

### 表达式（Expr）

```ts
type LiteralExpr =
  | { kind: 'Bool'; value: boolean }
  | { kind: 'Numeric'; value: number }
  | { kind: 'String'; value: string }
  | { kind: 'Null' };

type Expr =
  | { kind: 'Ident'; name: string }
  | { kind: 'Member'; obj: Expr; prop: string }
  | { kind: 'Call'; callee: Expr; args: Expr[] }
  | { kind: 'New'; type: TypeRef; args: Expr[] }
  | { kind: 'NewList'; elem: TypeRef; items: Expr[] }
  | LiteralExpr
  | {
      kind: 'Binary';
      operator:
        | '===' | '!==' | '&&' | '||'
        | '+' | '-' | '*' | '/'
        | '<' | '<=' | '>' | '>='
        | '=' | 'like' | 'in';
      left: Expr; right: Expr;
    }
  | { kind: 'Group'; expr: Expr };
```

表达式是**有值的**：`1 + 2` 的值是 `3`，`order.total` 的值是一个 Decimal。表达式**不产生副作用**——调用 `order.save()` 不是表达式（它是 `CallStmt` 语句），因为 `save()` 会修改数据库。

值得留意两个细节：

- **`Binary` 的运算符集合里藏着查询语言的痕迹**：`=`、`like`、`in` 不是普通编程语言常见的比较符，它们是 TDSL 查询 DSL 的产物——`where(name = '张三')`、`where(name like '张%')`、`where(id in [1,2,3])` 都复用同一个 `Binary` 节点。查询条件和普通表达式共用一种 AST 形态，这是 §2.8 要讨论的"AST 中性"策略的基础。
- **没有 `Index`（下标访问）节点**。TDSL 有意不提供 `list[0]` 这样的下标语法——列表访问一律通过 FFI 方法（如 `get(0)`）完成，这让 codegen 不需要处理下标越界语义，也减少了 AST 形态。

**为什么禁止赋值和自增作为表达式？** 在 C/Java 中，`x = 5` 和 `x++` 都是表达式（它们有值）。但 TDSL 选择把赋值限制为语句——这消除了 `if (x = 5)` 这类常见 bug，也简化了 codegen：表达式翻译不需要处理副作用。

### 语句（Statement）

```ts
type Statement =
  | { kind: 'VarDecl'; name: string; type?: TypeRef; init?: Expr }
  | { kind: 'Assign'; target: Expr; value: Expr }
  | { kind: 'Return'; value?: Expr }
  | { kind: 'If'; cond: Expr; then: Statement[]; else?: Statement[] }
  | { kind: 'ForEach'; item: string; container: Expr; body: Statement[] }
  | { kind: 'CallStmt'; call: Expr }
  | { kind: 'Throw'; message: Expr };
```

语句是**有副作用的**：`VarDecl` 声明变量，`Assign` 修改变量，`Return` 终止函数，`ForEach` 循环执行、`Throw` 抛出异常。语句**不产生值**（除了 `Return` 的值用于函数返回）。

TDSL 的语句集合出奇地小——只有七种。作为对比，Java 有声明、表达式、if、while、do-while、for、增强 for、switch、break、continue、return、try、throw 等十余种语句。TDSL 刻意砍掉了循环的多种形态（`while`、`for`、`break`、`continue` 都不存在）：

- **`for-of` 是唯一的循环**，且必然遍历"集合"（`ForEach` 的 `container` 字段是 Expr）。codegen 拿到 `ForEach` 就知道要生成 `for (X item : collection)`。
- **没有 `break`/`continue`**。产物不再需要标签和跳转分析。
- **`throw` 是最小的异常面**（G2/A1 表达式域定稿），用于 agent 生成代码时的显式错误，不涉及 try-catch——异常处理留给宿主语言。

这个分离在 codegen 中体现为两个不同的翻译函数：`genExpr` 处理表达式，`genStatement` 处理语句。两者不会互相调用（除了 `VarDecl` 的初始化表达式和 `Return` 的返回值表达式）。

## 2.8 查询 DSL 的 AST 表示

TDSL 的查询语言（`Order.where(total > 0).orderBy(total desc)`）是一个语法上的创新——它把数据库查询嵌入了普通函数调用语法中。

在 AST 层面，查询表达式就是普通的 `Call` 节点：

```
Call {
  callee: Member {
    obj: Call {
      callee: Member {
        obj: Ident('Order'),
        prop: 'where'
      },
      args: [Binary { op: '>', left: Ident('total'), right: Numeric(0) }]
    },
    prop: 'orderBy'
  },
  args: [Ident('total'), Ident('desc')]
}
```

`Order.where(...)` 是一个 `Call`（`callee` 是 `Member`，`prop` 是 `where`），`.orderBy(...)` 是外层的另一个 `Call`（`callee` 是前一个 Call 的 Member 形式）。

这个设计的关键在于：**AST 不感知"这是查询"**。查询的语义在 codegen 中被识别——codegen-java 扫描所有函数中的 `Call` 节点，识别出 `X.where(...)` 模式，将其收集为 `QuerySpec`（查询规格），然后生成对应的 Repository 方法。

这种"AST 中性、codegen 识别"的策略避免了在 AST 中引入专门的查询节点——减少了 AST 的复杂度，但增加了 codegen 的分析负担。对于 TDSL 这种查询形态有限的语言，这是一个合理的权衡。

## 2.9 nodePath 寻址

TDSL 中所有跨节点引用都以**字符串路径**存储，而非对象指针。这种设计称为"nodePath 寻址"。

### 什么是 nodePath

nodePath 是一个以点号分隔的路径字符串，从 App 根节点开始，沿着 AST 的数组字段逐级定位到目标节点：

```
app.datasources.defaultDS.entities.Order       → EntityNode
app.logics.createOrder                         → LogicNode
app.interfaces.OrderApi.endpoints[0]           → EndpointNode
```

### 为什么用字符串而非指针

三种权衡：

1. **可序列化**：字符串引用可以被 JSON 序列化。这意味着 AST 可以被写入文件、通过网络传输、被 LLM 读取和修改。对象指针在序列化后会丢失。

2. **可 diff**：两个 AST 的差异可以用字符串路径精确描述——"路径 A 处的节点不同"。这对于多文件工程的合并和对拍至关重要。

3. **可定点修复**：LLM 修复管线可以根据诊断中的 `path` 字段，精确定位到出错节点并生成修正文本。如果用对象指针，LLM 无法"看到"引用关系。

### `collectPaths()` 与 `resolve()` 函数

TDSL 的 nodePath 查询是基于 `path.ts` 中的 `collectPaths` 实现的——它一次性遍历整棵 AST，把每个节点展开为一条 `{ path, node }` 记录（PathEntry），返回一个扁平列表：

```ts
export function collectPaths(app: AppNode): PathEntry[] {
  const entries: PathEntry[] = [{ path: 'app', node: app }];
  for (const ds of app.datasources) {
    entries.push({ path: `app.datasources.${ds.name}`, node: ds });
    for (const ent of ds.entities) {
      entries.push({ path: `app.datasources.${ds.name}.entities.${ent.name}`, node: ent });
      for (const prop of ent.properties) {
        entries.push({ path: `app.datasources.${ds.name}.entities.${ent.name}.properties.${prop.name}`, node: prop });
      }
    }
  }
  // ... structures / enums / logics / interfaces / views / services 同理
  return entries;
}
```

注意路径段的风格差异：**具名段用名字**（`app.datasources.erp.entities.Order`），**数组段用下标**（`app.interfaces.OrderApi.endpoints[0]`、`app.views.OrderList.elements[0]`）。因为名称在声明中是唯一的，名字本身就是导航的依据；而 `returns`、`endpoints`、`elements` 这类列表里的元素没有名字，只能按位置寻址。

`resolve` 和 `nodePathOf` 都是在这个扁平列表上做线性扫描：

```ts
export function resolve<T extends BaseNode>(app: AppNode, path: string): T | null {
  const hit = collectPaths(app).find((e) => e.path === path);
  return (hit?.node as T | undefined) ?? null;
}

export function nodePathOf(app: AppNode, target: BaseNode): string | null {
  return collectPaths(app).find((e) => e.node.id === target.id)?.path ?? null;
}
```

`resolve` 的返回值是 `T | null`——如果路径无效（悬空引用），返回 null。typecheck 拿到 null 后报告诊断。`nodePathOf` 通过 `id` 反查节点（`BaseNode.id` 全局唯一，见 §2.3），供诊断报告使用：typecheck 发现错误节点后调用它取得路径，放入 `Diagnostic.path` 字段。

**为什么用"每次全量扫描"而不是维护索引？** 因为 AST 是不可变的数据快照——编译流水线里 AST 建好后不会被增量修改（修改只会重新 parse）。每次遍历构建的列表与当前 AST 永远一致，不需要处理"索引失效"问题。代价是每次 `resolve` 都是 O(n)：对几百个节点的应用 AST 这是几十微秒的运算，完全可接受。这是一个很典型的工程权衡：**为简单性付出常数级性能，换取正确性保证**。

## 2.10 SSoT 保证

Typed AST 是 TDSL 的**唯一事实来源**（Single Source of Truth）。这个保证在实践中意味着：

1. **没有隐藏状态**：AST 中没有"编译器自己加的临时字段"或"codegen 留下的缓存"。每个字段都是从源码中解析出来的。

2. **没有平行表示**：不存在"AST 的 JSON 版本"或"AST 的简化版本"。所有下游都消费同一棵 AST 对象树。

3. **修改路径唯一**：要修改 TDSL 的语义（比如新增一种语句类型），修改路径是：
   - `types.ts`：新增节点接口
   - `parser.ts`：新增解析逻辑
   - `typecheck/index.ts`：新增校验规则
   - `codegen-java/index.ts`：新增生成逻辑
   - `codegen-react/index.ts`：新增生成逻辑（如果前端需要）

   TypeScript 编译器会确保这五处修改的一致性——如果 `types.ts` 新增了节点但 codegen 的 switch 没处理，编译直接报错。

4. **单测锁定**：每个包的单测都直接构造或解析 AST 对象，验证特定行为。修改 AST 结构后，所有相关单测的 TypeScript 编译会先报错，提醒你更新测试数据。

这个 SSoT 保证是 TDSL 编译器可靠性的根基。它不依赖开发者的自觉——它被 TypeScript 的类型系统**机械化地**执行。
