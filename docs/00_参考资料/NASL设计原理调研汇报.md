# NASL 设计原理调研汇报

---

## 一句话说清 NASL 是什么

**NASL 就是网易低代码平台用来"描述一个应用长什么样"的一套规则。**

它不直接写代码，而是先把"你要做的应用"用一套规范化的方式描述清楚，
再由平台把这套描述**自动翻译成真正能跑的前后端代码**。

---

## 为什么不能直接让 AI 写代码

低代码平台最大的难题是：**实施项目的人大多不会写代码，却最终要面对"代码"。**

如果让 AI 直接生成一段一段的代码，会面临一串现实问题：

1. **看不懂、没法核对** —— 实施的人不写代码，AI 生成的代码摆在那，他也看不懂对不对、有没有问题。
2. **不可控** —— 同样的需求，AI 每次生成的可能都不一样；改一点需求，结果可能面目全非，难以预测。
3. **不好改** —— 需求变更是常态，可让不写代码的人去改 AI 生成的代码，基本改不动、也不敢改。
4. **没法检查** —— 生成的代码对不对、安不安全，靠人肉看代码根本看不出来，出错难定位。
5. **不可复用** —— 每个项目都是"一次性生成"，经验、模板、公共逻辑无法沉淀和复用，越做越累。

**结论**：让实施人员直接面对"代码"，这条路的门槛和风险都很高。
所以需要一个中间层，把"人描述需求"和"最终代码"隔开。

---

## 它解决的核心问题

NASL 的答案，就是在"描述"和"代码"中间，加一层**标准化的应用模型**：

```
人 / 大模型 描述应用
      │
      ▼
   标准化的应用模型（唯一的"事实依据"）
      │
      ▼
   自动翻译成 前端代码 + 后端代码
```

这样，实施人员面对的始终是"需求描述"，而不是"代码"。
代码由平台根据模型自动生成，一致、可控、可复用。

---

## 最小示例：他们（网易）是这么做的

下面用 NASL 的文本写法，展示"描述一个最简单的应用"长什么样。
就用"一个待办事项（Todo）应用"举例——最经典、最容易看懂。

> 说明：这只是**描述应用**的文本，不是最终代码。平台会把它翻译成真正的前后端代码。

### 第 1 步：定义"数据库里存什么"（实体）

```
// 一张"待办事项"表
entity Todo {
  id: Integer;        // 主键
  title: String;      // 标题
  done: Boolean;      // 是否完成
}
```

### 第 2 步：定义"页面提交什么"（数据结构）

```
// 新增待办时，前端提交的数据
struct TodoInput {
  title: String;
  done: Boolean;
}
```

### 第 3 步：定义"后端业务逻辑"（方法）

```
// 查"还没完成"的待办
logic findTodos(): List<Todo> {
  result := new List<Todo>();
  for (todo in Todo.all) {
    if (todo.done === false) {
      result.add(todo);
    }
  }
  return result;
}
```

### 第 4 步：定义"页面长什么样"（前端）

```
page TodoList {
  <table dataSource={useQuery('Todo.findTodos')}>   // 表格数据来自上面的 findTodos
    <column field="title" />
    <column field="done" />
  </table>
}
```

### 关键点

- 你**只描述"要什么"**（有哪些表、什么逻辑、什么页面），**不用写 SQL、不用写 Java、不用写前端组件**。
- 一个待办应用，**大约 4 小段描述**就够了。
- 平台把这 4 段翻译成：**后端 Java 代码（表 + 逻辑 + 接口） + 前端页面代码**。

**这就是 NASL 的核心价值**：把"我要一个能增删改查待办的应用"这个想法，
用一小段规范描述表达出来，剩下全自动。

## 它能覆盖什么（能力范围）

NASL 覆盖的是**一个完整企业应用**的方方面面，不是只有某个局部。大致可分四大块：

### 1. 后端（服务端）
- **数据库表**：定义表、字段、主键、唯一约束、索引、默认值、精度（如金额保留两位小数）
- **实体模型**：数据对象、数据结构（DTO）、枚举
- **业务逻辑**：方法、入参、出参、事务、条件/循环/赋值/调用等逻辑
- **对外接口**：REST 接口、请求/响应结构、接口与逻辑的绑定
- **数据库/外部数据源**：连接配置、数据访问

### 2. 前端（页面/交互）
- **页面**：列表页、详情页、表单页、弹窗、区块
- **页面元素**：表格、输入框、按钮、下拉等组件
- **数据绑定**：页面数据从哪来（接口/查询）、如何展示
- **交互逻辑**：点击、提交、跳转等事件处理

### 3. 流程与权限（企业应用特色）
- **审批流程**：会签、或签、顺序审批、多级审批等策略
- **触发器**：定时、消息、接口等触发的自动化
- **权限控制**：谁能访问、谁能操作、角色/组织/部门

### 4. 平台扩展能力
- **内置能力**：文件、日志、国际化、认证、消息、对象、数学、字符串、日期时间等标准库
- **多端适配**：同一套定义可生成 PC / 移动端 H5 / 小程序
- **外部对接**：调用其它系统接口、扩展组件、微服务调用

**一句话概括**：从数据库表 → 后端逻辑 → 前端页面 → 审批权限，**一整条企业应用的链路它都能描述、都能生成**。
而且往往**一次定义、多端生成**（PC + 移动 + 小程序共用一份）。

---

## 它的亮点（优势）

1. **覆盖面全** —— 从数据库表、实体、业务逻辑、接口，到页面、审批流程、权限，企业应用该有的都有（见上节）。
2. **有类型概念** —— 像编程语言一样，每个东西都有明确类型（数字、文字、日期…），不容易出错。
3. **能唯一定位** —— 应用里的每个东西都有"地址"（类似门牌号），能精确找到、修改、报错时定位。
4. **一份模型多处用** —— 同一个模型既能存储、又能给人看、又能让 AI 和工具消费。

---

## 结论

**一句话**：NASL 提供了一套成熟、完整的"把应用描述变成可运行代码"的设计范式，
**"一份模型、三种看法"的核心思路尤其值得学习**。

- **值得借鉴**：覆盖完整、有类型、能寻址、一份模型多处用。
