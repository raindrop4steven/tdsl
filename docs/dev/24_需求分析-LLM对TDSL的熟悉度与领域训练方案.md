# 24_需求分析 — LLM 对 TDSL 的熟悉度与领域训练方案

> 状态：需求分析中（阶段一）
> 审阅标记：`<rv-add>` 新增 / `<rv-del>` 删除 / `<rv-chg>` 修改

## 1. 问题描述

- 通用大模型（GLM/GPT/Claude/DeepSeek）不了解 TDSL，直接 prompt 生成存在：语法幻觉（误用 TS 语法到 entity/where 等领域扩展）、语义错误（查询链/端点暴露约束）。
- 对标事实：网易 CodeWave NASL 遇到同样问题，纯提示工程评测 HumanEval 通过率 ~55.3%，其中 ~18.3% **不训练就提升不了**；最终投入领域模型训练（SFT + DPO），HumanEval 提升至 ~80%。
- 我们当前 M9 agent 实战已暴露类似信号：诊断修复闭环有效，但**首轮生成质量依赖 few-shot 示例覆盖度**，难覆盖所有场景。

## 2. NASL 方案拆解（对我们可参考的部分）

| NASL 环节 | 对应我们的现有资产 | 缺口 |
|-----------|-------------------|------|
| 基座模型评测（DeepSeek/Qwen Coder 系列） | 无（直接用 GLM 端点） | 缺选型评测 |
| 数据合成：自然语言指令→代码 问答对，10W+ | agent session 记录（用户真实需求→产出） | 无规模化合成管道 |
| **语言沙箱**：编译/语义/执行校验 | **compile_tdsl 裁判（已有，天然等价物）** | —（可复用，差异：无执行能力，仅 parse/typecheck） |
| 多轮反馈合成（报错回流修复） | repair.ts 诊断修复闭环（已有） | 未用于批量合成 |
| SFT（LoRA）+ 拒绝采样回流 | 无 | 全缺 |
| DPO 偏好对齐（沙箱反馈正负样本三元组） | 无 | 全缺 |
| Benchmark 驱动迭代（Badcase 回流） | 规划中（memory 下一步第 1 位） | 未落地 |

## 3. 可选方案（需求层面）

<rv-add>

- **方案 A：不训练，继续强化提示工程 + Grammatical 示例扩展**。成本最低；对标数据显示存在天花板（~18% 的问题训练不可解），但 M9 修复闭环可部分弥补。
- **方案 B：先落地评测基准，再决定训练**。利用 CLI + agent session 天然采集器，量化"当前到底多少可编译率"，用数据说话（NASL 团队口径：No Data, No BB）。评测基准本身也是未来训练的验收工具——无论选不训练都需要。
- **方案 C：领域模型训练（SFT，可选后续 DPO）**。数据合成由“通用大模型 + TDSL 语法说明 + compile_tdsl 多轮反馈”生成问答对（冷启动方式与 NASL 完全一致）；R1 类推理模型合成收益显著是他们的关键经验。成本高：需 GPU、基座选型、持续投入；先判私有化部署是否是我们的需求（NASL 的强动机之一是私有化交付）。
- **方案 D（DSL 侧零成本优化）**：TDSL 表达式/控制流照 TS 手感已是[有意设计](docs/dev/24 决策 D4)，训练/提示时应让模型"复用 TS 先验 + 只学领域扩展"，这是数据合成的提示词要点，三方案通用。

</rv-add>

## 4. 初步建议（待讨论）

<rv-add>
推荐路径：**B → (视数据) → C**。理由：
1. 评测基准已在 memory "下一步"第 1 位，且是方案 C 的前置工具（训练前后都要用同一基准验收，NASL 团队强制"AI 功能升级必须过 Benchmark 才上线"）。
2. compile_tdsl + session 记录即数据管道雏形，方案 C 的最大成本（沙箱 + 数据）我们已解决一半。
3. 训练是否立项取决于私有化部署需求这一产品问题，不是技术问题——需要用户拍板。
</rv-add>
