# 43 · 需求分析 — 业务动作状态化与链路联动（去"CRUD 架子感"）

> 状态：⏸ 待用户 Gate 确认（阶段一·需求分析）
> 日期：2026-09-16
> 关联：dev/39（芋道能力验证）、dev/40-42（@ref）、dev/29（G2 前端表达式域）、dev/35（编译器优先清单）

## 1. 背景

用户实测芋道工程后判定"像个 CRUD 架子"：业务规则写在 logic 里，但**界面与业务链都不体现**。实测证据（当前代码）：

| # | 现象 | 证据（当前实现） |
|---|------|------------------|
| 1 | 单据状态机只存在于后端 | `auditErpPurchaseIn` 有 `status !== UNAUDIT` 抛错校验，但列表/详情里「编辑/删除/审批/反审批」**永远全部显示**，点错才弹 toast |
| 2 | 单据间无联动（业务链断裂） | `auditErpPurchaseIn` 只把 `status` 改成 AUDITED：**不写库存、不记库存流水、不回写订单明细 `inCount`、不推进订单状态**；库存变动要去库存模块单独手工操作 |
| 3 | 明细与计算不露出 | `saveErpPurchaseIn` 在服务端重算 `totalCount/totalPrice`，但表单录入时看不到合计；详情抽屉只显示主表字段，看不到明细行 |

结论：**不是 logic 没写，而是缺"动作可用性"与"业务链"两类表达，外加明细/合计的展示缺口。**

## 2. 目标（本切面范围）

### F1 动作状态化（语言 + codegen）

按钮支持可用性条件绑定：

```tdsl
<table dataSource={useQuery('queryErpPurchaseIn')}>
  <button text="审批"   action={useMutation('auditErpPurchaseIn', row.id)}
          visible={row.status === DocStatus.UNAUDIT} />
  <button text="反审批" action={useMutation('deauditErpPurchaseIn', row.id)}
          visible={row.status === DocStatus.AUDITED} />
  <button text="编辑"   action={openDialog('erpPurchaseInForm', row)}
          disabled={row.status !== DocStatus.UNAUDIT} />
</table>
```

- `visible={条件}`：不满足则**不渲染**该按钮（列表操作列 / 详情抽屉 / 页面级）；
- `disabled={条件}`：满足则按钮置灰（保留位置，避免操作列宽度跳动）；
- 条件表达式限定为**行上下文**（`row.<字段>` 的比较/逻辑组合，枚举用 `EnumType.MEMBER`）；
- codegen-react 映射：`visible` → 条件渲染；`disabled` → antd `disabled`；枚举成员 → 字符串字面量（列值即枚举名）。

### F2 详情/表单的明细与合计（语言 + codegen）

- `<detail>` 块内支持 `<repeat field="items">` 子表（只读表格，列 = `<column>`），详情抽屉能看单据明细行；
- 表单明细（既有 repeat）**汇总展示**：`<summary>` 声明求和字段，录入时实时显示合计（如「明细合计：¥xxx」）。
  - 依赖表达式域扩展：对 repeat 明细列表求 `count * productPrice` 之和（对标 dev/29 前端表达式域，纯函数、无 IO）。

### F3 业务链联动（纯 logic 补全，无新语法）

以 ERP 单据为主线，把单据动作接到库存与上下游：

| 动作 | 联动 |
|------|------|
| 采购入库 审批 | `Stock(count +)`（按 warehouse×product）；写 `StockRecord(采购入库, bizId/bizNo)`；回写 `PurchaseOrderItem.inCount`；订单全部入库 → 订单 `status=AUDITED` |
| 采购入库 反审批 | 库存回减 + 写取消流水；`inCount` 回退 |
| 采购退货 审批 | `Stock(count -)` + 退货出库流水 |
| 销售出库 审批 | `Stock(count -)` + 销售出库流水；回写 `SaleOrderItem.outCount` |
| 销售出库 反审批 | 库存回增 + 取消流水 |
| 销售退货 审批 | `Stock(count +)` + 退货入库流水 |
| 采购付款 审批 | 核销：回写 `PurchaseIn.paymentPrice` / 订单已付；付款单 `status=AUDITED` |
| 销售收款 审批 | 核销：回写 `SaleOut.receiptPrice` / 订单已收 |

共性校验（与状态机一致）：仅 `UNAUDIT` 可审批、仅 `AUDITED` 可反审批；**库存不足时出库审批抛业务错误**（`throw '库存不足'` → 前端 message 弹窗，已有链路）。

## 3. 状态流转

| 实体 | 状态字段 | 转换 | 触发 |
|------|----------|------|------|
| PurchaseIn/Return、SaleOut/Return、FinancePayment/Receipt | `status: DocStatus` | `UNAUDIT → AUDITED` | 审批（含库存/核销联动） |
| 同上 | | `AUDITED → UNAUDIT` | 反审批（联动回退） |
| PurchaseOrder | `status: DocStatus` | `UNAUDIT → AUDITED` | 全部明细 `inCount >= count`（入库审批推进） |
| SaleOrder | `status: DocStatus` | `UNAUDIT → AUDITED` | 全部明细 `outCount >= count`（出库审批推进） |

CRM（合同/回款）本轮**只做 F1 按钮状态化**，不加跨模块联动（边界见 §5）。

## 4. 验收标准（阶段五测试依据）

| # | 场景 | 预期 |
|---|------|------|
| A1 | 未审批入库单的列表行 | 只显示「审批」「编辑」；「反审批」不渲染 |
| A2 | 已审批入库单的列表行 / 详情抽屉 | 只显示「反审批」；「编辑」置灰（disabled） |
| A3 | 入库审批后 | 库存 `count` 增加、`StockRecord` 有「采购入库」流水、订单明细 `inCount` 回写、订单全入库后状态推进 |
| A4 | 出库审批库存不足 | 抛业务错误，前端弹窗提示，库存不变 |
| A5 | 详情抽屉 | 显示明细子表（单据明细行）+ 明细合计 |
| A6 | 核销 | 付款审批后入库单 `paymentPrice` / 订单已付金额回写 |
| R1 | 回归 | 既有 jxc/todo/todo-multi 样例零改动、全仓单测绿、`check-spec` 100%、双端 build ✓ |

## 5. 非目标（本轮不做）

- 工作流引擎 / 审批轨迹时间线 / 操作日志（P2，另立切面）；
- 权限矩阵、多租户、数据权限（dev/39 已裁剪）；
- 批量操作（多选批量审批/删除）、导出、分页排序、跨仓调拨、库存盘点联动；
- CRM 合同/回款的跨模块联动（仅按钮状态化）；
- `@ref` 之外的新查询能力（如 join 展示二级字段）。

## 6. 受影响面

| 包 | 改动 |

| examples/yudao | tdsl（按钮 visible/disabled + detail 子表 + 审批联动 logic）、spec.yaml（动作可用性维度）、seed（可选：造库存边界数据） |

## 7. 风险

| 风险 | 应对 |
|------|------|
| 视图表达式里枚举成员 `DocStatus.UNAUDIT` 的解析/校验边界 | 设计阶段定：仅支持「`row.<字段> <op> 枚举成员`」比较子集，不开放任意表达式 |
| `visible` 导致操作列宽度/折叠（Dropdown「更多」）行为变化 | 折叠计划以「静态按钮数」为准，visible 只控制渲染，不改折叠结构 |
| 库存联动的并发/幂等（重复审批） | 状态机前置校验已保证单向；反审批走反向流水，幂等以状态为准 |
| 详情子表与表单明细渲染复用度 | codegen 复用 repeat 单元格的只读分支，避免两套实现 |

## 8. 外部依赖

- 无新增 npm/java 依赖；不引入工作流/规则引擎。
