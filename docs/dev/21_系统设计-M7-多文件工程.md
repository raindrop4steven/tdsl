# 21 系统设计：M7 —— 多文件工程（分片合并）

> 关联：`10_设计/设计总览.md` §2（架构）、`dev/15`（M1 命名空间，作用域机制复用）、`dev/14`（路线图，CLI 前置）
> 状态：**已实现（编码/测试完成，2026-09）** —— `parseProject`（parser）/ `Diagnostic.file`（typecheck）/ `examples/todo-multi`（5 功能域分片 + 对拍，`npm run slice:multi` 双端 build 通过）
> 定位：让一个 app 由多个 `.tdsl` 文件组成（多 AI 分工产出），对标 NASL 的"多模块 + 全局命名空间"形态。
> 不做 import 语句、不做文件级可见性控制。

---

## 1. 目标与验收

### 1.1 背景（为什么现在做）

- **现状**：`parse(input: string)` 一次只吃一个文件，产出一个 App；跨文件引用**做不到**（`@export` 注解被识别但跳过，无语义；app 名硬编码 `'todo'`，`parser.ts:100`）。
- **NASL 对标结论**（见 `00_参考资料/NASL调研.md` §4.2）：NASL 天然多文件——app 是模块集合，`app.loadAll()` 组装；引用靠 **app 级全局命名空间（nodePath）**，**无 import 语句**。
- **驱动力**：
  1. **多 AI 协作**：不同切面的产物（实体/逻辑/页面）分文件落盘，互不踩踏；
  2. **CLI 地基**（下一步切面）：`tdsl parse/check/generate src/` 天然以"目录下多个 .tdsl"为输入；
  3. **LLM 友好**：单次生成单文件分片，出错率低，不用记 import/路径。

### 1.2 达成什么

1. **新 API `parseProject(files, appName?)`**（`@tdsl/parser`）：吃 `[{ path, content }]` 文件列表，产出**一个** AppNode；跨文件短名直接引用（无 import）。
2. **零新语法**：每个文件的内容与现在单文件的顶层声明完全一致（entity/struct/enum/logic/interface/page/service/component）。
3. **`@datasource` 按文件隔离**：文件内声明/切换数据源只影响本文件实体归属；跨文件同名 datasource 自动合并实体（两文件都写 `@datasource('erp')` → 实体都进 erp）。
4. **诊断带文件定位**：typecheck `Diagnostic` 增加 `file?` 字段；`TdslSyntaxError` 增加 `file` 字段；跨文件重名冲突报错消息含两个文件路径。
5. **端到端验证**：todo.tdsl 拆分为多文件版，`npm run slice:multi` 跑通 parse→typecheck→双端 codegen→mvn compile + vite build，且**产物与单文件版逐字节一致（对拍）**。

### 1.3 验收标准（全部达成）

- [x] `parseProject` 单测：跨文件短名引用（logic 用别文件的 entity/struct）、文件顺序无关、跨文件同名 datasource 合并、跨文件重名报错（消息含双文件路径）、空文件、app 名参数化。parser 48（+11）
- [x] `parse(input)` 单文件入口零回归（现有 37 parser 单测不动、全绿）。
- [x] typecheck 诊断新增 `file` 字段的单测（3 例：跨文件悬空/跨文件未知链/单文件 `<stdin>`）。
- [x] `npm run slice:multi`：todo-multi 5 分片双端 build 通过，且产物与单文件版 GeneratedFile **逐字节一致**。
- [x] 不回归：`npm test`（155）与 `npm run typecheck` 全绿；`npm run slice` 照常通过。

**新增单测 16 个**：parser +11 / typecheck +3 / codegen-java +2（app 名参数化 + 非法名报错），139 → 155。

### 1.4 范围外（本期不做）

- `import` 语句 / 文件路径解析 / 循环引用处理（NASL 也没有，YAGNI）
- `@export` / 可见性控制（识别跳过维持现状，留作未来钩子）
- 目录扫描策略（递归/过滤）——本期 API 吃显式文件列表，扫描留给 CLI 切面
- playground / llm 示例矩阵的多文件化（llm repair 对 `file` 字段天然兼容——可选字段）

## 2. 设计决策

| # | 决策 | 理由 / 依据 |
|---|------|-------------|
| D-M7-1 | **NASL 式分片合并，不做 import** | 对标 NASL（loadAll 组装模块）；link 是两遍式（先建表再绑定），**前向引用天然无问题**，文件顺序无关；LLM 不用记 import |
| D-M7-2 | **合并发生在 link 之前**，typecheck / codegen **零改动**（仍吃一个 AppNode） | 现有 139 单测是回归护栏；多文件只是"语法糖"，语义核不变 |
| D-M7-3 | `@datasource` 作用域**按文件隔离** | 每个文件独立 parseFragment，切换互不干扰；同名 ds 跨文件合并实体（与"同文件同名 ds 复用"语义一致） |
| D-M7-4 | **跨文件重名 → 报错**（error，含双文件路径）；同文件重名维持现状 | 重名会让 nodePath/符号表错乱，必须硬报；宽松策略只针对"无法静态推导"的场景，这是能确定推导的 |
| D-M7-5 | 节点溯源：parse 时给每个**顶层声明节点**打 `file?: string`（BaseNode 可选字段），诊断时 nodePath 反查顶层节点取 file | 最小侵入：不加新节点类型（不动判别联合），下游 `never` 收窄点全部零改动 |
| D-M7-6 | **app.name 参数化**：`parseProject(files, name)`，`parse()` 默认名维持 `'todo'` | codegen-java 的 groupId/包名依赖 app.name（`com.${app.name}`）；改默认值会破坏现有产物对拍，保持兼容 |
| D-M7-7 | 报错风格沿用 `TdslSyntaxError`（merge/link 阶段错误 line=0/col=0 + 引导语） | 与现有 link 阶段行为及 llm/repair 的"人话化"处理（`ParseErrorInfo.linkStage`）一致 |

## 3. 架构方案

### 3.1 管线

```
files[{path,content}] ──parseFragment(逐文件)──▶ Fragment(AppNode 形状, 节点已打 file)
                     ──mergeApp(冲突检查+段合并)──▶ AppNode
                     ──linkApp(现有,不动)──▶ Typed AST
                     ──check / generateJava / generateReact(全部不动)
```

### 3.2 parser 内部改造（`packages/parser/src/parser.ts`）

| 现状 | 改造后 |
|------|--------|
| `parseApp()` 硬编码 `name:'todo'`，循环消费 token 流 | 拆为 `parseAppInto(name, file)`：形状/逻辑不变，仅透传 name+file 并给顶层声明节点打标 |
| `parse(input)` = tokenize → parseApp → linkApp | `parse(input)` = `parseProject([{path:'<stdin>',content:input}])`（默认名 `'todo'`，保持兼容） |
| （无） | 新增 `parseProject(files, appName='todo')`：逐文件 parseFragment → mergeApp → linkApp → AppNode |
| （无） | 新增 `mergeApp(name, fragments)`：datasources 同名合并（entities 拼接）；structures/enums/logics/interfaces/views/services/components 顺序拼接；跨文件重名 → `TdslSyntaxError(含双 file)` |

关键点：

- **不新增节点类型**：Fragment 直接复用 `AppNode`（name 占位），merge 只做数组拼接——判别联合与全部 `never` 收窄点零改动。
- **打标时机**：单文件 parse 内完成（该文件所有顶层节点 `file = path`），merge 阶段不再触碰节点。
- **linkApp 不动**：M1 分层符号表 + `resolveShort(table, ref, ctxDs)` 在合并后的 App 上工作，天然支持跨文件引用（entity/logic/struct 的短名解析本就依赖符号表，与文件无关）。
- 文件名取 `path` 原样（不解析相对路径语义，展示用）；`<stdin>` 用于单文件入口。

### 3.3 诊断与错误定位

| 位置 | 改动 |
|------|------|
| `core/types.ts` | `BaseNode` 增加可选 `file?: string` |
| `parser`（`TdslSyntaxError`） | 增加 `file?: string`；parse 阶段错误带所在文件；merge 冲突错误同时列出两个文件 |
| `typecheck`（`Diagnostic`） | 增加 `file?: string`：check 开始时构建 `nodePath → file` 映射（遍历 app 顶层段），产出诊断时按 `ownerPath` 反查 |
| `llm/repair` | 零改动（`file` 可选字段，展示层有值则带出） |
| `playground` | 零改动（单文件场景 `file` 为 `<stdin>`，可选择性隐藏） |

### 3.4 语义规则明细

| 场景 | 规则 |
|------|------|
| 文件 A 定义 entity Order，文件 B 的 logic 引用 `Order` | ✅ 短名直接解析（link 统一绑定） |
| 文件 A、B 都 `@datasource('erp')` | ✅ erp datasource 合并，两文件实体都归 erp |
| 文件 A、B 各定义 `@datasource('a') entity Order` 与 `@datasource('b') entity Order` | ✅ 合法（跨源同名共存，M1 已有语义；引用需限定名） |
| 文件 A、B 同数据源下都定义 entity Order | ❌ 报错：`duplicate entity 'Order' in a.tdsl and b.tdsl` |
| 文件 A、B 都定义 logic `calc` | ❌ 报错（logics 是扁平全局段） |
| 文件 B 引用文件 A 里不存在的名字 | ❌ 现有报错不变：`cannot resolve type 'X'` |
| 空文件 / 纯注释文件 | ✅ 合法（产出空 fragment） |
| 文件内 `@datasource` 切换只影响本文件后续实体 | ✅（parseFragment 文件内状态机不变） |

### 4.0 拆分原则：语言层零约束，拆法是使用策略

合并机制（parseProject）**对拆法完全不感知**——只做逐文件 parse → 声明拼接 → 冲突检查，文件怎么组织它不关心（D-M7-2 的直接推论）。拆分标准是**使用方组织策略**，三种真实拆法：

| 拆法 | 形态 | 适合谁 |
|------|------|--------|
| 按节点段（全部实体一个文件…） | entities.tdsl / logics.tdsl / pages.tdsl | 编译器测试（覆盖段合并/跨文件引用） |
| 按 NASL 库形态 | backend.tdsl（entity+struct+logic+interface）+ frontend.tdsl（page） | 对标 NASL 后端库/前端库 |
| **按功能纵向切（推荐，示例采用）** | 一个功能域 = 一个文件，含它的实体+逻辑+页面 | **多 AI 协作真实形态**：每个 AI 领一个功能域，互不踩踏；同功能引用在同文件内，跨文件引用最少 |

## 4. 示例（端到端样例：`examples/todo-multi/`）

按**功能纵向切**拆为 5 个文件，内容不做任何改写（仅文本切分）；共享数据模型独立一个文件（多功能共用的实体/结构）：

```
examples/todo-multi/
  tdsl/
    01_order-model.tdsl   # @datasource + entity Order/OrderItem + struct OrderInput/OrderItemInput/OrderDetail（共享数据模型）
    02_order-create.tdsl  # logic createOrder + interface OrderApi + page OrderCreate（下单功能域）
    03_order-query.tdsl   # logic listOrders/searchOrders/pageOrders/topOrders + page OrderList（查询功能域）
    04_order-detail.tdsl  # logic getOrderDetail + page OrderDetail（详情功能域）
    05_order-misc.tdsl    # logic deleteOrder/orderStats/sumByCustomer（辅助功能域）
  scripts/slice-multi.ts  # 复用 slice.ts 管线：读 tdsl/*.tdsl → parseProject → check → 双端 codegen → build
```

注：todo.tdsl 是单订单域，entity 只有 2 个，故实体归属 01 共享模型文件；真实多域项目（如 erp）可直接把“某功能的实体+逻辑+页面”全放一个文件——机制上完全等价（同文件多段混排本来就是现有单文件能力）。

**对拍**：`slice-multi.ts` 内置对拍断言——同一 AppNode 分别来自 `parse(单文件拼接文本)` 与 `parseProject(文件列表)`，`generateJava/generateReact` 产物逐字节一致。这把“拆分无语义漂移”锁进单测/脚本。

npm script：`"slice:multi": "ts-node/-w @tdsl/... examples/todo-multi/scripts/slice-multi.ts"`（具体写法与 slice.ts 一致，用 workspace tsx 驱动）。
