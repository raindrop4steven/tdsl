# 24 系统设计：M10 —— 运行回路（前后端跑起来 + 用户反馈驱动的迭代循环）

> 关联：`dev/23`（M9 Agent 服务，本切面在其上扩展）、`dev/14`（总路线）
> 状态：**设计中（需求 Gate 待确认，编码未开始）**
> 一句话：**不只生成代码——把前后端真正跑起来，运行时反馈回流 agent，用户说"哪里不对"→ agent 改 DSL → 编译 → 重启 → 日志确认，闭环交付"能用的应用"。**

---

## 1. 需求（用户原话归纳）

> 不是生成代码、前后端能起来就不管了。而是：前后台代码编译运行起来，根据用户反馈动态调整：
> **自然语言 → DSL → checker → generate code → run（npm dev + java）→ 用户反馈 → 再调整**，如此循环。

M9 交付后的缺口：

- 生成产物只是"编译通过"，接口在真实运行中可能 500（DB 未建表/未启动）、页面点了报错无人知道。
- 用户在浏览器里发现的问题（表单交互、报错弹窗、数据不对）没有回流 agent 的通道。
- "保存草稿 vs 保存"这类语义偏差，靠用户在聊天里纠正后 agent 能改——但改完无法验证"真的好了"。

## 2. 达成什么

`packages/server` 扩展（不新建包），四件事：

1. **运行编排器（runner.ts）**：每会话管理一组进程
   - 后端：`generated/java` → `mvn -q spring-boot:run`（端口 `8080+i`）；启动探针 `GET /actuator/health`（或应用 `/healthz`）→ 状态机 idle→starting→up→failed
   - 前端：`generated/react` → `npm install`（首次/依赖变化）→ `npm run dev -- --port 5173+i --strictPort`（vite HMR：DSL 改动重生成后页面自动热更，无需重启）
   - 每会话进程树输出写入沙箱 `logs/{backend,frontend}.log`（环形截断，防撑爆）
   - 工具 `run_app`（action: up/down/restart/status/logs）——**编排固定命令，不是 bash**，延续白名单原则
2. **运行时反馈通道（自动采集）**：
   - 后端：日志尾部 ERROR/Exception 关键行 + HTTP 5xx 计数（简单 grep 日志，不引 APM）
   - 前端：生成 App 内注入轻量 reporter——`window.onerror` / `unhandledrejection` / `fetch` 非 2xx 拦截 → `POST /api/client-error` → server 写入该会话 `logs/frontend.log`（agent 用 read 工具检索）
3. **agent 循环策略（系统提示词）**：
   - 用户反馈 → `read_tdsl_files` 定位分片 → 修改 → `compile_tdsl` → `generate_code`（重生成落盘）→ `run_app restart`（重启后端；vite HMR 自动热更前端）→ 读日志确认无 ERROR → 文字总结"已修复，请刷新页面验证"
   - 编译通过不再是交付标准；**运行日志无 ERROR + 用户确认**才是
4. **页面 UI**：右栏新增"运行状态"面板（backend/frontend 状态灯 + 端口链接 + 日志尾部预览 + 预览 iframe 可选）；聊天即反馈入口（用户描述问题，agent 自己去查日志）

## 3. 设计决策

| # | 决策 | 理由 |
|---|------|------|
| D-M10-1 | DB 用 **H2 内存库 + ddl-auto:update**（codegen-java 脚手架切换） | 零安装零配置，演示即起；MySQL 兼容模式可后配。用户连真库作为进阶配置（env 覆盖 jdbc url） |
| D-M10-2 | 后端跑 **`mvn spring-boot:run`**（不打包 jar） | 免打包步骤；依赖已由 mvn compile 拉齐；重启=杀进程重跑 |
| D-M10-3 | 前端 **vite dev**（非 build+preview） | HMR 即时可见 agent 改动；无需预构建等待 |
| D-M10-4 | 进程管理：Node `child_process.spawn` + **tree-kill**；每会话最多一组前后端进程 | 简单可控；Windows 下进程树清理是硬需求 |
| D-M10-5 | 端口分配：会话序号偏移（java `8080+i`、vite `5173+i`），写入生成物（`API_BASE` 注入） | 多会话并发互不冲突；前端 API base 指向同会话后端 |
| D-M10-6 | 错误采集**内建轻量**（日志 grep + 前端 fetch 拦截），不引 APM/Playwright | 演示价值/成本比；Playwright 自动点页面留作后置增强 |
| D-M10-7 | `run_app` 是工具而非 bash 白名单放开 | 攻击面不扩大；命令集固定可审计 |
| D-M10-8 | API base 参数化：codegen-react 的 `API` 常量改为按构建注入（`import.meta.env` 或 dev server proxy） | 多会话端口隔离的前端前提；默认 vite proxy `/api` → 同会话后端，避免跨域 |

## 4. 架构增量

```
packages/server
  ├─ runner.ts        # NEW：进程状态机（up/starting/down/restart）+ 日志环形缓冲 + 端口分配
  ├─ tools.ts         # +run_app 工具（编排命令白名单）
  ├─ index.ts         # WS 事件 + /api/run-status + /api/client-error（前端错误回流）
  └─ public/index.html# 运行状态面板（状态灯/链接/日志尾）

codegen-java（一次脚手架改动）
  ├─ pom：spring-boot-maven-plugin + H2 依赖 + devtools(可选)
  ├─ application.properties：H2 mem、ddl-auto=update、server.port 参数化
  └─ 主应用加 /healthz 端点（探针用）
```

会话生命周期：`run_app up`（首次 install+启动）→ 用户验证 → 反馈 → agent 改分片 → compile → generate_code → `run_app restart` → 日志确认 → 交付。会话关闭/超时 → `down`（tree-kill + 端口释放）。

## 6. 风险与对策

| 风险 | 对策 |
|------|------|
| Windows 进程树 kill 不净（npm/mvn 子进程残留占端口） | tree-kill；启动前端口占用检测；残留时提示人工清理命令 |
| 并发多会话资源（内存/端口） | 每会话一组进程上限；全局并发会话上限（如 3）；TTL 回收 |
| Spring Data 派生方法名 agent 乱写 → 启动即崩 | 启动探针捕 failed + 日志回流 agent 自修（正是本循环的用武之地）；必要时日志模板教 agent 规范命名 |
| mvn/npm 首次下载慢 | 依赖走公网已配好；启动状态流式可见（"maven 下载依赖中"）|
| 演示环境无外网 | mvn/npm 依赖缓存预 warm；文档给离线仓配置说明 |
