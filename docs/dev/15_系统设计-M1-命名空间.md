# 15 系统设计：M1 —— 命名空间 / 作用域（数据源级）

> 关联：`docs/dev/14_路线规划-NASL对标与前后端能力.md` §7（命名空间/作用域专项）、`10_设计/设计总览` §4（引用与寻址）
> 状态：**阶段二（系统设计）** — 待用户 Gate 确认
> 定位：把 `linkApp` 的"全局唯一短名"改为**分层作用域**，让"两个数据源各有同名实体"成为合法表达，
> 跨源引用用限定名 `dsName.EntityName`。这是 M2 查询 / M4 View / M6 外部能力引用解析的共同基础。

---

## 1. 目标与验收

### 1.1 现状问题

`linkApp`（parser.ts:510）用**单一全局 `Map<name,path>`**：
- 实体/结构/枚举短名强制全局唯一，**跨数据源同名实体直接编译失败**。
- 无局部作用域概念（logic 内变量是后加的，且不与类型名冲突检查）。

这限制了真实业务表达：多数据源（多库/多租户）各有 `Order`/`User` 是常态。

### 1.2 达成什么

1. **实体短名以数据源为作用域**：`erp.Order` 与 `crm.Order` 可共存，不再冲突。
2. **限定名语法**：`dsName.EntityName` 显式引用跨源实体。
3. **短名书写糖**：当前数据源/全局唯一时，短名仍可直接写（不破坏现有 TDSL）。
4. **结构/枚举/逻辑/接口**保持 app 全局唯一（它们不属于任何数据源）。

### 1.3 验收标准

- [ ] `parse` 通过：两个数据源各有 `Order` 实体，结构/逻辑里用 `erp.Order` / `crm.Order` 限定引用，link 成功且 nodePath 不同。
- [ ] `parse` 报错：**同数据源内**重名实体（`defaultDS.Order` 定义两次）→ `duplicate` 错误。
- [ ] 短名仍可用：单数据源场景（现有 Todo/Order demo）零回归。
- [ ] `resolve(app, 'app.datasources.erp.entities.Order')` 能解析到正确实体。
- [ ] typecheck / codegen 对限定名的实体方法（`erp.Order.all`）工作。

## 2. 作用域模型

### 2.1 作用域层次

**类型命名空间**（跨节点引用，link 阶段绑定）：

```
app 全局（顶层）    : structure / enum / logic / interface（短名唯一，属 app 不属任何 ds）
数据源作用域        : entity（短名在数据源内唯一；跨源同名合法）
```

**变量作用域**（logic 方法体内，codegen 阶段）——**本切面一并纳入**：

```
方法体作用域        : logic 的 param + 顶层 := 声明（方法体内全程可见）
块作用域            : if/then-else、for 循环体内 := 声明 / ForEach item（块内可见，块外不可见）
同名语义            : 对齐 Java —— 无遮蔽（Rust 才有 shadowing）。:= 沿链查找：
                    链上已有同名变量 → 复用（生成赋值，类型沿用外层）；
                    链上无同名 → 声明新变量（块内，块外不可见）
```

> 例：`{ int x = 1; { x = 2; } }`（Java 合法：复用外层）——
> TDSL `if { x := 2 }` 编译为 `x = 2;`，块外 x 变 2。
> Java 不允许 `{ int x = 1; { int x = 2; } }`（遮蔽），TDSL 也不产生遮蔽。

> 两类作用域正交：变量名不进入类型符号表；类型名不进入变量作用域。
> 同一 logic 内变量 `Todo` 与类型 `Todo` 可共存（写 `Todo.all` 时按类型解析，写 `todo.field` 时按变量解析——codegen 已区分）。

### 2.2 符号表结构（core 提供）

```ts
// 类型命名空间
interface TypeSymbolTable {
  global: Map<string, string>;      // 短名 → nodePath（structure/enum/logic/interface + 全局唯一的 entity）
  dataSources: Map<string, Map<string, string>>;  // dsName → (短名 → nodePath)（entity）
}

// 变量作用域（logic 方法体）
interface VarScope {
  parent: VarScope | null;          // 外层作用域链
  vars: Map<string, string>;        // 变量名 → Java 类型
}
```

- **实体声明**（类型表）：
  - 必进 `dataSources[dsName]`（同数据源重名 → 报错）。
  - 若短名**全局唯一**（无其他数据源同名）→ 同时进 `global`（供无 ds 上下文的短名引用）。
  - 若跨源重名 → 不进 `global`（必须用限定名）。
- **结构/枚举/逻辑/接口**：进 `global`（重名报错，现状不变）。
- **变量作用域**（codegen 生成 Service 方法体时）：
  - 进入 `if`/`for` 块 → push 新 `VarScope`；块结束 → pop。
  - `:=` 声明 / ForEach item / param → 写入当前 `VarScope.vars`。
  - 变量查找 → 沿作用域链向上（内层优先）。
  - **同名语义（对齐 Java）**：`:=` 先沿链查找，链上已有同名 → 复用（生成赋值 `x = v;`，
    类型沿用外层，不声明新变量）；链上无同名 → 声明新变量（`Type x = v;`，块内可见）。

### 2.3 解析规则（优先序）

```
resolveShort(name, ctxDs?):
  1. ctxDs 有值 → 查 dataSources[ctxDs][name]（当前数据源优先）
  2. 查 global[name]（结构/枚举/逻辑/接口 + 全局唯一实体）
  3. 未命中 → "cannot resolve" 报错

resolveQualified(dsName, entName):
  → 查 dataSources[dsName][entName]，未命中报错
```

- `ctxDs`（当前数据源上下文）：遍历**实体属性**的 TypeRef 时传入该实体所在数据源；
  遍历结构/逻辑/接口时无 ctxDs（它们不属任何数据源，走全局）。
- 限定名 `dsName.EntityName` 显式指定数据源，不依赖 ctxDs。

### 2.4 冲突规则

| 冲突 | 处理 |
|------|------|
| 同数据源两实体同名 | **报错** `duplicate type name` |
| 不同数据源同名实体 | **允许**（作用域隔离），跨源必须限定名 |
| 限定名指向不存在的数据源/实体 | **报错** `cannot resolve` |
| 短名跨源重名但未限定 | **报错** `ambiguous 'Order', use 'dsName.Order'`（增强可读性） |

## 3. 语法与 IR 变更

### 3.1 类型引用（core/parser）

`TypeRef.reference.path` 语义扩展：允许两种形态（link 前书写面）：
- 短名：`Order`（link 按作用域解析）
- 限定名：`erp.Order`（link 按数据源解析）

```ts
// parser.parseTypeRef：default 分支支持 a.b
// 当前: { kind:'reference', path: t }         // t = expectIdent()
// 改为: 若 peek() === '.' 则消费 . + ident → path = `${a}.${b}`
```

link 后 `path` 统一归一为完整 nodePath（`app.datasources.erp.entities.Order`），resolve 语义不变。

### 3.2 实体方法调用（表达式，typecheck/codegen）

表达式里识别实体名的地方（`Todo.all` / `Todo.get(id)` / `Todo.where(...)` / `entity.save()`）需感知作用域：

- **codegen `entityNameOfIdent(app, name)`** → 改为 `resolveEntityName(app, name, ctxDs?)`：
  - `name` 含 `.` → 拆成 `dsName.entityName`，查 `dataSources`。
  - 短名 → 查当前 ds（若有）→ 全局唯一实体。
- **typecheck `resolveEntity`** 同步。

> 简化：实体短名在**单数据源**场景下仍全局唯一（进 global），现有 `findEntityByName` 逻辑不破坏；
> 多数据源场景新增的限定名实体方法（`erp.Order.all`）走新解析。

### 3.3 表达式限定名（可选增强）

`erp.Order.all` —— `Member(Ident('erp'), 'Order')` 形态。codegen 识别 `Ident` 为数据源名 + prop 为实体名。
本切面先支持**类型引用限定名**（`struct X { a: erp.Order }`）；**表达式限定名**（`erp.Order.all`）作为
M1 增量（若成本可控）或 M2 查询语言一并落地。

## 5. 边界

| 项 | 本切面 | 说明 |
|----|--------|------|
| 实体短名 → 数据源作用域 | ✅ | 核心 |
| 限定名 `ds.Entity`（类型引用） | ✅ | 核心 |
| 跨源同名实体共存 | ✅ | 核心 |
| 同源重名报错 | ✅ | 保持 |
| 表达式限定名（`erp.Order.all`） | 🟡 | 增量，或 M2 落地 |
| **logic 变量块作用域** | ✅ | **新增**：块内 `:=`/ForEach item 块内可见、块外不可见；同名对齐 Java 复用赋值（无遮蔽） |
| 数据源默认/隐式切换 | ❌ | 暂不支持（`@datasource` 显式声明） |
